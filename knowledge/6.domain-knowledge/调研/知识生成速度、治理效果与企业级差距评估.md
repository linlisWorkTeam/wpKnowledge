# domain-knowledge：知识生成速度、治理效果与企业级差距评估

> 分析日期：2026-09-03  
> 项目阶段：DEV-006 控制面实施中  
> 代码与规范基线：domain-knowledge PR #9、PR #10 及其 Accepted Spec  
> 结论性质：架构评估与目标建议；不是生产性能报告

## 一句话结论

domain-knowledge 的竞争力不是秒级生成文本，而是在分钟到小时级的异步流程中，把源码、知识、生成代码、真实测试、确定性 Gate 和发布记录组成可追溯闭环。它在“代码知识的可信生成与发布”上具有较强基础；与完整企业知识治理相比，主要缺口在身份权限、多项目隔离、责任体系、知识生命周期、来源生态、合规和长期运营。

## 当前工作流决定了什么速度

当前 LangGraph 工作流的主要路径是：

```text
编排
  ├─ 测试生成 → Oracle 验证 ─────────┐
  └─ 文档分块 → 知识生成 → 代码生成 → 检查
                                      ↓
                                独立评测 → 复核
                                      ↓
                              发布 / 下一轮迭代
```

测试生成和文档处理可以并行，但知识生成、代码生成、检查、评测和复核仍形成较长关键路径。默认策略最多三轮，文档 Worker 可配置为 0–5 个。Checkpoint 能减少故障后的重复工作，但不会减少正常路径上的模型推理和真实构建测试时间。

### 规划估计

以下区间用于容量规划，不能当作当前实测值：

| 场景 | 单轮估计 | 完整闭环估计 |
|---|---:|---:|
| 小型、结构清晰的模块 | 10–25 分钟 | 15–45 分钟 |
| 中型模块 | 20–50 分钟 | 30–120 分钟 |
| 大型或测试较慢的项目 | 45–120 分钟 | 1–4 小时 |
| 确定性 fixture 验收 | 秒到分钟 | 秒到分钟 |

该时间尺度与异步编码 Agent 相符。OpenAI 早期 Codex 资料给出的典型单任务时间为 1–30 分钟；GitHub Copilot cloud agent 的单会话硬上限为 59 分钟。二者只能说明行业产品的常见任务尺度，不能直接证明 domain-knowledge 的性能。

## 治理速度

治理速度至少包含三种不同指标：

| 环节 | 合理目标 | 主要限制 |
|---|---:|---|
| 失败事实进入待处理队列 | 秒级 | 事件提交与投影延迟 |
| 接手、确认和解决命令 | 亚秒到秒级 | API、鉴权、持久化和审计 |
| 重试失败节点 | 5–30 分钟 | 失败位置、模型调用和测试 |
| 带反馈重新生成 | 15–120 分钟 | 相当于有因果链的新批次 |
| 人工判断 | 分钟到天 | 证据质量、责任人和组织响应时间 |

DEV-006 的价值不是让模型推理更快，而是缩短从“发现异常”到“理解原因并采取合法动作”的时间。待处理事项必须关联原批次、失败节点、评测证据和 Gate；重试与重新生成不得改写历史决策。

## 治理效果预估

### 强项

1. **错误发布拦截**：独立评测与确定性 Gate 掌握发布权，模型不能自行把候选声明为 `VERIFIED`。
2. **证据与追溯**：批次、Agent 节点、Artifact、Evaluation、GateDecision 和 Publication 可以形成审计链。
3. **失败恢复**：节点边界 checkpoint、幂等键和配置快照可以减少重放副作用与重复执行。
4. **职责隔离**：CodeAgent 不读取参考源码或门禁答案，评测与发布不由生成 Agent 决定。
5. **局部纠错**：Correction 指向受影响范围，DocGen 增量修订后要求 fresh code generation 和复评。

### 弱项与风险

1. 已编码测试和确定性规则覆盖的问题拦截能力强，但未进入测试、规则或证据的语义错误仍可能漏检。
2. 初期更可能呈现“高精度、低到中等召回”：被拦截的问题通常真实，但系统未必发现全部问题。
3. 保守的失败关闭会降低错误发布率，也可能提高停止率和人工介入比例。
4. 自动修订质量依赖真实 Provider；fixture 只能证明机械链路，不能证明知识质量。
5. 当前缺少长期复发、误报、人工处理和跨项目效果数据，不能直接宣称治理效果先进。

### 建议目标，而非现状

| 指标 | 初期合理目标 |
|---|---:|
| 发布结果证据链完整率 | 100% |
| 已定义确定性门禁违规拦截率 | 接近 100% |
| 重复待处理事项抑制率 | ≥95% |
| 治理操作审计覆盖率 | 100% |
| 首次自动修订后通过率 | 50%–75% |
| 三轮内自动收敛率 | 70%–90% |
| 需要人工介入的批次 | 10%–30% |
| 已解决事项短期复发率 | <10%–20% |
| 语义问题误报率 | 初期可能为 15%–30% |

判断治理效果时，应优先观察错误发布率、自动收敛率、人工介入比例、事项复发率和每个有效知识版本的总成本，而不是只看生成耗时。

## 业界位置

| 维度 | 预估位置 | 判断 |
|---|---|---|
| 单任务生成速度 | 中等 | 多段 Agent 与真实测试增加关键路径 |
| 并行能力 | 中等 | 已有并行分支和 Worker，但尚非大规模调度平台 |
| 失败恢复 | 中上 | 有 checkpoint、配置冻结和幂等边界 |
| 证据与可追溯性 | 中上到高 | 生成、评测、Gate 和发布链路清晰 |
| 发布安全性 | 中上到高 | 确定性 Gate 不把模型自评当发布权威 |
| 语义错误发现 | 中等、待验证 | 取决于测试覆盖、评测规则和真实 Agent |
| 多项目吞吐和运营 | 早期 | 本地单服务、SQLite、项目空间尚未完成 |
| 企业治理完整度 | 早期到中期 | 缺少组织、合规和全生命周期能力 |

相较普通 RAG 或单 Agent 文档生成，本项目更慢但更可验证；相较成熟企业知识治理平台，它在代码知识行为验证上有特色，在组织治理和平台运营上仍有明显缺口。

## 与完整企业知识治理的差距

| 能力域 | 当前重点 | 完整企业能力 |
|---|---|---|
| 知识范围 | 代码和工程知识 | 文档、数据库、工单、聊天、邮件和业务系统 |
| 组织与身份 | 本地管理员和 Bearer token | SSO、OIDC/SAML、用户组、RBAC/ABAC、职责分离 |
| 数据隔离 | 本地路径和 Agent 工作区 | 租户、项目空间、地域和敏感级别隔离 |
| 来源生态 | 源码扫描候选 | Git、Wiki、Drive、Notion、Jira、Slack、数据库连接器 |
| 知识目录 | 模块、版本、状态、标签 | 统一目录、业务术语、Ontology、分类法和跨来源血缘 |
| 治理组织 | 自动 Gate 和异常事项 | Owner、Steward、Reviewer、审批链、升级与例外机制 |
| 生命周期 | 候选、验证、替代 | 创建、审核、发布、定期复核、过期、归档和删除 |
| 合规 | 审计与敏感数据边界 | 保留策略、Legal Hold、删除证明、数据驻留和合规报告 |
| 消费 | 本地查询与 API | 权限感知企业搜索、引用、订阅、推荐和多渠道分发 |
| 运营 | 本地 Console | SLA/SLO、高可用、灾备、容量、成本、告警和 SIEM |

最大的五个缺口是：企业身份与授权、多项目空间隔离、知识责任与生命周期、异构来源与统一知识体系、生产运营与合规。这些缺口不能通过增加 Agent 数量或新增几个页面解决，需要独立的领域模型和组织流程。

## 推荐产品边界

不建议立即把 domain-knowledge 扩展成大而全的企业 Wiki。更合理的定位是：

> 保持 domain-knowledge 为可信知识生产与验证引擎，逐步补齐企业身份、项目空间、知识生命周期和外部集成。

推荐顺序：

1. DEV-006 完成操作中心、治理动作、进度和实时状态。
2. DEV-007 接入 API URL/API Key、默认 Pi Agent、Provider 状态和基础性能/成本观测，形成单项目最小完整闭环。
3. DEV-008 完成知识血缘、差异、评测、来源注册和知识健康度，并增加项目空间和长期运营指标。
4. 企业化阶段再引入 SSO/RBAC、Steward/Owner、生命周期策略、连接器生态、合规和高可用。

## DEV-007 应采集的真实数据

接入真实 Pi Agent 后，应按节点、批次、Provider 和模型记录：

- 排队时间、首次开始时间、节点耗时和批次总耗时；
- Agent 调用次数、重试次数、失败类型；
- Token 用量、估算成本和成功知识版本总成本；
- P50/P95、首次修订通过率、三轮收敛率；
- 人工介入比例、平均处理时间和短期复发率。

凭据、Prompt、模型正文和未脱敏上游错误不得进入指标。DEV-008 再增加多项目维度、长期趋势、容量告警、SLO 和指标导出。
