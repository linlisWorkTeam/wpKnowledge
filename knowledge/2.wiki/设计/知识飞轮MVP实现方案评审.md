## 逐条详述

### 1. 评测对象是"知识卡质量"，不是"知识→代码还原度"

- **对应章节**：§4.1 S2、§4.2、§8
- **问题**：门禁评测的是知识卡文档质量（结构/溯源/时效/去重/可验证），不是"基于知识生成的代码是否还原源码"。知识卡质量分高，不等于知识能正确指导代码生成。这是相似度 proxy 的变体：换了一个 proxy，但仍是 proxy
- **实现现状**：80% 相似度门禁被 §4.2 明确搁置；S2 的相似度阈值用于防整段搬运（方向正确）；"知识→代码还原"强评测在 §8 迭代方向 1，未实现
- **风险**：当前门禁只能保证"知识卡写得好"，不能保证"知识有效"（能还原代码）
- **建议**：强评测环（还原相似度 + 测试通过率）应作为闭环的必选项，而非可选扩展

### 2. Reward hacking / 评测过拟合，无 holdout

- **对应章节**：§4.1 J、§4.2、§10.3
- **问题**：反复用同一套评分规则指导知识修订，可能"刷分"上涨而真实能力不涨。S1-S5 是确定性规则，刷分空间比模型评测小，但：S2 的"出现解释词加分"可被迎合；J 陪审团若与生成用同一模型，存在同模型 overfit；全流程没有不参与反馈的 hidden holdout / shadow tasks
- **实现现状**：J 陪审团默认关闭（§4.1），是缓解；重复评测 ≥3 次（§4.2）只抗方差，不抗过拟合
- **风险**：无法区分"真学习"与"刷当前评测"
- **建议**：知识卡评测分层 train/holdout，holdout 不参与反馈，定期用 holdout 评估真实能力

### 3. 同模型角色隔离 ≠ 错误独立

- **对应章节**：§3、§4.1 J
- **问题**：harvester（生成）与 jury（评分）若都用 GLM 5.1，共享底模盲点；LLM-as-Judge 的自我确认偏误无法靠角色分离消除
- **实现现状**：已基本解决。编排层是确定性管道（runner 脚本），打分/门禁/合并全是代码；LLM 只出现在 harvester 提炼和可选 jury；J 默认关闭
- **残余风险**：启用 jury 且同模型时，评审信号可能共享盲点
- **建议**：门禁判定保持纯确定性；若启用 jury，明确其定位是"解释/补充"而非"定义 truth"，或考虑外部模型交叉

### 4. 溯源锚点随代码演进失效

- **对应章节**：§4.1 S1、§6
- **问题**：sources 锚点以"文件+行号"为主（pinned 标记存在但未强制 commit/symbol 级），代码 rename/extract/move 后 traceability decay
- **实现现状**：§4.1 S1 要求 pinned 锚点（文件:行/commit/URL）；§6 模板 sources 含 path + lines + pinned
- **风险**：长期演进后溯源失效，归因定位不到
- **建议**：sources 升级为 commit SHA + symbol/function identity + AST/hash 为主锚，行号仅作展示；PoC 固定 commit 下可后置，格式上先预留字段

### 5. 固定流程缺 task-adaptive 编排

- **对应章节**：§1、§10.8
- **问题**：所有知识走同一 Acquire→Consolidate→Evaluate→Apply 链，没有按任务复杂度动态选择环节/early stopping
- **实现现状**：liveMode 有批次控制（每轮最多 4 文件，§10.8），任务形态单一（提炼知识卡），动态编排必要性低
- **风险**：扩展期（复杂跨模块任务）可能浪费成本或能力不足
- **建议**：保留 deterministic outer loop，扩展期再考虑按复杂度动态选择角色；当前不必做

### 6. Fresh context 不沉淀学习经验

- **对应章节**：§10.7、§8
- **问题**：harvester 每轮 fresh context，失败经验只落 ledger/liveMode-state（文件游标），不沉淀成可检索的失败模式/工作流；新 agent 重复踩坑
- **实现现状**：§10.7 反馈（命中/评分/勘误）只回流为 usage 评分信号；`correct` 勘误"尚未自动生成修订任务、定位来源段落或启动 Agent 重写"（原文）；"纠错→归因→修订→重测"回路是迭代项（§8 迭代方向 2）
- **风险**：飞轮"转起来了但不会改自己"，评测闭环缺了"反馈→修订"半环
- **建议**：区分"审计状态"（JSONL/ledger 全量保留）与"可学习经验"（失败模式/成功工作流提炼进知识库，参与下一轮）；优先实现 correct→归因→修订→重测

### 7. 无 ablation，无法证明设计优于简单方案

- **对应章节**：§11
- **问题**：没有对比实验证明多信号门禁/harvester/确定性管道比简单方案（直接入库、单信号、无 harvester）更优
- **实现现状**：§11 验证 = 15 项单测 + CLI/Dashboard 可运行，无对照实验
- **风险**：无法回答"这个设计值得吗"；复杂组件可能是过度设计
- **建议**：补充最小 ablation：harvester vs 无 harvester、多信号 vs 单信号、runner vs 直接入库，比较质量分/成本/人工介入
