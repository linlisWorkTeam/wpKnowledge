## 1. 背景、目标与边界

### 1.1 背景

- 单个业务代码仓约 30 万行，全部代码仓总量可达上亿行。
- 现有文档质量不一，且代码变更后往往没有同步更新，知识载体持续失真。
- 仅依赖人工维护，无法让文档稳定跟上超大规模代码库的演进。

### 1.2 目标

从源码反推出可读、可追溯、可验证的解释型知识，并用“知识能否支持生成行为正确的代码”检验和改进知识质量：

```text
源码 → 知识 → 代码 → 评测 → 归因 → 修订知识 → 再生成
```

循环的目标不是让生成代码在文本上复刻源码，而是让知识稳定保留业务逻辑、边界行为、数据结构、调用关系和设计原因。

### 1.3 三条不可动摇的基线

1. **评测对象 = 基于知识生成的代码**；不是给知识卡做脱离代码行为的文档质量打分。
2. **门禁主判 = 编译/静态检查必过 + 测试执行通过率**；文本或 AST 相似度只用于辅助归因。
3. **知识库是输入，飞轮演进知识副本**；首版知识生成由上游负责，不属于当前 runner 的 P0 范围。

### 1.4 项目约束

- 模型仅使用公司本地部署的 GLM 5.1，通过公司 codeagent CLI 访问；若 CLI 无法脚本化，再按实际能力使用其 SDK 或 HTTP API。
- 业务代码以 C/C++ 为主。
- 多 Agent 使用轻量自研编排，不引入与固定流水线、单一模型和内网环境不匹配的重型框架。
- 知识格式以 OKF 为锚点，运营流程参考 cannbot-knowledge；工程隔离、写保护和 readlist 参考[算子团队实现方案](算子团队实现方案.md)。

## 2. 术语与概念边界

| 术语 | 含义 |
|---|---|
| 知识飞轮 | 源码 → 知识 → 代码 → 评测 → 反馈 → 知识优化的循环及其编排层 |
| 知识文档 | 基于源码反推的解释型 Markdown 文档 |
| 知识生成 skill | 写明知识生成与修订步骤的操作手册；skill 自己不执行任务 |
| 知识生成 Agent | 加载 skill 后生成或修订知识的执行者，也是知识的唯一执笔者 |
| Coder Agent | 仅根据知识和需求生成临时代码，不读源码、不评测、不承担迭代 |
| Review Agent | 读取客观评测结果，定位差异、完成溯源归因并生成修订建议 |
| 评测闭环 | 自动执行编译、测试和辅助相似度分析的只读程序 |
| 门禁 | 决定知识版本能否合并或发布的可执行规则 |
| confidence | 测试通过用例数 / 总用例数；重复生成时同时报告均值与方差 |
| holdout | 不参与反馈修订、只用于检验泛化能力的冻结评测子集 |

## 3. 总体架构

### 3.1 协作模式

采用**固定流水线 + 循环迭代 + 文件交接 + 编排层状态机**。角色之间不直接共享会话：

```text
源码 ──▶ 知识生成 Agent ──▶ 知识文档 ──▶ Coder Agent ──▶ 临时代码
  ▲                                                          │
  │                                                          ▼
  └── 知识生成 Agent ◀── 修订指令 ◀── 编排层 ◀── 评测闭环 + Review
```

通信产物统一落盘：知识文档 `.md`、临时代码、评测报告 `.json`、归因报告 `.json`、修订指令 `.json`。这样可以审计、断点续跑和复现实验。

### 3.2 角色与权限

| 单元 | 职责 | 知识权限 | 源码权限 |
|---|---|---|---|
| 知识生成 Agent | 上游首版生成；按修订指令改指定段落 | 唯一执笔者 | 可读 |
| Coder Agent | 知识 + 需求 → 临时代码 | 只读 | **不可见** |
| 评测闭环 | 编译、测试、相似度与报告 | 只读 | 仅评测进程按需访问，不能泄露给 Coder |
| Review Agent | 读取评测报告，做差异定位和知识归因 | 只读 | 可读取评测所需差异信息，不把源码传给 Coder |
| 知识飞轮编排层 | 通过 / 迭代 / 回滚决策 | 有决策权，不执笔 | 不需要读取源码正文 |

硬规则：谁评测谁不改，谁生成谁可改；生成与验证必须分离；门禁不依赖任何 Agent 的自我感觉。

### 3.3 每轮状态机

1. 选择当前知识版本和评测任务。
2. Coder 只基于知识与需求生成代码。
3. 评测闭环先编译，再运行测试，并计算辅助相似度。
4. Review 根据失败用例、diff 和 sources 生成结构化归因。
5. 编排层决策：
   - 满足门禁：标记通过，候选知识可合并；
   - 未满足门禁：生成修订指令，进入下一轮；
   - 指标较基线倒退或触发安全规则：回滚；
   - 达到轮次、时间或成本上限：停止并报告未收敛。
6. 知识生成 Agent 只修订被归因命中的段落，再进入下一轮。

## 4. 知识文档规范

### 4.1 形态

知识文档使用 Markdown + YAML frontmatter，至少包含来源、状态、验证和版本信息：

```yaml
---
title: parser 边界处理
status: draft
version: 3
verified: false
source_commit: <commit>
sources:
  - file: src/parser.cpp
    symbol: parse_input
    ast_hash: <optional>
---
```

`file + symbol + commit` 是稳定锚点；行号只作展示，因为代码变更后会漂移。`ast_hash` 在 P1 再引入。

### 4.2 内容原则

知识文档应保留源码的“魂”，而不是复制源码的“壳”：

| 应保留 | 应舍弃或限制 |
|---|---|
| 关键伪代码、边界处理、数据结构、调用关系 | 命名、格式和无业务意义的样板代码 |
| 为什么这样设计、解决什么问题、历史兼容原因 | 无解释的整段源码搬运 |
| 适用场景、约束、失败模式和权衡 | 脱离上下文的孤立结论 |
| 对应源码的稳定溯源锚点 | 只靠易漂移行号的来源标注 |

核心模块按可执行规格标准编写，边缘模块可以降低规格严格度；避免一刀切导致成本失控。

### 4.3 生成顺序与粒度

- 生成顺序按依赖拓扑：先依赖项，后被依赖项；对比实验必须固定顺序。
- 知识按函数或模块级单元生成、评测和合并，不做整库或整篇无差别重写。
- 某段知识反复触发失败时进入“薄弱点地图”，优先重写并记录失败机制。

## 5. 溯源、反馈与修订

### 5.1 反向归因

```text
失败用例 / 生成代码差异
  → 定位源码 symbol
  → 通过 sources 反查知识段落
  → 生成针对该段的修订指令
```

### 5.2 反馈格式

反馈由两层组成：

| 层 | 内容 | 示例 |
|---|---|---|
| 结构化信号 | 失败用例、编译错误、symbol、diff、测试通过率、辅助相似度 | `parse_input(empty)` 期望 `null`，实际抛异常 |
| 自然语言解读 | 差异原因、命中的知识段落、建议补充内容 | “§3.2 未说明空输入兼容行为” |

修订指令采用 readlist 三字段：`ID + 知识段落路径 + 可执行验证判据`。纯自然语言建议不能直接驱动合并。

### 5.3 防污染

- 未通过门禁的知识版本不得合并。
- 修订后主指标低于基线时自动回滚。
- 保留每轮知识副本、评测报告和归因报告，保证可恢复、可追责。
- 来源不可信或反馈输入异常时进入人工检查，不自动写入知识。

## 6. 门禁与评测摘要

完整规则见[门禁与评测机制](门禁与评测机制.md)，评测集制作见[评测集构建指南](评测集构建指南.md)。

### 6.1 信号优先级

1. **编译 / 静态检查**：必过前置门槛。
2. **测试执行通过率**：唯一主判信号，`confidence = passed / total`。
3. **文本、AST 或数据流相似度**：只进归因报告，不参与通过/失败判定。
4. **LLM Review**：解释失败和定位知识缺口，不替代客观判定。

“相似度 ≥ 80%”是早期方案，已废弃为主门禁；`0.8` 只能作为待校准的测试通过率候选值，不能在没有实测评测集强度时写死。

### 6.2 可靠性

- 同一配置重复生成与评测建议至少 5 次，报告 confidence 均值、方差和最差值；方差过大视为不稳定。
- train 用例可以产生反馈；holdout 冻结且不得进入修订上下文。
- 期望输出必须由探针运行真实源码获得，无法运行时须明确记录人工推导依据。
- 用覆盖率定位“哪里没测”，用变异测试检验“测错能否抓住”；两者用于评测集质量，不直接替代门禁主判。
- 私有代码优先；公开代码需做语义保持变换，降低训练数据记忆和抄源码风险。

## 7. 工程落地方案（P0）

### 7.1 目录隔离

```text
/workspace/
├── flywheel/              # codeagent workdir 仅指向这里
│   ├── knowledge/         # 知识版本
│   ├── interfaces/        # 必需的接口头文件副本
│   ├── evalset/           # 测试及已固化期望，不含源码实现
│   ├── artifacts/         # 临时代码、报告、轨迹
│   └── fw/ eval/ roles/   # 编排、评测与角色适配器
└── src-biz/               # 业务源码，位于飞轮目录之外并只读
```

隔离红线：

- Coder 的工作目录、prompt、环境变量和会话轨迹中不得出现源码路径。
- `evalset/` 不存放源码实现；如离线评测需要 golden 源码，只能放在 Coder 不可访问的受保护区。
- 评测编译只引用 `interfaces/`、`evalset/` 和生成代码，不让 Coder 通过构建错误反推出源码正文。
- 对受保护路径建立 SHA-256 快照，角色越权修改即失败。

### 7.2 模块划分

| 模块 | 输入 → 输出 | P0 职责 |
|---|---|---|
| `runner` | 报告 + 归因 → 决策 | 确定性状态机，通过 / 迭代 / 回滚 |
| `roles` | 角色输入 → 文件产物 | 独立上下文调用 GLM 5.1 |
| `eval` | 代码 + 评测集 → 评测报告 | 编译、测试、辅助相似度 |
| `revise` | 归因 → 新知识候选 | pending corrections、sources 反查、重测 |
| `storage` | 知识及版本元数据 | 版本、索引、历史、回滚 |

### 7.3 评测执行

- C/C++ 使用项目既有构建系统；无既有约定时使用 gcc/g++/clang，并启用 `-Wall -Werror`。
- 编译失败立即结束本轮，不进入测试。
- 测试报告至少包含总数、通过数、失败详情、confidence、重复次数、均值和方差。
- 相似度字段只能位于诊断/归因区，状态机不得读取它决定通过。

### 7.4 holdout

- 初始候选：按模块稳定哈希划分 20% holdout；比例应可配置。
- holdout 用例不进入 Review 修订输入，不得通过日志或失败详情泄露给生成角色。
- 收敛曲线和最终验收同时报告 train 与 holdout，最终能力以 holdout 为准。

### 7.5 修订闭环

1. Review 归因写入 `pending_corrections`。
2. 编排层把归因转换为 readlist 修订指令。
3. 知识生成 Agent 按 sources 定位并修订指定段落。
4. 新版本重新运行完整门禁。
5. 通过后升级版本；未通过不合并；倒退则回滚。

## 8. P0 验收清单

- [ ] 一次完整运行可完成：知识 → 代码 → 编译 → 测试 → 归因 → 修订 → 重测。
- [ ] 编译失败会被拦截，不进入测试。
- [ ] confidence 严格等于通过用例数 / 总用例数。
- [ ] 重复评测报告均值和方差，不以单次最好成绩通过。
- [ ] 相似度只进入归因报告，不参与门禁判定。
- [ ] Coder 无法读取源码、golden 实现或 holdout 详情。
- [ ] holdout 不进入反馈回路，只报告结果。
- [ ] 门禁通过才合并；指标下降自动回滚。
- [ ] 知识、临时代码、评测、归因、修订和轨迹产物全部落盘且可审计。
- [ ] 受保护路径的 SHA-256 校验能发现越权修改。

## 9. 落地路线

| 阶段 | 范围 |
|---|---|
| P0 | 评测闭环、目录与上下文隔离、holdout、修订闭环、版本回滚、端到端审计 |
| P1 | 评测集增强、覆盖率与变异测试、commit/symbol/ast_hash 溯源、AST 相似度、多候选 |
| P2 | 消融实验、鲁棒性变换、评测集轮换、效率评测、规模化切分和收敛曲线 |

P0 不做：把文档质量多信号打分当成飞轮主门禁、依赖 harvester 入库替代代码还原评测、未经验证的自动全库改写。

## 10. 已废弃方案与保留原因

| 旧说法 / 实现 | 当前结论 | 保留记录的原因 |
|---|---|---|
| endlessWpKnowledgeRunner 的知识卡“70 分文档质量门禁” | 方向错误，不作为飞轮门禁 | 防止后续实现再次偏离评测对象 |
| 生成代码与源码“相似度 ≥ 80%”即通过 | 相似度降为辅助，测试通过率主判 | 功能等价代码可能写法不同 |
| Coder 自评或 LLM 裁判直接判对错 | 禁止；只能做归因解释 | 存在确认偏误、位置偏差和不稳定性 |
| 评测集内直接放 golden 源码供全流程读取 | 生产环境禁止；必须与 Coder 隔离 | 防止源码泄露和抄写式高分 |
