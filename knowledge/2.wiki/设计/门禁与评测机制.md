# 门禁与评测机制

> 最后收敛：2026-08-26
>
> 定位：定义知识飞轮的裁判规则、可靠性约束和通过/迭代/回滚条件。工程流程见[知识飞轮实现方案](知识飞轮实现方案.md)，评测集制作见[评测集构建指南](评测集构建指南.md)，指标依据见[评测的选型调研报告](评测的选型调研报告.md)。

## 1. 目的与评测对象

门禁保证只有经过客观验证的知识版本才能合并或发布。

- **被验证对象**：知识文档支持生成行为正确代码的能力。
- **实际受测产物**：Coder 仅基于知识和需求生成的临时代码。
- **对照信号**：真实源码行为固化出的测试期望，以及只用于诊断的源码结构差异。
- **不属于主门禁**：文档篇幅、格式完整度、LLM 主观评分或单纯文本相似度。

## 2. 已确定的门禁规则

### 2.1 信号优先级

| 顺序 | 信号 | 用途 | 是否决定通过 |
|---|---|---|---|
| 1 | 编译 / 静态检查 | 确认代码可构建、接口正确 | 是，必过 |
| 2 | 测试执行通过率 | 验证外部可观察行为 | 是，主判 |
| 3 | 文本 / AST / 数据流相似度 | 定位实现差异和知识缺口 | 否，仅辅助 |
| 4 | Review Agent 解读 | 把失败映射到知识段落 | 否，仅归因 |

### 2.2 单次运行

```text
编译失败                      → FAIL_COMPILE → 迭代
编译通过且 confidence ≥ 门限  → PASS 候选
编译通过且 confidence < 门限  → FAIL_TEST → 迭代
主指标低于上一已接受版本       → REGRESSION → 回滚
```

```text
confidence = passed_cases / total_cases
```

门限必须可配置。`0.8` 是历史候选值，不是未经实验即可写死的默认标准；最终阈值应根据评测集强度和 holdout 分布校准。

### 2.3 重复生成的最终判定

LLM 生成具有随机性，同一知识版本在相同配置下建议重复至少 5 次。报告至少包含：

- 每次 confidence；
- 均值、方差、最差值；
- 编译成功率；
- 每条失败用例的出现次数。

最终通过规则须在 PoC 后确定。目前禁止“取多次最好成绩即通过”；方差过大应标记 `UNSTABLE` 并进入迭代或人工检查。

## 3. 评测闭环

### 3.1 输入与输出

| 类型 | 内容 |
|---|---|
| 输入 | 需求描述、当前知识版本、接口定义、train 或 holdout 评测子集 |
| Coder 输出 | 临时代码 |
| 自动评测输出 | 编译结果、测试统计、失败详情、辅助相似度、运行环境 |
| Review 输出 | 结构化归因 + 自然语言解释 + 命中的知识段落 |
| 编排输出 | 通过、迭代、回滚或停止 |

### 3.2 标准顺序

1. Coder 在看不到源码和评测期望的环境中生成临时代码。
2. 评测进程执行编译和静态检查；失败则结束本轮。
3. 编译通过后运行行为测试，计算 confidence。
4. 自动计算相似度，但状态机不得用它决定通过。
5. Review 只读取必要的失败和差异信息，完成 sources 反向归因。
6. 编排层按确定性规则决策。

### 3.3 评测报告最小结构

```json
{
  "run_id": "...",
  "knowledge_version": "...",
  "evalset_version": "...",
  "source_commit": "...",
  "environment": {"compiler": "...", "flags": ["-Wall", "-Werror"]},
  "compile": {"passed": true, "errors": []},
  "tests": {
    "passed": 18,
    "total": 20,
    "confidence": 0.9,
    "failures": []
  },
  "diagnostics": {"text_similarity": 0.72, "ast_similarity": null},
  "repetitions": {"count": 5, "mean": 0.88, "variance": 0.0024, "min": 0.85},
  "decision": "pass | iterate | rollback | unstable"
}
```

## 4. 职责与信息边界

| 参与者 | 允许做 | 禁止做 |
|---|---|---|
| Coder Agent | 根据知识和需求生成代码 | 读源码、评测期望、holdout 详情；自评；修改知识 |
| 自动评测 | 编译、测试、计算客观指标 | 修改知识或生成代码 |
| Review Agent | 解释失败、差异定位、知识归因 | 直接判定通过；直接修改知识 |
| 编排层 | 根据报告做状态决策 | 执笔修改知识；用相似度或 LLM 感觉绕过测试 |
| 知识生成 Agent | 按修订指令修改指定知识段落 | 看到 holdout 失败详情；修改门禁报告 |

原则：**谁评测谁不改，谁生成谁可改；知识飞轮只决策，知识生成 Agent 才执笔。**

## 5. 可靠性与防作弊

### 5.1 评测集独立

- 评测集与知识库分离存放。
- train 失败可以产生修订反馈；holdout 失败只用于报告，不能进入生成上下文。
- 评测集来源 commit、版本、构建方法和环境必须可追溯。

### 5.2 防源码泄露

- 优先评测私有代码；公开代码需要语义保持变换，降低预训练记忆影响。
- Coder 工作目录与业务源码物理隔离。
- 评测集不得向 Coder 暴露 golden 源码实现。
- Coder 轨迹中出现源码路径读取，或生成结果与源码异常高度一致时，触发作弊审计；高度一致本身不是定罪证据。

### 5.3 评测集质量

- 期望输出优先通过探针运行真实源码获得，禁止 LLM 编造。
- 覆盖率用于定位未覆盖路径；变异测试用于验证测试能否抓住错误。
- 覆盖率高不等于测试强，二者必须结合看。
- 边界、空输入、错误和极值用例不可只靠正常路径替代。

### 5.4 稳定性与环境

- 固定模型、参数、prompt 版本、任务顺序、编译器和运行环境。
- 报告均值与方差，不以单次结果宣布改进。
- 性能门禁必须先测环境噪声，再按真实源码基线设置裕量。

### 5.5 防知识污染

- 未过门禁不合并。
- 低于已接受基线自动回滚。
- 保留知识版本、评测报告、归因和修订轨迹。
- 反馈来源不可信时进入人工检查。

## 6. train、holdout 与发布

```text
train 评测失败
  → 可输出具体失败与归因
  → 修订知识
  → train 重测

holdout 评测
  → 只输出聚合结果给编排层
  → 不把用例、期望或详细失败反馈给生成角色
  → 用于最终验收和收敛曲线
```

候选知识必须先通过 train 门禁，再接受 holdout 验证。发布条件、holdout 阈值和不稳定性阈值需在首个 PoC 后固化。

## 7. 已收敛、待确认与历史方案

### 7.1 已收敛

- 评测对象是基于知识生成的代码。
- 编译必过，测试执行通过率主判，相似度辅助归因。
- confidence = 通过用例数 / 总用例数。
- 评测和 Review 全程只读；修订由知识生成 Agent 执行。
- 未过门禁不合并，倒退自动回滚。
- 期望输出来自真实源码行为。

### 7.2 待确认 / 待实验

1. 门禁阈值及是否按用例重要性加权。
2. 重复评测的通过规则、方差上限和最差值要求。
3. 模块、函数和场景三种粒度如何组合统计。
4. holdout 比例与轮换周期。
5. 覆盖率和 mutation score 的合格线。
6. 性能、内存等非功能指标何时进入门禁。
7. “AI 推荐路径”的业务定义和责任人。

### 7.3 历史方案

- “源码还原相似度 ≥ 80%”曾是主门禁设想，现已降级为诊断信号。
- TDD 曾列为探讨方案，现已正式采纳其核心：执行测试是主信号。
- 知识卡文档质量多信号打分曾被实现为 MVP，但评测对象错误，已废弃。
