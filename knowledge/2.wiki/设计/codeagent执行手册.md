# codeagent 执行手册（构建知识飞轮 runner）

> 定位：给 codeagent 的直接执行指令。按本文档在本地构建/改造 runner，每步做完按验收标准自检。
> 阅读顺序：先读本文档，再读 [知识飞轮实现方案.md](知识飞轮实现方案.md)（设计基线）、[评测集构建指南.md](评测集构建指南.md)（评测集 schema）、[门禁与评测机制.md](门禁与评测机制.md)（评测方法背景）。
> 使用方式：把本文档 + 上述配套文档交给 codeagent，按步骤执行。所有步骤完成后运行 §7 端到端验收，全部通过才算完成。

## 0. 输入物与前置条件

开始前确认以下输入就位：

| 输入 | 说明 | 来源 |
|------|------|------|
| 源码仓库 | 被测模块源码（**C/C++**，本地） | 用户提供 |
| 评测集 | 按《评测集构建指南》schema 构建（本地） | 用户提供 |
| 知识文档 | 首版知识（OKF 格式，Markdown + frontmatter） | 上游 / 知识生成 Agent |
| endlessWpKnowledgeRunner | 现有 runner 代码（作为改造基础） | 仓库 |

**硬性约束（违反即失败）：**
- 只实现 P0（评测闭环 + holdout + 修订闭环），P1/P2 不做
- 评测对象 = 基于知识生成的代码 vs 源码（代码还原）。任何把评测对象换成"知识卡文档质量打分"的实现都算失败
- 不修改 2.wiki 设计文档
- 角色调用统一走 codeagent CLI 访问 GLM 5.1；若 CLI 不支持脚本化（非交互/--json），改用其 Python SDK 或 HTTP API（以实际能力为准）

## 1. 改造范围（保留 / 替换 / 新增）

| 处理 | 内容 |
|------|------|
| **保留** | OKF 知识卡存储（concepts/drafts/history）、版本保护、索引/日志、BM25 检索、使用反馈回流 |
| **替换** | 多信号文档质量门禁（70 分）→ 代码还原评测闭环（编译必过 + 测试主判 + 相似度辅助） |
| **新增** | holdout 分层（holdout_ratio=0.2）、修订闭环（pending_corrections 队列 + `fw revise` 流程） |

## 2. 功能模块清单

以现有 endlessWpKnowledgeRunner 结构为准，就地改造；如无对应模块则新建。功能划分如下：

| 模块 | 职责 | 输入 → 输出 |
|------|------|------------|
| 编排层（runner） | 确定性状态机：读置信度+归因 → 决策（通过/迭代/回滚），只决策不执笔 | 评测报告+归因报告 → 决策指令 |
| 角色执行（roles） | 知识生成 Agent / Coder / Review 三个角色，各自独立上下文，调用 GLM 5.1 | 知识文档/临时代码/差异 → 产物 |
| 评测闭环（eval） | 编译检查 + 测试执行 + 相似度 → 置信度；只读，不改知识 | 临时代码+评测集 → 评测报告 json |
| 修订闭环（revise） | pending_corrections 队列 + 修订流程：读反馈 → sources 反查 → 修订 → 重测 | 归因报告 → 修订后知识（版本升级） |
| 存储（storage） | 知识卡存储、版本控制、索引（保留现有） | — |

## 3. 评测闭环实现（P0 核心）

### 3.1 编译 / 静态检查（必过门槛）

- **步骤**：对 Coder 生成的临时代码执行编译与静态检查（**C/C++ 用 gcc/g++/clang，开启 -Wall -Werror 严格告警**）
- **输出**：pass/fail + 错误列表
- **验收**：编译失败 → 本轮直接判失败（不进测试阶段），进入修订闭环

### 3.2 测试执行（主信号）

- **步骤**：运行评测集 cases（行为测试用例，schema 见《评测集构建指南》§2.1），记录通过/失败
- **输出**：通过用例数 / 总用例数
- **验收**：置信度 = 通过用例数 / 总用例数；同配置重复评测 ≥ 5 次，报告均值 ± 方差（[门禁与评测机制.md](门禁与评测机制.md) §3.5）

### 3.3 相似度（辅助归因）

- **步骤**：临时代码 vs golden 源码做文本级/AST 级相似度
- **输出**：相似度分数
- **验收**：相似度**不参与门禁通过/失败判定**，仅作为 Review 归因的辅助诊断（功能等价但写法不同不得误杀）

### 3.4 置信度与门禁判定

- **公式**：confidence = passed / total（测试主判）
- **门限**：可配置，默认值由用户指定
- **判定**：confidence ≥ 门限 → 通过；< 门限 → 迭代；较上一轮下降 → 回滚（防污染）

## 4. holdout 分层实现

- **步骤**：评测集按模块名哈希划分 train / holdout（holdout_ratio = 0.2）；train 参与反馈迭代，holdout 冻结不参与
- **输出**：`fw_eval --holdout` 只报告 holdout 结果，不写回知识库
- **验收**：holdout 模块的用例不出现在修订闭环的反馈里；收敛曲线必须用 holdout 结果画（防刷分）

## 5. 修订闭环实现

- **步骤**：
  1. Review 归因报告（结构化 + 自然语言）入 `pending_corrections` 队列
  2. `fw revise` 流程：读反馈 → 按 sources 反查知识段落 → 修订 → 走评测（§3）→ 通过则版本升级，未过则不合并
  3. 修订指令结构化：ID + 知识段落路径 + 验证判据（readlist 三字段）
- **验收**：修订后重测；门禁通过才合并回知识库；分数下降自动回滚（[知识飞轮实现方案.md](知识飞轮实现方案.md) §5）

## 6. 角色执行约定

| 角色 | 动作 | 产物 | 修改权限 |
|------|------|------|---------|
| 知识生成 Agent | 源码 → 知识文档（伪代码+为什么+溯源）；按反馈修订指定段落 | 知识文档 | ✅ 唯一执笔者 |
| Coder Agent | 仅基于知识写代码，不迭代、不验证、不读源码 | 临时代码 | ❌ |
| Review Agent | diff 定位 + 溯源归因 + 生成反馈 | 归因报告（json） | ❌ 只读 |

- 每个角色调用时**独立构造上下文**，历史会话只属于编排层，角色间不传递（信息隔离）
- 通信 = 文件产物（知识 md / 临时代码 / 评测报告 json / 归因报告 json），物理交接、可审计、可断点续跑

## 7. 端到端验收清单

完成以下验证，全部通过才算实现完成：

- [ ] 一次完整飞轮运行：知识 → 代码 → 评测 → 归因 → 修订 → 重测，全流程可跑通
- [ ] 编译失败被正确拦截，不进入测试阶段
- [ ] 置信度 = 通过用例数 / 总用例数，重复 ≥ 5 次报告均值 ± 方差
- [ ] 相似度只出现在归因报告，不参与门禁判定
- [ ] holdout 模块用例不进入反馈回路，`fw_eval --holdout` 只报告不写回
- [ ] 修订后门禁通过才合并，分数下降自动回滚
- [ ] 所有报告落盘（json），路径可审计

## 8. 不做清单（超出 P0 即停止）

- P1：溯源锚点升级（commit/symbol/ast_hash）、评测集构建（评测集由用户本地提供，不在此实现范围）
- P2：ablation 对比实验、收敛曲线报告
- 已废弃 MVP 机制：多信号文档质量门禁（70 分）、harvester 提炼入库作为飞轮主体、四环节知识运营形态

> 判定标准：任何实现若评测对象不是"基于知识生成的代码 vs 源码"，即偏离基线，立即停止并报告。
