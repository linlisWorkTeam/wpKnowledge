# 项目概述（Overview）

> 最后更新：2026-08-20

## 1. 背景与痛点

我们正在建设一个**知识工程项目**，核心背景是：

- **代码库规模巨大**：单个代码仓约 30 万行代码，所有代码仓合计代码量可达 **上亿行**。
- **文档质量参差不齐**：现有文档质量差异大，缺乏统一标准。
- **文档滞后于代码**：代码发生变更后，开发人员大概率不会同步更新对应文档，导致文档与最新代码版本不一致。

**结论**：依赖人工维护的文档无法跟上超大规模代码库的演进速度，文档作为"知识载体"的可信度持续下降。

## 2. 项目目标

从代码仓的**源码反推出文档和知识**，并基于这些知识构建 **知识飞轮（Knowledge Flywheel）**，实现：

- 让知识文档与源码保持同步（知识从源码自动生成，随源码演进）。
- 让知识不仅"可读"，而且"可验证"——通过知识能否还原出接近源码的代码来检验知识质量。

## 3. 知识飞轮（总览）

```
┌──────────┐    ┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│ 源码仓库  │ →  │ Skill 生成知识 │ →  │ Coder 写代码  │ →  │ Review 对比差异 │
└──────────┘    └──────────────┘    └──────────────┘    └──────────────┘
      ↑                                                         │
      └──── 反馈：归因结果驱动知识修改 ←──────────────────────────┘
```

1. **知识生成**：Skill 基于源码生成知识文档（Markdown，每段带溯源链接）。
2. **代码生成**：Coder Agent 仅基于该知识编写代码。
3. **差异对比**：Review Agent（独立于 Coder）将生成的代码与原始源码反复对比，通过溯源链接归因到具体文档段落。
4. **反馈优化**：Review 生成结构化反馈 + 归因结果，Skill 据此修改对应段落。

循环往复，使**基于知识生成出来的代码越来越趋近于原始源码**。角色分工与归因机制详见 [知识飞轮流程设计.md](知识飞轮流程设计.md) §3-§6。

## 4. 门禁机制（总览）

设置类似门禁/评测阈值的机制：

- 当 Agent 根据某份知识生成的代码，与原始源码相比达到 **80% 的正确率 / 相似度**（阈值可配置），即认为该知识**通过门禁**，视为合格知识。

> 详见 [门禁与评测机制.md](门禁与评测机制.md)。

## 5. 约束与前提

- **模型**：仅能使用公司**本地部署的 GLM 5.1**，飞轮各环节（知识生成、代码生成、差异分析）均运行在该模型之上。
- **代码访问**：基于公司代码仓源码进行知识反推。

## 6. 设计核心参考（锚点仓库）

本项目的知识格式与运营流程设计，**以以下两个仓库为锚点**，后续设计决策与它们对齐：

| 仓库 | 地址 | 在本项目中的锚点角色 |
|------|------|---------------------|
| **knowledge-catalog / OKF** | https://github.com/GoogleCloudPlatform/knowledge-catalog（⭐8756，活跃维护） | **格式锚点**：知识格式 = Markdown + YAML frontmatter（sources/status/verified），知识库天生可信、可 diff、可评审 |
| **cannbot-knowledge** | https://gitcode.com/cann/cannbot-skills/tree/master/plugins-community/cannbot-knowledge | **流程锚点**：知识「生产 → 治理 → 消费 → 反馈」全生命周期运营（ingest 生产 / lint 门禁 / query 检索 / issue-report 反馈），且 frontmatter 采用 okf.v1 |

> 两仓库是同一体系：**OKF 定格式，cannbot 定运营流程**。飞轮各环节设计（`设计/知识飞轮流程设计.md`、`设计/门禁与评测机制.md`）均以这两者为参考基线。
> 注：cannbot 在 gitcode 平台（star 少），但为昇腾官方活跃维护项目，与本项目（华为知识工程）场景直接相关，属设计核心参考而非公开来源参考。
