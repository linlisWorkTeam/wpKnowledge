# 评测集构建指南（源码 + 专家文档 → 评测集）

> 来源：2026-08-24 项目探讨。
> 定位：回答"怎么把 源码 + 专家治理文档（未 OKF 格式化）变成知识飞轮的评测集"。评测集支撑两件事：门禁强评测环 S6（知识→代码还原度）与知识卡质量验证。
> 配套：[知识飞轮实现方案.md](知识飞轮实现方案.md) §4（评测方法：编译必过 + 测试主判 + 相似度辅助）。

## 1. 评测集要回答什么问题

评测集是用来验证两件事的客观信号集合：

1. **知识有效性**：一张知识卡（无论由谁生成）能否支撑"基于它还原出正确的代码"。对应强评测环 S6
2. **知识忠实度**：知识卡是否准确吸收了专家治理文档的知识点，没有丢失、歪曲、编造

你有源码 + 专家文档，恰好为这两个问题都提供了"标准答案"：

| 评测对象 | 标准答案来源 |
|---------|-------------|
| 行为正确性 | 源码实际行为（跑源码拿输出，golden） |
| 知识忠实度 | 专家治理文档（知识点参考答案） |

## 2. 评测集结构（evalset schema）

```text
evalset/
├── manifest.json              # 评测集清单：版本、来源 commit、统计
├── cases/                     # 行为测试用例（输入/期望输出）
│   └── <module>.cases.json
├── golden/                    # golden 参考（源码函数摘录 + 签名）
│   └── <module>.py
├── knowledge/                 # 知识评测（专家知识点 → 期望知识卡内容）
│   └── <module>.knowledge.json
└── README.md                  # 构建说明、维护记录
```

### 2.1 cases：行为测试用例

```json
{
  "id": "parser-parse_input-001",
  "module": "parser",
  "function": "parse_input",
  "source_ref": {"file": "src/parser.py", "symbol": "parse_input", "lines": "120-135", "commit": "必填"},
  "edge_type": "normal | boundary | empty | error | extreme",
  "input": {"text": ""},
  "expected_output": null,
  "golden_note": "空输入返回 null，来自源码 120 行实际行为"
}
```

- **期望输出必须来自源码实际行为**（运行源码确认或从源码逻辑严格推导），禁止 LLM 猜测
- `edge_type` 五类都要覆盖，边界/空/异常/极值合计建议 ≥ 30%

### 2.2 golden：参考实现

每个核心函数一份：源码函数摘录 + 签名 + 说明。用途：知识卡 → 生成代码 → 与 golden 做差分/测试对比。

### 2.3 knowledge：知识忠实度评测

```json
{
  "id": "parser-kp-001",
  "module": "parser",
  "topic": "空输入边界处理",
  "expert_doc_ref": {"file": "docs/parser.md", "section": "边界处理"},
  "source_ref": {"file": "src/parser.py", "symbol": "parse_input", "lines": "120-135"},
  "key_points": [
    "空输入返回默认值 null",
    "兼容空输入是历史需求（不抛异常）"
  ],
  "validation": "生成的知识卡应包含：伪代码（if input empty: return null）+ 为什么（历史需求兼容）"
}
```

## 3. 构建步骤（六步）

### 3.1 盘点

- 源码：列出模块、核心函数清单（文件、符号、行号、输入输出签名）。核心函数 = 有业务逻辑、有边界行为、被文档提到的
- 专家文档：列出文档清单与章节结构

### 3.2 映射

专家文档章节 ↔ 源码模块/函数对应表。这是评测集的骨架，映射错了后面全偏。

### 3.3 提取知识点

对每个映射到的模块，从专家文档提取 3-10 个知识点（主题、关键逻辑、为什么、对应源码位置）。专家文档未 OKF 化没关系，评测集把它的知识点显式化即可。

### 3.4 生成行为用例

对每个核心函数生成测试用例：

- **正常路径**：典型输入 → 期望输出
- **边界**：空输入、单元素、最大长度
- **异常**：非法输入、类型错误
- **极值**：大数值、深嵌套、超长字符串
- 期望输出优先**运行源码确认**（写一次性脚本跑源码拿输出），无法运行则从源码逻辑严格推导并标记 `golden_note`

### 3.5 格式化

按 schema 写入 manifest.json + cases/ + golden/ + knowledge/。manifest 记录来源 commit 与文档版本（溯源要求）。

### 3.6 验证评测集本身

评测集也要防"太弱导致假达标"：

- **变异测试**：对 golden 源码注入 bug，看评测集能否抓出（抓不出 = 用例太少/太弱）
- **可执行性抽查**：每条用例能跑、期望输出与源码一致
- **人工抽查**：知识点提取是否有歪曲

## 4. 维护与版本

- manifest.json 记录 source_commit，源码变更后评测集必须重跑 3.4（行为可能变）
- 专家文档更新 → 知识 points 增量更新，不整包重生成
- 评测集与知识库分离存放（如 `evalset/` 独立目录），不混入 knowledge/2.wiki

## 5. 与飞轮的对接

- 门禁强评测环 S6：知识卡 → 生成代码 → 跑 cases（测试通过率）→ 与 golden 差分 → 还原度分
- 知识忠实度：知识卡 ↔ knowledge/ 知识点对照（内容是否覆盖 key_points）
- holdout（[知识飞轮实现方案.md](知识飞轮实现方案.md) §4）：按模块划分 train/holdout，holdout 模块的用例不参与反馈

## 附录 A：AI 生成评测集 Prompt（可直接复制给 AI）

```text
你是评测集生成专家。请基于给定的源码仓库和专家治理文档，生成知识飞轮评测集。

## 输入
- 源码仓库路径: {源码路径}
- 专家文档路径: {文档路径}
- 输出目录: {输出路径}/evalset/

## 任务
生成以下文件（严格按 schema）：
- evalset/manifest.json        # 版本、来源 commit、统计
- evalset/cases/<module>.cases.json   # 行为测试用例
- evalset/golden/<module>.py   # golden 参考（源码函数摘录）
- evalset/knowledge/<module>.knowledge.json  # 知识忠实度评测
- evalset/README.md            # 构建说明 + 待人工确认项

## 执行步骤
1. 盘点：列出仓库模块与核心函数（文件/符号/行号/输入输出签名）；列出专家文档章节结构
2. 映射：建立 专家文档章节 ↔ 源码模块/函数 对应表，写入 manifest.json
3. 提取知识点：每个模块提取 3-10 个知识点（topic / key_points / expert_doc_ref / source_ref / validation）
4. 生成行为用例：对每个核心函数生成测试用例，覆盖 normal/boundary/empty/error/extreme 五类，
   边界+空+异常+极值合计不少于 30%
5. 生成 golden：摘录每个核心函数的源码实现（含签名），标注文件与行号

## 硬性要求
1. expected_output 必须真实：优先运行源码确认，无法运行则从源码逻辑严格推导，并在 golden_note 说明推导依据；禁止编造
2. 每个知识点必须有 expert_doc_ref（文档章节）和 source_ref（文件/符号/行号/commit）
3. 专家文档未按 OKF 格式化没关系，直接按其章节结构提取知识点，不要求先转换
4. 每条用例的 source_ref.commit 记录源码 commit
5. 输出 JSON 严格符合 schema，字段名与上表一致

## 完成后输出
1. 各文件路径
2. 统计摘要：模块数 / 函数数 / 用例数 / 知识点数 / 五类用例分布
3. 待人工确认清单：无法运行源码的用例、映射不确定的文档章节、可能遗漏的核心函数
```

## 附录 B：用法提示

- 把附录 A 的 prompt 发给 AI 时，替换 `{源码路径}`、`{文档路径}`、`{输出路径}`
- 首次建议限定范围：先挑 1-2 个核心模块跑通，确认 schema 与质量后再全量
- 生成的评测集务必执行 3.6 验证（变异测试 + 抽查），不要直接信任 AI 输出
