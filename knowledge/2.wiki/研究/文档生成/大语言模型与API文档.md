## 它解决了什么问题

人都知道：写代码遇到不熟的 API，查文档很有用。RAG 也假设：给 LLM 注入文档（API 文档、库文档）应该能提升代码生成。但论文发现这个假设**没那么成立**：

- 文档确实帮开发者（对照组验证）
- 但检索注入文档对 LLM 代码生成的提升**有限、不稳定**
- 原因：LLM 读文档的方式和人类不同，文档里的冗余信息会干扰；检索到的片段未必是生成该代码最需要的

## 实验结果

- 文档对人类开发者价值明确
- 对 LLM：**简单检索注入效果有限**，甚至有时负收益
- 文档的质量、相关度、注入方式（不是简单的"塞进上下文"）决定效果
- 结论：文档要"对 LLM 友好"地组织，不能直接照搬给人看的文档

## 局限与注意

- 研究聚焦 API 文档场景，其他文档类型结论可能不同
- RAG 检索质量影响实验，检索器换了好结果可能变

## 对我们项目的启发 ⭐

这篇对我们**很有警示价值**，直接影响知识消费端（第二步）的设计。

### 直接相关

**① 知识文档 ≠ 给人看的文档**：我们生成的知识是给 GLM 5.1 消费的，不是给人看的。论文证明"给人看的文档直接喂给 LLM 效果差"。我们的知识格式必须**为 LLM 优化**：结构化、去冗余、信息密度高、示例精准——这正是"解释型知识"和"普通文档"的区别，也解释了为什么不能简单搬运源码。

**② 检索注入方式要设计**：不能把知识"塞进上下文"就完事。要研究：注入哪些片段、什么顺序、要不要过滤。我们飞轮第二步（基于知识生成代码）的 prompt 设计需要实验，不是想当然。

### 需要改造的

**① 它测"外部文档"，我们测"内部知识"**：论文的文档是 API 参考（LLM 训练时可能见过）。我们的知识是从**私有源码**生成的，LLM 没见过——这正是我们知识价值的来源，也意味着我们的注入效果可能比它的场景更好（无预训练污染）。但格式仍需优化。

**② 验证方法可借用**：它的对照实验设计（有/无文档 × 人类/LLM）可以复制到我们的门禁评测：对比"有知识 vs 无知识"的代码生成差异，证明知识真的有用。

### 需要注意的

- 这是反直觉的发现：直觉上"知识越多越好"，但实验说"不一定"。飞轮 PoC 阶段建议先做这个小实验：同一模块，给/不给知识文档，看生成质量差多少——如果没差，说明知识格式有问题，先修格式再跑飞轮。
