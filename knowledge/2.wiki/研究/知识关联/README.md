# 知识关联：三层知识源与两条主线的方案调研

外部知识关联这一段的调研材料。对应 `association` 模块与 `Association.md` 的 IO-23。

本目录原有材料是按「功能延期」状态准备的。用户在本轮明确了完整方案（三层知识源加两条主线）与五个关键挑战，要求收敛成可用于项目的方案，因此本次按方案的五个挑战重新组织。

## 先看结论

### 五个挑战里，哪些有现成答案，哪些没有

| 挑战 | 现成答案 | 最可直接用的材料 | 缺口 |
|---|---|---|---|
| 一 知识编译（卡片化） | 部分 | WikiSkill、DIAL-KG 三阶段闭环 | 按业务定制卡片类型没有对口方案 |
| 二 模态转换 | **有，且很硬** | Docling 加层级切分（94.1%） | 非拉丁语系需自测；本项目的口径更严 |
| 三 经验污染治理 | 部分 | CLD-KB、DIAL-KG 的软废弃与废弃日志 | 置信度分级与代码卡片同级发布没有对照 |
| 四 关联与防孤岛 | **有，且成体系** | ArDoCo 工具族、LLM 文档到代码追溯评测 | 都没有以「代码符号」作锚点 |
| 五 索引与时效 | **有，且能直接移植** | 过期代码元素引用检测（两次快照比对） | 依赖修订感知，不依赖时间戳这条没有现成实现 |

### 最重要的一句话

**用户方案里「以代码符号引用作为硬证据」这条，是把五个挑战串起来的关键，也是文献里覆盖最薄的一条。** 现有追溯工作大多以自然语言文本相似度或架构模型作中介（ArDoCo 用架构模型、LLM 追溯用文本相似度），没有把「公开符号」当作唯一的、可机械验证的关联锚点。用户方案的这条约束反而更严格，也更可实现。

## 方案与项目现状的对照

### 挑战四对应的领域契约已经存在

`AssociationDomainService.ts` 已定义四个类型：

- `ExternalFact`：`factId`、`source`、`subject`、`predicate`、`object`，即主谓宾三元组
- `AssociationTarget`：`targetId`、`aliases`，**别名列表是外部提法映射到符号的落点**
- `AssociationLink`：`factId`、`targetId`、`confidence`、`reason`
- `ExternalExtractor` 与 `ReverseMapper` 两个注入点

领域服务做的是确定性校验：正文与来源非空、`factId` 非空且唯一、关联必须引用已提取事实与已提供目标、`confidence` 在 0 到 1、`reason` 非空。**提取与映射策略由外部注入**，领域层不碰模型与数据库。

这个契约的形状与用户方案是对得上的：事实三元组对应「外部知识提到的符号」，`aliases` 对应「公开符号的多种提法」，`confidence` 对应「经验卡片默认低置信」。

### 挑战五的度量骨架也已存在

`KnowledgeHealth.schema.json` 已定义三个指标，每个都要 `numerator` 与 `denominator`：

- `freshness`
- `coverage`
- `quality`

`coverage` 正是「防孤岛」的度量位，`freshness` 正是「时效」的度量位。**schema 有了，但指标还没有与关联机制接线。**

### 关联时机与现有规则的张力

`Association.md` 明确：关联「不改变每次飞轮只修订一份文档的约定，也不扩大 CodeAgent 的读取白名单」。用户方案里「外部知识以不可变快照方式参与关联」与这条是相容的，但**「卡片更新后旧关联自动失效」需要一个新的事件与状态迁移**，现有 `KnowledgeVersion` 状态机（CANDIDATE、ACCEPTED、VERIFIED、SUPERSEDED、LOW_CONFIDENCE）里 `SUPERSEDED` 可承载「被替代」，但**关联级失效还没有对应状态**。

## 三套组合方案

| 方案 | 内容 | 复杂度 |
|---|---|---|
| A 规则锚定优先 | 确定性符号匹配建立关联 → 模型只处理未命中的长尾 → 层级回填闭包 | 中 |
| B 双快照失效检测 | 记录关联建立时的源码修订 → 用两次快照比对算实例数 → 归零即失效 | 低 |
| C 全套治理 | A 加 B，再加演化意图判定与废弃日志，形成可审计的增删改废弃 | 高 |

**落地顺序建议**：

```
零  先把 KnowledgeHealth 的三个指标接上真实分母（当前只有 schema 没有接线）
一  做方案 B（成本最低，且能立刻暴露存量失效关联）
二  做方案 A 的确定性一级（符号精确匹配），先不接模型
三  模型只做长尾，且必须带置信度与理由，进 LOW_CONFIDENCE
四  补演化意图判定与废弃日志，让「旧关联自动失效」可审计
```

**为什么把度量放第一步**：`coverage` 与 `freshness` 的分母要先定下来，否则后面无法判断关联机制是否有效。这一点与「读取源码」专题的结论一致。测什么比怎么改更该先定。

**为什么模型放第三步**：`2511.00215` 给出的数据是，朴素提示词会把 98% 的函数判为不一致，加了局部归类与外部过滤后才降到 14%。直接把模型接到关联判断上，产出的关联会不可用。

## 需要项目先定的四件事

1. **符号锚点的匹配口径**：精确串匹配（论文做法）还是允许别名与大小写变体。这决定误报率，也是 `aliases` 字段的实际用法
2. **经验卡片的置信度区间与门禁关系**：用户已定「默认低置信、不与代码卡片同级发布」，但低置信的数值边界与是否影响 `confidence` 门禁值没有定
3. **关联级失效的状态表示**：`SUPERSEDED` 是版本级状态，关联本身需要独立的失效标记还是复用它
4. **全量索引与增量关联的边界**：材料级索引支持按主题、来源、时间过滤，但增量更新时索引如何局部刷新没有定

## 两个耦合冲突

- **不可变快照与存储成本**：用户方案要求外部知识以不可变快照参与关联，而 `Knowledge.md` 的 IO-19 规则要求质量达标后清理中间产物。快照属于必须长期保留的一类，否则旧关联无法复核。**清理策略需为快照开例外**，这与增量维护专题发现的同类冲突一致
- **三角关系的实测支撑不足**：用户方案要求代码卡、设计文档卡、经验卡三者形成三角关系，但文献里没有把「三类异构知识源同时挂到符号」作为设计的方案。最接近的是 `2606.18855` 的异构产物图，但它只做了 5 个变更场景的验证，**论文自己说明是机制示例，不是泛化结论**

## 检索与核实说明

**检索规模**：arXiv API 55 组查询 + papers.cool 34 组查询，去重后 712 条，与全仓已有 305 个标识去重得 692 条，按五大挑战建词表筛出 183 条相关，逐篇读 16 篇、深读 12 篇。

**核实方式**：全部论文标识经 arXiv 或 papers.cool 逐条核对标题与年份。检索过程中发现两个通道限制，已记入 skill：arXiv API 在同一出口并发请求时会返回 429 且退避很久；批量 `id_list` 查询会静默返回空。**本目录的年份以核对结果为准**，其中 `2212.01479` 为 2022 年发布（2023 年有会议版本），是唯一早于 2025 年的材料，因机制直接对应用户的时效挑战而保留并显式标注。

**检索噪声说明**：关键词含 `link`、`connect`、`metadata` 等泛词，初检命中大量无关材料（图论连通性、简历实体分配、电力知识图谱、卫星调制）。**692 条里只有 183 条与本专题相关。** 复用这批检索时不要仅凭关键词命中引入。
