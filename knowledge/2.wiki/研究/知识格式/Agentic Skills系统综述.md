## 它解决了什么问题

Agent 系统越来越依赖"可复用的程序性能力"来可靠执行长时程工作流。但此前这类能力的概念是混乱的：

- 有人叫它 **tool**（工具），但它只是原子调用
- 有人叫它 **plan**（计划），但它是一次性的
- 有人叫它 **prompt**（提示词），但技能有执行策略和终止条件

**技能（skill）的独特之处**：它把程序性知识打包成**可调用模块**，带明确的适用条件（applicability conditions）、执行策略（execution policies）、终止条件（termination criteria）和可复用接口（reusable interfaces）。技能跨任务复用，这是它与一次性计划、原子工具调用的本质区别。

对我们项目来说，这条综述回答了一个根本问题：**我们"Skill 基于源码生成知识"里的 Skill 到底是什么、怎么管？**

## 方法核心

### 技能生命周期（7 个阶段）

```mermaid
flowchart LR
    A[发现<br/>Discovery] --> B[练习<br/>Practice]
    B --> C[蒸馏<br/>Distillation]
    C --> D[存储<br/>Storage]
    D --> E[组合<br/>Composition]
    E --> F[评测<br/>Evaluation]
    F --> G[更新<br/>Update]
    G --> A
```

| 阶段 | 干什么 | 对应知识飞轮 |
|------|--------|-------------|
| **发现** | 从经验/数据中识别可复用模式 | 源码 → 知识：发现可复用的编码模式 |
| **练习** | 在任务中试用、验证技能 | 知识 → 代码：生成代码验证知识有效性 |
| **蒸馏** | 把经验提炼成精炼技能描述 | 差异反馈 → 知识迭代优化 |
| **存储** | 结构化存储、可检索 | 知识库组织（OKF/cannbot） |
| **组合** | 技能间组合成复杂工作流 | 多知识文档协同生成 |
| **评测** | 验证技能有效性 | 门禁（gate） |
| **更新** | 技能随环境变化迭代 | 知识飞轮循环本身 |

### 7 种系统级设计模式

综述总结了技能在系统中的 7 种打包/组合方式（设计模式），例如：
- 技能作为独立模块被检索调用
- 技能作为管道串联
- 技能自指式组合（技能调用技能）

### 两种分类法

1. **系统级分类**：技能如何被系统打包和使用（7 种模式）
2. **技能内部分类**：技能自身的内容结构（程序性知识 vs 声明性知识等）

## 关键洞察（对我们最有价值的部分）

1. **技能 ≠ 工具 ≠ 计划**：技能带适用条件 + 终止条件 + 可复用接口，这是"知识可执行化"的完整定义
2. **生命周期是闭环**：发现到更新形成循环，**评测阶段是更新的闸门**，这与我们"门禁通过才合并知识"完全一致
3. **蒸馏是核心工序**：把嘈杂经验提炼成精炼技能描述，对应我们"差异反馈 → 知识优化"的提炼过程

## 局限与注意

- 综述无实验验证，7 种模式没有优劣排序
- 技能（skill）与文档（document）的关系未深入：技能偏程序性（可执行），文档偏声明性（可读），我们的"解释型知识文档"介于两者之间，需要自己定义清楚
- 评测技能有效性本身是开放问题（与我们的门禁难题同源）

## 对我们项目的启发

### 直接借鉴 ✅

1. **技能生命周期 = 知识生命周期**：我们的知识飞轮本质是"技能/知识"的生命周期管理。综述的 7 阶段给了完整的框架图，飞轮各环节可以逐一对齐（见上表）
2. **技能定义要素**：知识文档作为"技能"时应包含：适用条件（何时用这份知识）、执行策略（怎么用）、终止条件（什么算完成）、接口（输入输出）。这可以升级我们的知识模板（设计/知识形态定义.md）
3. **评测是更新的闸门**：综述把评测放在更新之前，支持我们把门禁作为知识合并的硬闸门

### 需要改造 🔧

- 综述的技能是**程序性**的（怎么执行）；我们的知识文档是**解释型**的（为什么这么写）。需要定义"解释型知识如何转成可执行技能"，飞轮的第二步（知识 → 代码）就是这个转化
- 组合模式：多份知识文档组合生成一个大模块时，参考综述的组合模式设计

### 需要注意 ⚠️

- 技能概念的边界要小心：不要把"知识文档"和"可执行技能"混为一谈，两者在飞轮中角色不同（知识是中间产物，技能是消费形态）
