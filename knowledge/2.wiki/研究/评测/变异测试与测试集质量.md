## 它解决了什么问题

评测一个测试套件（或评测集）好不好，不能只看"代码覆盖率"：

1. **覆盖率高的测试套件也可能很弱**：覆盖了代码行但断言不严，行为错了照样通过
2. **测试套件质量没有客观量化**：行覆盖、分支覆盖都是"结构指标"，测不到"测试到底能不能发现错误"
3. **LLM 生成的测试质量未知**：LLM 写测试可能"看起来合理但杀不死任何变异体"

变异测试的回答：**把程序故意改坏（变异体），看测试能不能发现。发现得越多，测试越强。**

## 方法核心

```mermaid
flowchart TD
    A[原始程序 P] --> B[变异算子生成变异体<br/>改运算符/改常量/删语句]
    B --> C[变异体集合 M<br/>P1 P2 ... Pn]
    C --> D[测试套件 T 跑每个变异体]
    D -->|测试失败| E[变异体被击杀 killed]
    D -->|测试通过| F[变异体存活 survived]
    F --> G{等价变异体?}
    G -->|是| H[人工/自动识别剔除]
    G -->|否| I[测试盲区：T 没测到这个错误]
    E --> J[mutation score = killed / (total - equivalent)]
```

### 经典变异算子（C/C++）

- **运算符替换**：`+` → `-`、`>` → `>=`、`&&` → `||`
- **常量修改**：`1` → `0`、`0` → `1`、边界值 ±1
- **语句删除**：删掉 `if` 分支、删掉赋值
- **返回语句修改**：`return x` → `return 0`

### LLM 化（MutGen）

1. 用 LLM 生成测试
2. 跑变异测试，看哪些变异体存活
3. 把"存活的变异体"信息反馈给 LLM prompt
4. LLM 针对存活变异体生成新测试，直到击杀率提升

MutGen 在 104-204 个真实项目上显著超过 EvoSuite 与朴素 prompt 策略（mutation score 提升明显）。

## 关键洞察

1. **mutation score 是评测集强度的金标准**：比覆盖率更能说明"测试真的能抓错"
2. **存活变异体 = 测试盲区清单**：每个存活变异体都是一类"没被测到"的错误，可直接指导补测试
3. **LLM 能生成杀变异测试**：把变异反馈给 LLM，测试生成质量可迭代提升
4. **等价变异体是噪声源**：识别等价变异体需要人工/工具辅助，否则 mutation score 被低估

## 局限与注意

- 变异体数量爆炸：大型项目全量变异成本极高（需要抽样子集）
- 等价变异体识别困难：理论上不可判定，实践中靠近似
- 变异体质量影响结论：变异算子太弱，mutation score 虚高；太强，虚低

## 对我们项目的启发

### 直接借鉴 ✅

1. **评测集强度门禁（P1 核心）**：我们的评测集（tiling 8 条用例）应加 mutation score 度量：对源码做变异（删 tailNumLastCore、改 ceil 为 floor、改 TILE_LENGTH 常量等），看评测集能否击杀。mutation score ≥ 60% 才认定评测集合格，否则补用例
2. **存活变异体 → 补测试清单**：跑完变异测试后，把存活的变异体转成新增评测用例（如"tailNumLastCore 计算错误"应该被杀）
3. **防作弊的另一面**：评测集能杀变异体 = 能抓"部分正确"的作弊实现（比如只实现主路径、边界全错）

### 需要改造 🔧

- 变异工具选型：C++ 项目用 LLVM-mutate / Mull（C++ 变异测试工具），或自写轻量变异器（对模板 tiling 只需 5-8 个关键变异算子）
- 变异成本控制：MVP 阶段只对被测模块做变异，不做全仓

### 需要注意 ⚠️

- 等价变异体：变异结果要跑评测集验证，若变异体与源码输出完全一致（如 `(totalTiles + cores - 1) / cores` 改写法），需人工确认
- 变异测试是"评测集的评测"，不是飞轮每轮都跑；建议在评测集构建/更新时跑
