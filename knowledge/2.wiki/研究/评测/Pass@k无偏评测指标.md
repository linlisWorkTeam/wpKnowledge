# Pass@k — 代码生成的无偏评测指标

> 论文：https://arxiv.org/abs/2107.03374
> 名称：Evaluating Large Language Models Trained on Code（Codex 论文，HumanEval 基准出处）

## 基本信息

| 项目 | 内容 |
|------|------|
| **链接** | https://arxiv.org/abs/2107.03374 |
| **发布时间** | 2021-07 |
| **一句话总结** | 提出 pass@k 指标：每个问题生成 n 个候选，前 k 个里至少一个通过隐藏测试即算过；用无偏估计器避免小样本方差 |
| **核心创新** | 功能正确性优先于文本相似度：以隐藏测试执行结果评判代码，而不是看生成代码像不像参考实现 |

## 置信度评估

| 信号 | 评估 |
|------|------|
| 发表场所 | arXiv 预印本（OpenAI Codex） |
| 引用/影响 | 极高（HumanEval + pass@k 成为 LLM 代码评测事实标准） |

## 它解决了什么问题

1. **旧指标不测功能**：BLEU/CodeBLEU 测"像不像参考"，不测"跑不跑得对"
2. **生成是概率性的**：LLM 每次生成不同，单次成功与否随机，需要多次采样统计
3. **朴素 pass@k 有偏**：简单"采样 k 次看是否成功"在小样本下有方差/偏差，需要无偏估计

## 方法核心

```mermaid
flowchart TD
    A[问题集 HumanEval<br/>164 个 Python 函数] --> B[每个问题生成 n 个候选]
    B --> C[每个候选跑隐藏单元测试]
    C --> D{至少一个通过?}
    D -->|是| E[该问题算过]
    D -->|否| F[该问题算失败]
    E --> G[pass@k 无偏估计]
```

### pass@k 无偏估计器

生成 n 个样本，其中 c 个通过测试，则：

```
pass@k = 1 - C(n - c, k) / C(n, k)
```

（C 为组合数；k ≤ n。该估计器对所有 k 无偏，避免朴素估计的方差。）

### 关键实践

- **采样数**：Codex 评测 pass@1 用 n=1，pass@100 用 n=100 等
- **温度**：采样时用高温度（如 0.8）增加多样性
- **执行环境**：每个候选在沙箱内运行隐藏测试，防资源滥用

## 关键洞察

1. **执行式评测是金标准**：隐藏测试通过与否，直接反映功能正确性，不受"像不像"干扰
2. **多次采样揭示模型上限**：pass@100 高而 pass@1 低 = 模型"会但不够稳"，需要推理/采样策略弥补
3. **无偏估计器是统计细节，影响结论**：小样本下朴素估计虚高，无偏估计更可信
4. **测试质量决定评测可信度**：HumanEval 的测试太少（平均 7.7 个）正是后来 EvalPlus 批评的点

## 局限与注意

- pass@k 只测功能正确，不测性能/内存/可维护性
- 采样成本高：pass@100 需要跑 100 次执行
- 基准污染：训练语料含测试题，得分可能虚高（后续有防污染研究）

## 对我们项目的启发

### 直接借鉴 ✅

1. **"生成多个候选再择优"的评测思路**：飞轮当前每轮只生成 1 个代码（pass@1 语义）。可升级为：Coder 生成 k 个候选 → 评测集择优 → 最优者进门禁，提升迭代收敛率
2. **执行式评测已落地**：我们评测闭环（编译 + 测试执行 + confidence）正是执行式评测，方向与 pass@k 一致
3. **confidence 的语义 = pass@1**：当前 confidence = 通过用例数/总用例数，等价于单候选功能正确率，与 pass@k 家族兼容

### 需要改造 🔧

- 候选择优需要 Coder 接口支持"一次生成多个候选"（MVP 可先加参数）
- 择优用评测集跑分，不是 LLM 自评（避免自我感觉偏差）

### 需要注意 ⚠️

- 多次采样增加成本：MVP 阶段保持 1 候选，P1 再考虑 k 候选
- 评测集质量直接决定 pass@k 可信度，配套 EvalPlus/变异测试保证评测集强度
