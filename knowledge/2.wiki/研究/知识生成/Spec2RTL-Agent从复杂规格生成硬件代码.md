## 它解决了什么问题

硬件 RTL 代码开发复杂且人才稀缺。现有 LLM 方案要么用简化描述（太简单），要么依赖高级语言综合（不灵活）。Spec2RTL 的目标：让 LLM agent 直接读**复杂规格说明**，生成接近工业质量的 RTL 代码。

---

## 方法核心

```mermaid
flowchart LR
    A[复杂规格说明<br/>功能需求/接口/时序] --> B[解析与结构化<br/>拆解为子任务]
    B --> C[多阶段生成<br/>架构设计→RTL实现→验证]
    C --> D[验证反馈<br/>仿真/检查]
    D --> E[迭代修正]
    E --> C
```

- **规格解析**：从自然语言规格提取接口、行为、时序约束
- **多阶段 agent**：架构设计 → RTL 实现 → 验证，分工协作
- **验证回路**：用仿真/静态检查结果反馈，迭代修正
- 面向真实硬件场景（不只是 toy example）

---

## 实验结果

- 在真实硬件设计任务上生成可用 RTL 代码
- 复杂规格（多模块、有时序约束）也能处理
- 验证回路显著提升生成质量

## 局限与注意

- 硬件领域专用，迁移到软件需要适配
- 依赖仿真环境做验证反馈
- 生成代码仍需人工审查

## 对我们项目的启发 ⭐

### 可以直接借鉴的

**① 复杂规格 → 代码的可行证明**：硬件规格比软件文档更严格（接口/时序必须精确），Spec2RTL 证明 LLM agent 能处理"复杂规格 → 高质量代码"。我们的知识文档如果结构化到类似程度（接口契约、行为约束），基于它生成代码是可行的——这是对我们飞轮第二步的强信号。

**② 验证回路 = 反馈循环**：它的"仿真/检查 → 迭代修正"就是我们飞轮的"对比 → 反馈"在硬件场景的翻版。验证信号（仿真通过/失败）驱动迭代，和我们门禁信号驱动知识优化同构。

**③ 多阶段分工**：架构设计 → 实现 → 验证的分工，可以映射到我们的知识生成/代码生成/差异分析。

### 需要改造的

**① 验证信号从"仿真"到"源码对比"**：硬件用仿真验证，我们用源码对比验证——我们的信号更直接（源码就是真值），且不需要仿真环境。

**② 规格格式**：它用自然语言规格。我们可以借鉴"规格结构化"的程度——知识文档要包含可执行的接口/行为描述（类似硬件规格的严格度），而不只是散文。

### 需要注意的

- 这是"规格越严格、生成越可靠"的实证。我们知识模板设计时，应该把"可执行规格"（接口、约束、行为）作为必填部分，散文解释作为辅助——这个优先级很重要。
