# 版本管理

知识卡片版本管理的调研材料。解决的问题是：如果只保存最终更新后的知识库，会陷入局部最优，因此需要管理各个版本的知识卡片。

星级按**对本项目的可落地程度**评定，不按论文本身影响力。五星表示可直接指导实现决策。

## 版本管理全景

知识卡片每修订一次就产生一个新版本，多个谱系可以并存。下图给出各版之间的分叉关系，以及各个问题分别由哪篇回答。

```text
                    Knowledge Version System

        ┌──────────────────────────────────────┐
        │        每次修改都产生一个新版本       │
        └───────────────────┬──────────────────┘
                            │
                            ▼
              v1 ───→ v2 ───→ v3
                \              \
                 → v2b          → v4
                            │
        ┌───────────────────┼───────────────────┐
        ▼                   ▼                   ▼
     怎么存？             选哪个？            怎么回退？
    ChronoMem          EvoGit + HGM         ChronoMem
        │                   │                   │
        └───────────────────┼───────────────────┘
                            ▼
                   新版本敢不敢上线？
            Governed Capability Evolution
                            │
                            ▼
                怎么保证没人绕过这一套？
                      Autogenesis
```

三点读法：

- **上半部分是版本树**。v2b 和 v4 是从主干分出的支路，与主干的版本之间没有祖先关系，谁都不支配谁，因此不能比较优劣，只能并列。
- **中间三问并列**。怎么存、选哪个、怎么回退是三个独立问题，各自有对应方案，不必等上一个有结论才能推进。
- **下半部分递进**。先要能判断新版本敢不敢上线，才有「防绕过」的必要。Autogenesis 管的是贯穿全程的约束，画在末端表示它是最后一道机制保障。

## 四类路线

**路线 A 结构表达**：版本之间的关系怎么表达
- EvoGit：偏序 + 极大元。不设标量适应度，用祖先关系判断
- 适合回答「哪些版本可以并列作为继续探索的起点」

**路线 B 存储与回滚执行**：版本怎么存、怎么回退
- ChronoMem：全量快照 + 事件日志 + 语义索引，按 ID 确定性恢复
- Governed Capability Evolution：硬回滚、软降级、档案降级三种强度
- 适合回答「回滚到哪一版、怎么退」

**路线 C 选择依据**：选哪个版本继续
- DGM（见[知识飞轮](../知识飞轮/DGM开放进化自我改进Agent.md)）：归档采样
- HGM：按后代整支聚合表现，修正 DGM 的贪心判据
- GEPA（见[知识飞轮](../知识飞轮/GEPA反思式提示词进化.md)）：按逐测试项覆盖度加权
- 适合回答「历史最佳怎么定义」

**路线 D 机制保障**：怎么让版本化不依赖实现者自觉
- Autogenesis：协议层强制所有变更走接口
- Governed Evolution of Agent Runtimes：有界、可观测、可审计的运行时演化
- 适合回答「怎么保证将来新增路径也不绕过版本管理」

## 对本项目的核心结论

1. **偏序替代标量评分**。EvoGit 明确拒绝标量适应度。本项目 `Evaluation.md` 已写「相似度、模型自评分和自然语言『通过』不能覆盖这些条件」，`GateDecision` 是一组事实，落不到一个分数上，立场一致。

2. **版本索引应建在增量描述上，不在正文上**。ChronoMem 强调检索成本与版本数相关、与快照大小无关。知识文档可能很大，这一点直接决定可行性。

3. **回滚可靠性是准入条件**。Governed Capability Evolution 把「候选失败后系统还能不能恢复」列为准入判据，等到失败才考虑就已经晚了。本项目 `IO-19` 规定达标后清理中间候选只留最终版本与被替换的上一版，如果连上一版也清理，恢复能力就退化了，这是可程序化检查的条件。

4. **当前表现不等于改进潜力**。HGM 用数据证明 DGM 的选择判据与真实潜力相关性只有 0.285，自己做到 0.778。本项目的 `EvaluationReport` 衡量「这一版对不对」，要拿它推断「这一版还有多少改进空间」，两个问题之间没有可靠通路。

5. **回滚不是终点**。ChronoMem 的评测协议要求回滚后重新执行下游任务并验证反事实一致性；Governed Capability Evolution 的在线监控阶段持续追踪漂移。本项目 `ROLLING_BACK → GENERATING` 的边已经存在，回滚后必须重新走 check 与 evaluation。

6. **保留而非截断**。ChronoMem 回滚会截断后续版本（Git reset 风格），本项目 `KnowledgeVersion` 的设计是保留 `SUPERSEDED` 历史。这一点应采用本项目原有取向，被截断的版本可能是后续有价值的分支。

## 怎么用这批材料

- **要设计版本关系**：EvoGit 的偏序与极大元
- **要设计回滚定位**：ChronoMem 的四阶段流程
- **要设计回滚验收**：Governed Capability Evolution 的七阶段与指标定义
- **要定「历史最佳」判据**：HGM 的 clade 聚合
- **要保证机制不被绕过**：Autogenesis 的接口强制
