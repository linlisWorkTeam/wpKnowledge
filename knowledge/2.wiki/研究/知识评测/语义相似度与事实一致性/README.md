# 语义相似度与事实一致性：卡片去重、一致判定与覆盖率量化

知识卡片三项质量判定能力的调研：卡片之间是否重复或矛盾、卡片与真实代码是否一致、Git Diff 的改动是否被完整记录。对应项目 `DocGenAgent` 的「处理重复与矛盾」职责与 `CheckAgent.md` 明确留待研究的**相似度算法、评分、权重与阈值**。

## 为什么是三件事

三件事看起来都在问「对不对」，但**失败模式与技术路线完全不同**：

| 判定 | 问题形状 | 主要失败模式 | 可用信号 |
|---|---|---|---|
| 卡片之间是否同一件事 | 文本对文本 | 换词改写被漏判、模板化文本被误判重复 | 语义相似、原子事实、结构图 |
| 卡片与代码是否一致 | 文本对代码 | 模型不看文档也能猜对（捷径信号） | 执行结果、原子事实对齐 |
| 改动是否被完整记录 | 集合对集合 | 漏覆盖集中删除类改动 | 结构化改动清单、可枚举分母 |

**把三件事混成一个「相似度分数」是本项目需要避免的**，理由见下面第一条结论。

## 先看结论

### 三条最重要的发现

**一、用「代码-注释一致性检测」这类方法判断事实准确性，实测不成立。**

`2406.14836` 测了三个模型生成的 Java 注释，**即使最好的模型也有约五分之一含可证明不准确的陈述**。然后它去测现有的一致性检测技术能否抓出这些错误，结论是**这些技术与注释准确性之间没有统计显著关系**。它把替代路线叫作**文档测试**：用模型根据文档生成测试、跑测试、看通过还是失败。这条路与准确性之间**有稳健的统计关系**。

**这条直接决定了本项目的方向：事实一致性应当靠执行验证，而不是靠文本比对。** 与「文档相似度」专题里 `2608.00884` 的发现一致（删掉文档依据后模型准确率几乎不变，说明它在抓捷径信号）。

**二、非 Embedding 的可靠路线有四条，且各有明确的适用边界。**

| 路线 | 代表工作 | 原理 | 适用 |
|---|---|---|---|
| 原子事实分解对齐 | FIZZ `2404.11184` | 把文档拆成细粒度原子事实，与源文档做自适应粒度对齐 | 判「哪里不一致」，可解释性最好 |
| 依赖图相似 | CSSG `2601.04085` | 用程序依赖图建模控制依赖与变量交互，替代表面串匹配 | 代码侧相似度，非文本侧 |
| 语义哈希 + 多粒度门控 | SemHash-LLM `2607.01601` | 字符/词/文档三级信号门控融合，候选级联过滤 | 大规模去重，成本低于 1% 神经验证开销 |
| 两阶段混合 | HyClone `2508.01357` | 模型先筛，剩下的用执行验证判定功能等价 | 判「是否同一功能」最可靠 |

**三、覆盖率要算得出来，前提是有可枚举的分母，而不是让模型去 diff 里找。**

`2605.02163` DocSync 把这件事的困难说得很准：**静态分析能检测文档缺失，但无法评估语义一致性；LLM 有生成灵活性，但更新文档时缺乏对代码的深层结构认知会幻觉**。它给出的答案是 **AST 表示与 RAG 融合再加批评者迭代**，用中小模型达到自动裁判分 **3.44/5.0**（基线 CodeT5-base 为 1.91）。对本项目的直接含义见下面第三节。

## 一、语义相似度：判断两张卡片是否描述同一件事

### 纯 Embedding 不够用的三个理由

1. **模板化文本会误判重复**。知识卡片由流水线批量生成，句式高度相似，句向量的余弦相似度天然偏高
2. **换词改写会漏判**。同一个业务行为用不同术语表述，纯向量可能低于阈值
3. **无法区分「重复」与「矛盾」**。这两者在向量空间里可能都很接近，但处理动作完全相反：一个是合并，一个是拉出来评审

### 四条非 Embedding 路线

**路线一：原子事实分解对齐（FIZZ `2404.11184`，⭐⭐⭐⭐⭐）**

把文档拆成**细粒度的原子事实**，再通过**自适应粒度扩展**把摘要里的原子事实与源文档对齐。论文强调原子事实是更细的信息单位，因此**可解释性强**，能指出具体哪条事实不一致。

**对本项目的价值**：这是判「两张卡片矛盾」最直接的方法。两张卡片各拆成原子事实集合，再做对齐，冲突会落在具体事实对上，评审者能直接看到冲突内容。与「知识关联」专题里 DIAL-KG 的**陈述事实与状态迁移区分**可以配合：前者判重复，后者判过时。

**路线二：程序依赖图相似（CSSG `2601.04085`，⭐⭐⭐⭐）**

论文指出 BLEU、CodeBLEU、TSED 这类指标「依赖表面字符串重合或语法树结构，抓不到程序间更深层的语义关系」。CSSG 用**程序依赖图显式建模控制依赖与变量交互**，在 CodeContests+ 数据集上跨语言与单语言设置都优于既有指标。

**对本项目的价值**：卡片主要描述业务行为而非贴代码，因此 CSSG 用在**代码侧**更合适：判断「两次改动是不是在改同一个行为」。这条与 Q3 的结构化改动清单天然衔接。

**路线三：语义哈希多粒度门控（SemHash-LLM `2607.01601`，⭐⭐⭐⭐）**

四件事统一在一套框架里：**语义投影哈希**（在蒸馏的 LLM 嵌入空间学紧凑二进制码）、**注意力加权 MinHash**（抑制模板文本、突出信息内容）、**对比边界学习**、**选择性 LLM 裁决**。三级信号（字符、词、文档）通过门控融合，再做**级联过滤**缩小候选。

论文明确针对的抗性场景包括 **模板污染、短文本扰动、包含关系、病毒式片段**，并声称重复检测质量强而**神经验证成本低于 1%**。

**对本项目的价值最高的一条**：知识卡片正是**模板污染**的典型场景（同一套格式批量生成），注意力加权 MinHash 专门抑制模板文本。**成本低于 1%** 意味着可以每次生成后全量跑。

**路线四：两阶段混合（HyClone `2508.01357`，⭐⭐⭐⭐⭐）**

两阶段：**模型先做语义筛选**剔掉明显不是克隆的对子；**剩下的用执行验证**，由模型生成测试输入，**交叉执行**判定功能等价。

论文指出现有方法抓不到 Type 4 语义克隆（语法结构不同但功能相同），而**直接上模型效果不佳，因为模型对语法差异敏感**。两阶段设计正是为了解决这个敏感性。

**对本项目的价值**：这是「判断两张卡片是否描述同一功能」最可靠的路线。但要注意它的前提，**需要能执行**。卡片描述的是行为，可以用项目已有的 TestGenAgent 能力做交叉执行。

### 矛盾识别的专门方法

**`2511.19199` CLASH（⭐⭐⭐）** 给了矛盾检测的**分类法**：把矛盾分为**对象级**（object-level）与**属性级**（attribute-level）两类，并同时提供多选与开放式两种评测格式。

虽然 CLASH 是**多模态**基准（图文），但它的分类法对卡片矛盾识别有直接参考价值：**两张卡片说同一模块支持某功能 vs 说某功能的参数不同，是两类不同的矛盾**，识别难度与处理动作都不同。论文还发现当前最先进模型在跨模态冲突识别上有「系统性模态偏差与类别特定弱点」。

## 二、事实一致性：卡片与真实代码是否一致

### 关键反转：文本比对路线实测无效

`2406.14836` 的实验结论对本项目最重要：

- 三个 LLM 生成 Java 注释，**最好的也有约 1/5 含可证明不准确陈述**
- 现有代码-注释一致性检测技术**与注释准确性之间没有统计显著关系**
- 作者提出**文档测试**：用 LLM 根据文档生成测试 → 运行 → 观察通过或失败
- 实测**文档测试与准确性有稳健统计关系**，而此前技术做不到

论文还做了定性评估，指出这条路「在赢得开发者信任方面有前景，同时暴露了当前实现的局限」。

**对本项目的含义**：项目已有 TestGenAgent 与执行验证能力，**文档测试这条路是现成能力的新用法，不需要引入新依赖**。

### 四类可直接复用的机制

**机制一：文档测试（`2406.14836`，⭐⭐⭐⭐⭐）**

核心原理：**文档声称的行为如果为真，那么按文档写的测试应当通过；为假则失败**。这把「文档与代码是否一致」转成了可执行判定。

**机制二：原子事实对齐（FIZZ `2404.11184`，⭐⭐⭐⭐⭐）**

细粒度分解 + 自适应粒度扩展对齐，**输出可定位到具体事实**。用于错误定位。

**机制三：结构检索 + 批评者迭代（DocSync `2605.02163`，⭐⭐⭐⭐⭐）**

**AST 表示与 RAG 融合**提供依赖感知上下文，再用 **Reflexion 范式的批评者循环**让模型对照源码自我修正。论文的关键实测结论：**迭代批评循环带来可测量的语义正确性提升，且不需要增大参数量**。自动裁判分 **3.44/5.0**，基线 CodeT5-base **1.91**。

论文用 **LoRA 适配的小模型**，明确标注是「资源受限实现」。**这对本项目很关键**：项目只能用本地部署模型，这篇证明小模型加正确架构也能达到可用水平。

**机制四：SIFiD 的关键句过滤（`2403.07557`，⭐⭐⭐）**

论文重新评估了 LLM 做不一致检测的表现，发现**早期尝试中 LLM 表现不如传统模型**，原因是「指令遵循能力有限且缺乏有效的检测方法」。SIFiD 的应对是**先用自然语言推理或语义相似度筛出文档中的关键句**，再基于过滤后的文档做检测。

**对本项目的含义**：不要直接把整张卡片丢给模型判一致性，**先筛关键句能显著改善**。这条在长卡片上尤为重要。

## 三、内容覆盖率：Git Diff 的改动是否被完整记录

### 覆盖率算不出来的两个原因

1. **分母不可枚举**。如果让模型「读 diff 找哪些没被记录」，它无法给出一个可核对的清单，覆盖率就无从计算
2. **改动类型的影响被忽略**。`2512.19883`（见「文档相似度」专题）指出，把改动分解成**替换、删除、新增**的有序序列后 F1 提升最高 13.54%。**删除类改动最容易漏覆盖**，因为文档通常只加不减

### 三层递进的做法

**第一层：静态分析提取结构化改动清单（确定性，无模型）**

用语法分析或成熟的 diff 库把 diff 分解成带类型的改动活动序列。**产出物有两重身份**：既是模型判断的输入，也是覆盖率的统计底表。

这一层给出覆盖率的分母。可产出四个中间指标：

| 中间指标 | 怎么算 | 意义 |
|---|---|---|
| 改动活动总数 | 分解器输出 | 覆盖率分母 |
| 被卡片提及的活动数 | 逐条核对 | 覆盖率分子 |
| 活动类型分布 | 按替换/删除/新增计数 | 验证「删除类最易漏覆盖」 |
| 未匹配活动的类型分布 | 未匹配项分类 | 指出漏覆盖集中处 |

**这四个指标不依赖模型，可复现，不因换模型而变。**

**第二层：AST 与依赖感知上下文（DocSync `2605.02163`）**

DocSync 的做法是**融合 AST 表示与 RAG**，提供**依赖感知的上下文**。论文明确指出这一层解决的是「LLM 更新文档时缺乏对代码的深层结构认知」这个具体问题。

**对本项目的含义**：判断某条改动是否被某张卡片覆盖，需要知道「这条改动影响的文件与卡片描述的文件是否有依赖关系」。AST 加依赖图能提供这个上下文，而不是把整个 diff 丢给模型。

**第三层：批评者迭代确认（DocSync 的 Reflexion 循环）**

论文实测迭代批评循环带来可测量的语义正确性提升，**且不需要增大参数量**。对本项目的含义是：**覆盖率判定不必一次成型**，可以迭代收敛。

### 一个必须声明的边界

`2605.02163` DocSync 论文原话点出了工具的能力边界：

> 静态分析工具能检测文档的缺失，但无法评估其语义一致性；而标准 LLM 提供生成灵活性，但在更新文档时经常产生幻觉，缺乏对底层代码的深层结构认知。

**这句话正好界定了本项目三件事的分工**：静态分析管「有没有」，模型管「对不对」，执行验证管「是不是真的」。三者的边界不能互相替代。

## 四、方案对比：准确性、性能与实现成本

### 三种路线族对照

| 维度 | 纯 LLM | 传统算法 | 静态分析 | 混合（推荐） |
|---|---|---|---|---|
| **准确性** | 中（`2608.00884`：删掉依据准确率几乎不变，说明判断未建立在文档上） | 中（CLASH：跨模态冲突识别有系统偏差） | 高但范围窄（只能判有/无，不能判语义） | **高**（HyClone、DocSync 均为混合方案且均优于单一路线） |
| **性能** | 高开销（每对一次模型调用，长卡片更贵） | **低**（SemHash-LLM 神经验证成本 <1%） | **极低**（毫秒级，可每次跑） | 中（模型只处理候选集） |
| **实现成本** | 低（提示词即用） | 中（需调参、维护词表与哈希结构） | 中（需语法分析器，但项目已有词法提取能力） | 中高（需编排三层） |
| **可解释性** | 低（模型说「不一致」，说不出依据） | 中（相似度分数无业务含义） | **高**（改动清单可枚举） | **高**（冲突落在具体原子事实或改动活动上） |
| **主要失败模式** | 捷径信号、幻觉、漏报 | 模板污染误判、换词漏判 | 只能判有无，判不出语义 | 编排复杂度，任一层失配即退化 |

### 成本与收益的实测参照

| 方法 | 论文 | 关键数字 |
|---|---|---|
| DocSync（AST + RAG + 批评循环，LoRA 小模型） | `2605.02163` | 自动裁判 **3.44/5.0** vs CodeT5-base **1.91** |
| SemHash-LLM（多粒度哈希 + 选择性 LLM 裁决） | `2607.01601` | 神经验证成本 **<1%** |
| 结构化改动序列（CodeT5+ 中等模型） | `2512.19883` | F1 提升最高 **13.54%** |
| HyClone（模型筛选 + 执行验证） | `2508.01357` | precision、recall、F1 均显著优于纯 LLM |
| CSSG（依赖图相似） | `2601.04085` | 跨语言与单语言均优于 BLEU/CodeBLEU/TSED |
| 文档测试 | `2406.14836` | 与准确率有稳健统计关系；一致性检测技术则**无显著关系** |

### 为什么混合方案更优（三条证据）

1. **`2508.01357` HyClone**：纯 LLM 路线「因对语法差异敏感而效果不佳」，两阶段（筛选加执行验证）在三个指标上全面提升
2. **`2605.02163` DocSync**：结构检索加智能体精化「无需增大参数量即可带来语义正确性提升」
3. **`2512.19883`**：结构化预处理加中等模型**打赢了直接喂大模型的方案**，说明输入组织形式比模型规模更重要

### 三条必须遵守的既有边界

1. **「不把编号索引、相似度算法或新的代码检测系统作为实现前提」**（`CheckAgent.md` 第 64 行）。本专题推荐的**结构化改动分解**属于「程序提取」而非新检测系统，但边界需要显式说清
2. **「不能把简单名称搜索等同于行为一致性判定」**（同处）。这条支持把一致判定交给执行验证，而不是文本匹配
3. **「实现和评测不能自行给出一个相似度分数作为发布依据」**（第 133 行）。与 `Evaluation.md` 的「Similarity 仅用于归因」一致。**本专题的所有量化输出都应当定位为归因与诊断信号，不作发布依据**

### 一个结构性的判断

三件事不应共用同一个分数。`2406.14836` 说明**文本一致性检测与事实准确性之间没有统计关系**，意味着用「相似度」同时承担去重与一致性判断，会得到两个都不准的结果。**建议三件事各用各的信号**：

- 卡片间重复与矛盾 → 原子事实对齐加语义哈希
- 卡片与代码一致 → 文档测试（执行验证）
- 改动覆盖率 → 结构化改动清单加枚举式核对
