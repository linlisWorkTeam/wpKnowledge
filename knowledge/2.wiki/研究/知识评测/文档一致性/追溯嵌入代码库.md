# 追溯嵌入代码库

把可追溯元素嵌入代码本身，让追溯成为编译期可验证属性。

论文：ReqToCode: Embedding Requirements Traceability as a Structural Property of the Codebase
标识：`2603.13999`
链接：[https://arxiv.org/abs/2603.13999](https://arxiv.org/abs/2603.13999)

## 要解决的问题

安全关键软件开发中的需求追溯**仍然主要依赖与系统分离维护的外部文档**。

论文把这个分离带来的后果说得很准：

> 这种分离引入了**结构性脆弱**：随着需求、代码和测试在工具、仓库和修订之间**独立演化**，追溯**静默退化**。

论文还对现有 LLM 追溯路线给了一个定性判断：**当前基于 LLM 的追溯方法专注于事后恢复已断开的链接，这是一种内在的回顾式（retrospective）方法**。

对方向的判断很明确：**从事后恢复到事前预防**。

## 方法核心

ReqToCode 的核心是**把可追溯的系统元素直接嵌入代码库**，使追溯成为**系统的编译期可验证属性**，而不再是外部的文档工作。

### Traceable：语言原生的生成元素

核心概念是 **Traceable**：一个**语言原生（language-native）、生成（generated）的代码元素**，代表**单条需求**，并**携带其元数据**。

开发者在**实现代码与测试代码中引用 Traceable**，从而创建**硬性的双向链接**，这些链接在**构建过程中自动验证**。

### 渐进生命周期

当需求变化时，系统通过**渐进式生命周期**响应：

1. **弃用警告（deprecation warnings）**
2. **构建失败（build failures）**

论文强调这个设计提供的是**可操作的信号**，而非**突然的断裂**。

这个设计细节很重要：直接构建失败会在需求变更时立刻阻断开发，给团队的是「突然断裂」。渐进式设计让团队有时间响应。

## 关键数据

这是一篇**方法提出型论文**，摘要中未报告量化实验数据。可确认的内容：

- 方法：语言原生生成元素承载需求，硬性双向链接
- 验证机制：构建期自动验证
- 变更响应：弃用警告到构建失败的渐进生命周期
- 论文用一个**通用示例**贯穿说明：需求定义、工件生成、代码集成、构建期验证

## 对本项目的启发

### 方案要点

**一、「静默退化」是本项目必须正视的风险。**

论文的诊断直接适用于知识卡片：如果卡片与代码的关联完全靠外部判断（每次都重新用模型对照），那么随着代码演化，**关联会静默退化而没有任何报警**。

本项目的现状正是这种形态：每次 Git Diff 后重新判断，不保留跨版本的锚点。退化表现为「某张卡片已经半年没被更新过，但没人注意到」。

**二、完整方案对本项目过重，但可以取其中一层。**

ReqToCode 要求**修改被测代码**（嵌入 Traceable 元素），对本项目不可行 —— 知识卡片系统不应侵入它记录的对象。

但它的设计里有一层可以取用：**让卡片记录它所依据的符号与位置**。这样即使不侵入代码，也能在符号消失或位置失效时立刻报警。

这与「知识关联」专题已调研的符号锚定级联策略是同一方向，本专题的增量在于**把它定位为防退化机制**，而不只是定位手段。

**三、渐进式信号的设计值得借鉴。**

「弃用警告到构建失败」的两级设计可以直接映射到卡片的状态机：

| 阶段 | 触发条件 | 信号强度 |
|---|---|---|
| 正常 | 锚点全部有效 | 无 |
| 弃用警告 | 锚点部分失效或长期未更新 | 提醒，不阻断 |
| 构建失败 | 锚点全部失效或声明被证伪 | 阻断发布 |

这个设计避免了「要么不管，要么全停」的两极。

**四、双向链接比单向比对更有信息量。**

论文强调创建**硬性双向链接**。对本项目的含义：不仅要能回答「这张卡片依据哪些代码」，还要能回答「这段代码被哪些卡片记录」。

第二个方向正是 Q2 的多对一问题：**多处代码共同支撑一段文档**。如果没有反向索引，判断「一段文档是否被完整支撑」就无从下手。

**五、编译期验证这个形态是理想态，但不是必需。**

论文的最大优势是验证**不消耗模型调用**且**不可能漏报**（链接失效即编译失败）。本项目做不到编译期，但可以用**提交时校验**近似：每次 Git Diff 后先跑一次锚点有效性检查，失败即报警，不需要模型参与。

### 与本项目三条路线的定位对比

| 路线 | 是否侵入代码 | 验证成本 | 防退化能力 |
|---|---|---|---|
| ReqToCode（本文） | 是 | 零（编译期） | 完全 |
| 卡片记录符号锚点（折中） | 否 | 低（提交时校验） | 部分 |
| 每次重新模型比对（现状） | 否 | 高 | 无 |

## 局限

- **摘要是方法提出型**，未提供量化实验数据。这一点需要明确：没有实测的准确率、覆盖率或成本数字
- **完整方案侵入被测代码库**，对本项目及多数以「记录」为职责的系统不适用
- **需要语言原生支持**。论文假设可以在代码中生成语言原生的元素，这依赖语言与构建系统的能力
- **需求变更时的构建失败会阻断开发**。渐进式设计缓解了这一点，但团队仍需维护这套机制
- **论文只给出通用示例**，没有在真实大型项目上的验证，可扩展性未知
- **与既有追溯工具的关系未说明**。是否兼容现有需求管理系统不明
