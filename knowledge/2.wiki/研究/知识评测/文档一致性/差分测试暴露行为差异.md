# 差分测试暴露行为差异

用变更导向的差分测试给出「行为是否真的变了」的客观判据，以及 union coverage 指标。

论文：DiffTestGen: Change-Directed LLM-Based Testing for Exposing Behavioral Differences
标识：`2607.16024`
链接：[https://arxiv.org/abs/2607.16024](https://arxiv.org/abs/2607.16024)

## 要解决的问题

软件演化过程中，需要确保**行为变更符合开发者意图**。一个有前景的方向是**生成能暴露新旧版本之间行为差异的测试**。

但论文指出现状：**当前方法对许多代码改动无法触发行为差异**。

问题在于测试要触达被改动的代码并不容易：改动的代码可能藏在深层调用链里，测试需要构造正确的入口和输入。

## 方法核心

DiffTestGen 是一个**变更导向的、基于 LLM 的差分测试方法**，专门设计用来暴露代码改动引入的行为差异。它有两个关键贡献。

### 贡献一：用静态分析与文档定位有效入口

DiffTestGen 利用**静态调用图分析**与**项目文档**来：

- 识别**测试生成的有效入口点**
- **引导 LLM 到达被改动的代码**

这里「项目文档」的用法很有启发：文档被当作**定位辅助**，而不是被验证的对象。对本项目而言这是一个反向启示，知识卡片本身可以成为测试生成的导航信号。

### 贡献二：union coverage 指标与迭代反馈

论文引入一个新的覆盖度量 **union coverage**：

> 组合**旧版本与新增本中被修改代码**的覆盖。

设计动机很清晰：如果只测新版本的改动代码，就无法保证测试真的触达了「变化」本身，因为可能新代码在旧代码从未被执行过的路径上，测试通过只是因为没有触发差异。

DiffTestGen **迭代改进 union coverage**，方式是向 LLM 提供**有针对性的覆盖反馈**。

### 与回归检测的集成

论文把 DiffTestGen 与 **Testora 回归检测器**集成，证明识别出的行为差异**能用来检测现有最佳方法漏掉的回归 bug**。

## 关键数据

评测在**两个数据集，共 463 个 PR** 上进行。

| 指标 | 实测值 |
|---|---|
| 暴露行为差异的 PR 比例 | **78.2%** |
| 平均 union coverage | **90.7%** |
| 相比基线的改进 | 总体**多暴露 99 个 PR** |
| 代码覆盖率提升 | **12.5** 与 **15.6** 个百分点 |

与 Testora 集成后：**能发现现有最佳方法漏掉的回归 bug**。

## 对本项目的启发

### 方案要点

**一、union coverage 是覆盖率指标设计的直接参照。**

这是本条最有复用价值的产出。指标定义：**旧版本中被修改的代码**与**新版本中被修改的代码**，两者的**并集**被测试覆盖的比例。

对本项目「改动覆盖率」的启示在于：判断一条改动是否被文档记录时，**不应只看改动后的状态**。有些改动只有在理解「改动前是什么样」的情况下才能判断它是否值得记录。

举例：删除了一个输入校验分支。只看新代码，看不出这里曾有校验；看 diff，才知道存在一次行为收窄。这与「文档相似度」专题已确认的结论一致（**删除类改动最易漏覆盖**）。

**二、78.2% 是「能暴露行为差异」的现实上限。**

即使在最好的设置下，仍有约 **22% 的 PR 无法暴露行为差异**。对本项目的含义是：**差分测试不能作为唯一判据**，它需要与其他层配合。

**三、90.7% 的覆盖率说明入口定位是可行的问题。**

论文用静态调用图加项目文档定位入口，达到平均 90.7% 的 union coverage。这说明「如何让测试触达被改动的代码」这个问题已有可用的解法。

**四、迭代式覆盖反馈是必要的。**

论文采用了迭代方式生成测试，根据覆盖情况持续提供反馈。这与 DocSync 的批评者循环思路一致（见「文档相似度」专题），**覆盖率判定不必一次成型**。

**五、文档可以作为测试生成的导航信号。**

论文用项目文档帮助识别入口点。对本项目的含义有两层：

- 知识卡片如果质量高，可以辅助测试生成，形成正循环
- 反之，如果卡片记录了不存在的入口，会误导测试生成

第二层是本项目 OVERSTATED 的一个**下游危害**：错误的卡片不只是记录错误，还会污染依赖它的环节。

### 在 Q1 三层手段中的位置

| 层 | 手段 | 输出 | 是否需要可执行 |
|---|---|---|---|
| 一 | 重构检测 | 行为保持改动清单 | 否 |
| 二 | 模型 oracle | 行为变更判断 | 否 |
| 三 | **差分测试** | **行为是否变了的客观证据** | **是** |

第三层是唯一给出**客观证据**的层，代价是要求代码可执行且能生成测试。

对本项目而言，项目已有 TestGenAgent 能力，所以这一层的**边际成本低于从零建设**。

### 可以直接借鉴的指标

| 指标 | 定义 | 本项目用途 |
|---|---|---|
| union coverage | 新旧版本被修改代码的并集覆盖率 | 覆盖率分母的清洗方式 |
| 行为差异暴露率 | 能暴露差异的 PR / 全部 PR | 判定手段的覆盖上限参照 |
| 入口点识别准确率 | 正确入口 / 识别的入口 | 测试生成的先行指标 |

## 局限

- **约 22% 的 PR 无法暴露行为差异**，这是方法的固有上限，论文未说明失败原因的分类
- **需要可执行的代码与可生成的测试**。对不可执行的改动（如配置、文档本身）不适用
- **两个数据集共 463 个 PR**，规模中等，跨项目泛化性有限
- **依赖项目文档作为入口定位信号**。如果文档本身不可靠，方法效果会受影响，论文未评估这种敏感性
- **未报告误报率**。「暴露了行为差异」不等于「差异是非预期的」，判定意图仍需人工或额外机制
- **与 Testora 的集成收益未量化**，只说能发现漏掉的回归 bug，未给出数量
- **union coverage 的计算需要版本对比能力**，对本项目的 Git Diff 场景是可行的，但如果只有单边代码则不适用
