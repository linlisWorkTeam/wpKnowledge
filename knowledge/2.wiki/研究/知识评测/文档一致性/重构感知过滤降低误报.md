# 重构感知过滤降低误报

区分行为保持的重构与影响行为的改动，以及不做这一步的代价。

论文：RefFilter: Improving Semantic Conflict Detection via Refactoring-Aware Static Analysis
标识：`2510.01960`
链接：[https://arxiv.org/abs/2510.01960](https://arxiv.org/abs/2510.01960)

配套论文：How Much Can a Behavior-Preserving Changeset Be Decomposed into Refactoring Operations?
标识：`2508.11993`
链接：[https://arxiv.org/abs/2508.11993](https://arxiv.org/abs/2508.11993)

## 要解决的问题

协作开发中的语义干扰检测（一次改动影响另一次改动）一直很难。基于程序依赖图的传统方法准确但慢，近期轻量静态分析技术提升了效率，**但仍受高假阳性率困扰**。

RefFilter 指出了这个假阳性的具体成因：

> 这些假阳性的一个关键原因，是**行为保持的代码重构**的存在，当前技术**无法有效地把它与影响行为、可能与他人产生干扰的改动区分开**。

这正是本项目 Q1 的核心问题。Git Diff 里混着两类东西：重构（不需要更新文档）和功能变更（需要更新文档）。不区分它们，覆盖率的分母就被灌水，UNDERSERVED 判定也就失真。

## 方法核心

### RefFilter 的做法

RefFilter 在既有静态分析技术之上，**加入自动化的重构检测**来提高精度。具体机制是：

1. 用重构检测器识别 diff 中的行为保持重构
2. 把这些重构**从报告中丢弃**
3. 保留其余改动的检测覆盖

论文把这个策略概括为「重构感知的干扰检测」，并证明它**在保持检测覆盖的同时降低假阳性**。

### 配套研究给出的分解上限

`2508.11993` 回答了一个更基础的问题：**一个行为保持的改动集，有多大比例能被分解成重构操作**？

这个问题的重要性在于：如果分解覆盖率低，说明就算有完美的重构检测器，也识别不出全部的行为保持改动，剩余部分会被误判为功能变更。

论文用功能等价方法对数据集做量化，结果不乐观：

- 使用**现有重构检测器**：**仅 33.9%** 的改动被识别为重构操作
- 加入论文**新定义的 67 个功能等价操作**后：覆盖率**提升超过 128%**
- **仍有无法解释的差异**，作者指出存在改进空间

第二个数字是重点：覆盖率的相对提升很大（128%），但**基数低**。这说明现有工具的识别能力远未饱和，同时也说明**这条路线没有终点**，总有一部分改动无法归类。

## 关键数据

**RefFilter（重构感知静态分析）**，两个数据集：

- 带标注数据集：**99 个场景**，有 ground truth
- 新建数据集：**1087 个多样化合并场景**

实测结果：

- 假阳性**降低近 32%**
- 假阴性增加**不显著**
- 论文结论：精度的整体收益**显著超过**召回上的微小代价

**分解覆盖率（`2508.11993`）**：

- 现有重构检测器：**33.9%**
- 加入新定义操作后：**提升 128% 以上**
- 剩余差异：无法解释，存在改进空间

## 对本项目的启发

### 方案要点

**一、把重构检测作为覆盖率流水线的第一道工序。**

顺序很重要：**先剔除行为保持的改动，再计算覆盖率**。反过来做，分母包含大量重构，覆盖率会虚低，UNDERSERVED 会虚高。

这一步是**确定性的、不依赖模型**的，所以它可以在每次提交时稳定运行。

**二、假阳性降低 32% 是过滤重构的直接收益。**

这个数字出自同类任务（语义冲突检测），机制与本项目的场景一致：都是要把行为保持的重构排除在「需要关注的改动」之外。论文还提供了可直接复用的评估数据集（1087 个合并场景）。

**三、33.9% 意味着过滤不可能是完备的。**

这是本条最重要的限制。即使接入最好的重构检测器，**也只识别出约三分之一的行为保持改动**，剩余三分之二会被当成功能变更。后果是：

- UNDERSERVED 仍有相当比例的假阳性
- 不能声称覆盖率是精确值，只能作为**相对趋势指标**

配套论文的作者自己也在继续定义新的功能等价操作来提升覆盖率，说明这是一个持续推进的问题。

**四、假阴性与假阳性的取舍方向已经明确。**

RefFilter 的实测给出的是「假阳性大降、假阴性微增」，论文认为这个取舍是划算的。对本项目同样成立：**宁可漏报几条真遗漏（转人工时还能被发现），也要大幅削减噪音**，因为人工评审的注意力是稀缺资源。

**五、这两个数据集可以直接用作评测素材。**

- 99 个场景的带标注数据集（有 ground truth）
- 1087 个多样化合并场景

如果你的四类结论要做可靠性评估，这类带标注的真实场景数据比自造样例更有说服力。

### 落地顺序建议

| 步骤 | 动作 | 依赖 | 确定性 |
|---|---|---|---|
| 1 | 接入重构检测器 | 无 | 是 |
| 2 | 从 diff 中剔除行为保持改动 | 步骤 1 | 是 |
| 3 | 剩余改动做结构化分解 | 解析器 | 是 |
| 4 | 模型对照卡片声明判定 | 模型 | 否 |
| 5 | 报告未匹配项为 UNDERSERVED | 步骤 3、4 | 部分 |

步骤 1 到 3 都不依赖模型，可以先做，且收益（降噪）立即体现。

## 局限

- **重构检测只覆盖 33.9%**，剩余行为保持改动会被误判为功能变更，这是路线本身的固有上限
- **RefFilter 的评测场景是合并冲突**，与本项目的 Git Diff 到文档场景不完全同构。假阳性降低 32% 这个数字不能直接移植，需在本项目数据上重测
- **论文未给出假阴性的具体数值**，只说「不显著增加」
- **重构检测器的语言与工具支持范围是硬约束**。本项目使用的语言是否有成熟检测器需要单独确认
- **两个数据集的语言与技术栈**需核对是否与本项目匹配
