# 基础模型作重构正确性判据

用基础模型直接读 git diff 判断重构是否改变了行为，以及这个判据的外部验证。

论文一：Detecting Behavioral Changes in Python Refactoring Implementations with Foundation Models
标识：`2608.09919`
链接：[https://arxiv.org/abs/2608.09919](https://arxiv.org/abs/2608.09919)

论文二：Foundation Models as Oracles for Refactoring Correctness Detection
标识：`2605.02096`
链接：[https://arxiv.org/abs/2605.02096](https://arxiv.org/abs/2605.02096)

## 要解决的问题

重构的定义是**改善代码内部结构而不改变外部行为**。因此「重构是否引入了行为变更」是一个可以判定的是非问题，判定失误会损害软件可靠性。

两篇论文各自解决这个问题的不同侧面：

- `2608.09919`：**Python 自动化重构工具本身有 bug**，如何找出它们
- `2605.02096`：IDE 的重构工具会引入**非预期的行为变更或编译错误**，如何检测

传统检测路线是**手写前置条件、静态分析、动态分析**，论文指出它们**在适应性上受限，且会漏掉细微的正确性问题**。

## 方法核心

### 论文二（`2605.02096`）：零样本提示作 oracle

核心思路是把基础模型当作**重构正确性的判定 oracle**，用**零样本提示（zero-shot prompting）**，**不做任务专属训练**。

评测素材的质量很高：**226 个真实重构 bug**，从广泛使用的 Java IDE（**IntelliJ IDEA、Eclipse、NetBeans**）中收集，**时间跨度超过十年**，覆盖 **47 种重构类型**。

这是一份**真实 bug 数据集**，而非合成样本。

论文还用**蜕变测试（metamorphic testing）**检验模型预测在**语义保持扰动**下是否稳定。

### 论文一（`2608.09919`）：直接分析 git-style diff

这条路线与本项目的形态**完全一致**：用基础模型 oracle **分析 git 风格的 diff**，识别 Python 重构引入的行为变更。

评测设计：

- 复用先前研究的 **1152 次重构尝试**
- 用 oracle 分析其中 **217 个变换对**
- 覆盖 **7 种重构类型**（论文中研究的那几种）

## 关键数据

### 论文二（`2605.02096`）准确率

| 模型 | 准确率（首次运行设置） |
|---|---|
| **GPT-5.4** | **93.8%** |
| **GPT-OSS-20B**（开源） | **80.5%** |

其他评测模型：**Gemma-4-31B** 是开源模型中表现最强的；**Gemini-3.1-Pro-Preview** 是所有评测模型中总体最优的。

论文还发现基础模型能提供**简短解释**，有助于开发者审查；且能**跨重构类型工作，无需显式编码重构专属规则**。

### 论文二的重要限定声明

蜕变测试显示模型预测在**所测试的语义保持扰动下大体一致**，但论文明确声明：

> 这些结果应当被解读为**鲁棒性证据**，而非**反对记忆或数据污染的证据**。

**这条声明应当被继承。** 它说明「模型在这个任务上准确率高」可能部分来自训练数据见过这些 bug，而非真的在做推理。

### 论文一（`2608.09919`）外部验证

这是本条最重要的数据，因为它是**外部证据而非自评**：

- 在 **217 个变换对**中识别出 **13 个不同的 bug**
- 覆盖 **7 种重构类型**
- **全部 13 个 bug 都提交给了对应开发者**
- 根据 **issue tracker 证据**，**12 个 issue 报告被接受**

12/13 的接受率意味着这些是真实缺陷，而非模型幻觉。论文由此得出结论：**当前 Python 重构工具的鲁棒性需要改进**。

## 对本项目的启发

### 方案要点

**一、93.8% 是上限参照，80.5% 是本地部署的现实参照。**

这个对比对本项目有直接意义：项目只能用本地部署模型。**GPT-OSS-20B 在 20B 量级达到 80.5%**，说明这个任务在小模型上也可用。

它还说明一个选择：**如果只做重构正确性判定，不需要最强模型**。把这个任务与需要深层语义推理的任务分开，可以让不同难度的环节用不同规模的模型。

**二、12/13 被接受这个证据链的形态值得复制。**

论文的验证方式落在「我们的发现被独立第三方接受」，而非「我们的指标提升了」。对本项目而言，如果四类结论要证明有效性，最有说服力的方式同样是：

- 把发现的 UNDERSERVED / OVERSTATED 案例提交给独立评审者
- 统计**接受率**，而非模型自评分数

这个证据形态可以绕过「模型自己评自己」的循环。

**三、不要声称蜕变测试证明了模型没有记忆。**

论文自己做了这个限定。这在向他人报告结果时是一个纪律问题：鲁棒性证据不等同于泛化性证据。项目已有类似的经验（`2608.00884` 的捷径信号发现），这里的原则一致。

**四、git diff 是有效输入形态。**

论文一**直接分析 git-style diff**，这与你的流水线输入完全一致。它证明「让模型读 diff 判行为变更」这条路**有真实产出**，不需要先做复杂的中间表示。

但要注意：论文一的任务是**判断重构实现是否有 bug**，不是「判断是否需要更新文档」。两者共享输入形态与部分能力，但判定目标不同。

**五、跨重构类型工作不需要显式规则，这是一个实用优势。**

论文二指出基础模型能**跨重构类型工作，无需显式编码重构专属规则**。对本项目而言，这避免维护一张「哪些重构类型需要更新文档」的规则表。

但代价是**可解释性与规则表相比更弱**，且无法保证覆盖已知类型。

### 与 Q1 的关系

基准模型作 oracle 是本项目 Q1 的**第二层手段**（第一层是确定性的重构检测，见「重构感知过滤降低误报」）。两者的分工：

| 层 | 手段 | 作用 | 确定性 |
|---|---|---|---|
| 一 | 重构检测器 | 标出行为保持改动 | 是 |
| 二 | 基础模型 oracle | 在剩余改动上判行为变更 | 否 |
| 三 | 差分测试 | 给出行为是否变了的客观证据 | 是（但需可执行） |

模型 oracle 的价值在于**填第一层覆盖不到的部分**（重构检测只覆盖 33.9%），而它的可靠性用第三层来兜。

## 局限

**论文二（`2605.02096`）**：

- **蜕变性证据不排除记忆或污染**，这是论文自述的最重要限制
- **准确率数字来自零样本首次运行**，多次运行或不同提示词下的表现未说明
- **226 个 bug 来自三个主流 IDE**，说明数据集有明确的生态偏向
- **未报告假阳性率**。93.8% 准确率未说明错误是偏向误报还是漏报
- **只评测 Java**，其他语言的泛化性未知
- **论文用的是「首次运行设置」**，实际部署中可能有重试，成本与效果都会变化

**论文一（`2608.09919`）**：

- **217 个变换对规模较小**，13 个 bug 的绝对数量也少，统计效力有限
- **只覆盖 7 种重构类型**，未覆盖的类型未知
- **针对 Python 与 Rope 重构工具**，其他语言与工具需单独验证
- **未报告漏检率**。它发现了 13 个 bug 并被接受，但不能说明总共漏掉多少
- **12/13 的接受率依赖 issue tracker 记录**，项目维护者的接受标准各不相同
