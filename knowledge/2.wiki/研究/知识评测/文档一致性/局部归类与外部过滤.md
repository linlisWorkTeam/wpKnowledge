# 局部归类与外部过滤：避免把抽象间隙判成文档错误

代码-文档不一致检测里误报率的实测上限，以及把误报从 98% 压到 14% 的具体做法。

论文：DocPrism: Multi-lingual Detection of Incorrectness Inconsistencies between Code and Documentation
标识：`2511.00215`
链接：[https://arxiv.org/abs/2511.00215](https://arxiv.org/abs/2511.00215)

## 要解决的问题

代码与文档不一致很常见，会导致开发者误解和软件缺陷。但检测这件事有一个被低估的困难：**文档与代码之间天然存在抽象层级的差距**。文档描述业务意图，代码描述实现细节，两者之间的空隙是正常的，不是错误。

论文指出，朴素使用 LLM 做这件事的后果是灾难性的：**超过 90% 的函数被标记为与文档不一致**。用标准提示词技术时，**标记率高达 98%**。

这意味着如果直接把 LLM 判定接进流水线，几乎每一张卡片都会被判为有问题。对四类结论而言，**UNDERSERVED 会吞掉 COVERED、OVERSTATED 和 DRIFT**。

## 方法核心

### 根因诊断

论文给出的原因很具体：**LLM 把高层文档与代码之间的自然间隙识别为「不完整」（incompleteness）类不一致**。

这个诊断区分了两类不同的东西：

- **不正确（incorrectness）不一致**：文档说了代码没做的事，或说错了做的事。这是真错误
- **不完整（incompleteness）不一致**：文档没提到代码的某些细节。这是抽象层级的正常结果

朴素提示词把后者大量误判为问题，导致标记率虚高。

### LCEF：局部归类、外部过滤

论文提出 **Local Categorization, External Filtering（LCEF）** 方法论。核心设计是：

> 使用 LLM 的**局部补全能力**，而非它的**长程推理能力**，来专注报告不正确类不一致。

这个转换很关键。让模型做「通读文档与代码，判断是否一致」这种长程推理任务时，模型会自由联想、扩大判定范围。改成局部补全式任务后，判定范围被任务形态本身约束住了。

**对本项目的含义**：判据不该设计成「这张卡片和这段代码一致吗」，而该设计成**具体可补全的局部任务**（例如「这段文档声称的参数默认值，能否在代码中补齐」）。任务形态决定了误报率。

## 关键数据

**消融实验（LCEF 对比标准提示词）**：

- 标记率：**98% → 14%**
- F1：**0.22 → 0.77**

**跨语言评测（Python、TypeScript、C++、Java）**：

- 标记率维持在 **17%**
- precision **0.63**（**零微调**，未做任何模型微调）

**真实不一致的下界**：论文在四种语言上建立了**保守下界**，显示**不一致错误存在于 11% 的代码-文档对中**。

**与 SOTA 的对比**：在既有合成数据集上 precision 相当，但在自建真实 Java 数据集上**大幅超过 SOTA**：

- DocPrism：**0.47~0.67**
- SOTA：**0.05~0.14**

这个对比本身说明了合成数据集与真实场景的差距有多大。SOTA 在真实数据上 precision 掉到 0.05，意味着**它报出的不一致里 95% 是假的**。

## 对本项目的启发

### 方案要点

**一、把 98% 这个数字当作默认判据的体检指标。**

在接入四类结论之前，先跑一次基线：用你现在的提示词对一批已知良好的卡片做检测。如果标记率接近 90% 以上，说明判据需要局部化改造，此时计算出的 UNDERSERVED 数量没有意义。

**二、11% 是真实不一致的下界，可以当作预期基线。**

论文的保守下界（四种语言均成立）说明：真实存在不一致的比例约在 11% 量级。如果你的流水线报出 60% 的卡片有问题，差距不在代码，在判据。

**三、任务形态比提示词内容更重要。**

LCEF 的收益来自把任务从「长程推理」改成「局部补全」。对本项目的直接做法：把「判断这张卡片是否准确描述代码」改成一组具体的局部核对任务，例如「卡片声称的输入校验规则，逐条在代码中找对应实现」。

**四、precision 0.63 是零微调能达到的现实水平。**

这是跨四语言的实测值。它意味着接近 **37% 的报告是误报**。这个量级决定了四类结论**只能用于人工评审的输入**，不能直接驱动自动修复。这与项目 `Evaluation.md` 的既有边界一致。

**五、不完整类与本项目的 UNDERSERVED 不是同一件事。**

论文区分的不正确与不完整，在本项目里有对应关系但不等同：

- 不正确不一致 → OVERSTATED 或 DRIFT
- 不完整不一致 → 可能是 UNDERSERVED，也可能是正常的抽象省略

**不能把「文档没提到某个实现细节」直接判为 UNDERSERVED**，否则会把抽象层级的正常结果算成遗漏。判定 UNDERSERVED 应当用「行为改动是否被记录」这个可枚举的口径，而不是「文档是否覆盖了所有代码细节」。

### 与四类结论的映射

| 论文概念 | 本项目对应 | 注意 |
|---|---|---|
| 不正确不一致 | OVERSTATED / DRIFT | 主判定目标 |
| 不完整不一致 | 部分 UNDERSERVED | 需用改动清单区分正常省略与真遗漏 |
| 标记率 | UNDERSERVED 的虚高程度 | 接入前先体检 |

## 局限

- **precision 0.63 仍然不够高**。论文明确指出这是零微调的结果，隐含微调可改善，但未给出微调后的数字
- **11% 是保守下界**，不是精确比例。真实不一致率可能更高，论文只证明「至少这么多」
- **多语言评测覆盖四种语言**，对项目使用的语言需自行验证
- **论文聚焦不正确类不一致**，对完整性判定没有给出方案。本项目的覆盖率问题需要另找依据（见「文档-代码等价与完整覆盖」与「差分测试暴露行为差异」）
- **局部补全任务的构造需要领域知识**。论文没有给出通用的任务生成方法，对本项目而言这部分需要自行设计
