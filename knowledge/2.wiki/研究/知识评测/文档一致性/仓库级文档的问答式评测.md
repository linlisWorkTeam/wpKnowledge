# 仓库级文档的问答式评测

用功能检测、定位、补全三项问答任务代替直接打分。

论文：Evaluating Repository-level Software Documentation via Question Answering and Feature-Driven Development
标识：`2604.06793`
链接：[https://arxiv.org/abs/2604.06793](https://arxiv.org/abs/2604.06793)

## 要解决的问题

论文指出大模型已把文档生成从代码片段推进到整个仓库，但**现有基准有两个关键局限**：

1. **缺乏整体的、仓库级的评估**
2. **依赖不可靠的评测策略**，例如 **LLM-as-a-judge，它受困于标准模糊与有限的仓库级知识**

第二条对本项目直接相关：如果你打算用模型给卡片打分，会遇到同样的问题（判据模糊、缺乏仓库上下文）。

## 方法核心

### SWD-Bench

论文提出 **SWD-Bench**，一个**仓库级软件文档基准**。

### 核心设计：不直接打分，而是考下游能力

论文的评测策略受**文档驱动开发（documentation-driven development）**启发：

> 我们的策略通过**评估 LLM 使用文档来理解和实现功能的能力**来评价文档质量，而非直接给它打分。

这是一个**能力导向**而非**打分导向**的评测设计。具体通过**功能驱动的问答（function-driven QA）**任务衡量。

### 三项互联的问答任务

| 任务 | 目的 | 对应文档质量维度 |
|---|---|---|
| **功能检测（Functionality Detection）** | 判断某个功能是否被文档描述 | 覆盖的有无 |
| **功能定位（Functionality Localization）** | 评估定位相关文件的准确性 | 描述的精确性 |
| **功能补全（Functionality Completion）** | 衡量实现细节描述的全面性 | 描述的完整性 |

这三项任务与你的三个子问题有清晰的映射关系（见下）。

### 基准构造

论文**挖掘高质量的 Pull Request**，并用**仓库级上下文**富化，构建了**含 4170 个条目**的基准。

## 关键数据

| 指标 | 数值 |
|---|---|
| 基准规模 | **4170 个条目** |
| 文档对下游任务的提升 | 最佳方法的文档使 SWE-Agent 的**问题解决率提升 20.00%** |
| 实验发现 | 当前文档生成方法存在局限；**源代码提供互补价值** |

「源代码提供互补价值」这一条是重要发现：它说明**文档无法完全替代代码**，两者是互补关系。这为「文档该记录什么、不必记录什么」提供了一条依据。

## 对本项目的启发

### 方案要点

**一、三项 QA 任务与你的三个子问题几乎同构。**

这个映射关系值得单独列出：

| SWD-Bench 任务 | 本项目子问题 | 判定内容 |
|---|---|---|
| **功能检测** | 覆盖率（有无） | 某个功能是否被记录 |
| **功能定位** | 语义相似度 / 对应关系 | 描述是否指向正确的模块 |
| **功能补全** | 事实一致性 | 实现细节是否描述全面 |

**这意味着你可以用同一套问答任务同时评估三个环节**，而不必为每个环节单独设计评测。

**二、用下游能力代替打分，绕开了 LLM-as-a-judge 的不可靠。**

论文明确批评 LLM-as-a-judge 的标准模糊与仓库级知识不足。替代方案是**让模型用文档去完成任务，看任务成功率**。

对本项目的含义：评估知识卡片质量时，可以设计一个**依赖卡片的实际任务**（例如「根据卡片回答这个模块的行为问题」或「根据卡片完成一次代码修改」），用任务成功率作为卡片质量的代理指标。

**这个设计的优势**：任务成功率是客观的，不受判据模糊影响；而且它衡量的是**卡片有没有用**，而不只是**卡片写得对不对**。

**三、20.00% 这个数字说明文档质量的影响是可测的。**

最佳方法的文档使 SWE-Agent 问题解决率提升 20 个百分点。这给出一条间接的评估路径：**如果卡片改善了，依赖它的下游任务指标应当有可测的提升**。

项目已有评测体系，可以把这项指标接进去作为外部验证。

**四、4170 个条目的构造方式可以复用。**

论文的做法是**挖掘高质量 Pull Request** 并用**仓库级上下文**富化。对本项目的直接启示：

- 真实的 Git Diff（来自高质量提交）是构建评测集的自然来源
- 需要补充**仓库级上下文**，而不只是 diff 本身

第二点尤其重要：只给 diff 的评测会低估难度，因为真实判断需要仓库上下文。

**五、「源代码提供互补价值」界定了文档的边界。**

论文发现源代码对文档有互补价值，即**拥有文档不等于不需要源代码**。反过来说：**文档不必试图完整复现代码**。

这为 UNDERSERVED 的判定提供了一个重要约束：**不能把「代码里有但文档没写的实现细节」都算作遗漏**。文档的职责是描述行为与意图，不是逐行转录代码。

这与 DocPrism 的发现一致（把抽象间隙当不完整会导致 98% 的误报率）。

### 与本项目评测设计的结合

| 层次 | 手段 | 优点 | 局限 |
|---|---|---|---|
| 直接打分 | LLM-as-a-judge | 简单 | 判据模糊，仓库知识不足 |
| **下游能力** | **问答或任务成功率** | **客观，衡量实用性** | **间接，需要任务设计** |
| 判据核对 | 四类结论与锚点核对 | 可定位 | 需要锚点抽取能力 |
| 人工评审 | 提交给独立评审者 | 最可靠 | 成本高 |

**建议组合**：用判据核对做日常诊断，用下游能力做周期性验证，用人工评审做基准校准。

## 局限

- **评测的是仓库级文档整体**，不是单张卡片。粒度不匹配，需要改造才能用于卡片级评估
- **三项 QA 任务的构造需要人工设计**，论文未给出自动生成任务的方法
- **4170 个条目来自高质量 Pull Request**，可能偏向文档规范的项目，分布与实际项目有差异
- **问题解决率提升 20.00% 是单点数值**，未给出波动范围或统计显著性
- **下游任务用 SWE-Agent**，受该 Agent 自身能力影响，结论的通用性需验证
- **未报告人工评估与自动指标的相关性**，无法判断这些指标能否替代人工判断
- **论文未给出各文档生成方法的具体分数对比**，只给出最佳方法的下游收益
