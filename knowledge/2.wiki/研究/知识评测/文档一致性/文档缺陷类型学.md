# 文档缺陷类型学

从 101 个真实缺陷归纳出的文档债务类型分布，以及两种缓解方案。

论文：Towards identifying and minimizing customer-facing documentation debt
标识：`2402.11048`
链接：[https://arxiv.org/abs/2402.11048](https://arxiv.org/abs/2402.11048)

## 要解决的问题

论文从现实压力出发：

> 软件文档常常难以跟上软件演化的步伐。**缺乏正确、完整和最新的文档**导致文档缺陷数量增加，可能给软件系统集成带来延迟。

研究基于此前的发现：**与文档相关的缺陷贡献了大量 bug 报告**（该发现来自一个叫 MultiDimEr 的 bug 分析工具研究）。

论文的两个目标：

1. **识别造成文档缺陷的缺陷类型**，从而定位文档债务
2. **寻找务实的解决方案**来最小化最常见的文档缺陷

## 方法核心

论文调查了一个**工业软件系统**中与文档相关的缺陷：

1. 考察**不同的文档类型**及其关联的 bug 报告
2. 按**既有文档缺陷分类法（taxonomy）**对缺陷归类
3. 基于 **101 个缺陷**的样本分析

### 提出的两种方案

论文建议采用两个主要方案来应对文档债务：

**(i) 动态文档生成（Dynamic Documentation Generation, DDG）**

**(ii) 自动化文档测试（Automated Documentation Testing, ADT）**

两者都基于一个共同前提：**为文档定义单一且稳健的信息源**。

这个共同前提是关键：两个方案的分野落在「生成还是测试」上，但两者都要求**先确立一个权威信息源**。

论文也点出了债务难免的现实：

> 实践中，文档债务很容易**不被发现**，因为大量资源与关注被投入到交付高质量软件上。

## 关键数据

### 缺陷类型分布（101 个缺陷样本）

**大类**：大多数缺陷属于**信息内容（Information Content，即「What」）类别**，共 **86 个**。

**该类别内的三种主要缺陷类型**：

| 缺陷类型 | 数量 |
|---|---|
| **缺失文档（Missing documentation）** | **35** |
| **错误代码示例（Erroneous code examples）** | **23** |
| **内容过时（Outdated content）** | **19** |

（三项合计 77，其余 9 个分散在其他类型中。）

### 分布的三条解读

**第一，信息内容类占绝对多数**（86/101）。这说明文档缺陷主要是**内容问题**，而非格式、结构或组织问题。

**第二，缺失最多**（35）。文档没写，是最主要的缺陷形态。

**第三，错误示例与内容过时接近**（23 与 19）。两者合计 42，与缺失相当。

## 对本项目的启发

### 方案要点

**一、三种类型与本项目的三类结论一一对应。**

这是本条最直接的用处，它给四类结论提供了**真实世界的分布依据**：

| 论文的缺陷类型 | 本项目对应 | 占比参照 |
|---|---|---|
| 缺失文档（35） | **UNDERSERVED** | 最多 |
| 内容过时（19） | **DRIFT** | 次之 |
| 错误代码示例（23） | **OVERSTATED**（的一种具体形态） | 与过时接近 |

这个对应关系说明四类划分**有真实缺陷分布作为依据**，而非凭空设计。

**二、缺失最多，说明 UNDERSERVED 应当是重点。**

在 101 个缺陷中缺失类占 35（约 35%）。对本项目的含义：如果判定资源有限，**优先投入在漏覆盖检测上**，因为这是真实世界最常见的文档问题。

同时这也意味着 UNDERSERVED 的假阳性代价最高：它是最常报的一类，误报会被放大。

**三、错误代码示例是一种具体的 OVERSTATED 形态。**

论文把「错误代码示例」单列为一类，这个分类很有用。它提醒「文档说的和代码不一致」有多种形态：

- 文字描述错误（说错了行为）
- **示例代码错误**（示例跑不通或行为不符）

第二种在本项目里对应卡片中可能包含的用法示例。**示例是否可运行是一个可确定性验证的判据**，比判断自然语言描述准确得多。

**四、「定义单一且稳健的信息源」是两种方案的共同前提。**

论文的两种缓解方案（动态生成与自动化测试）都基于**为文档定义单一且稳健的信息源**。

这个前提对本项目**尚不成立**。当前的形态是：Git Diff 与知识卡片各自独立存在，没有一处被指定为权威源。这意味着：

- 出现冲突时，无法判定谁对
- 自动化测试没有可对照的基准

**对项目的含义**：在引入任何检测机制之前，需要先明确「代码是唯一权威源」这一立场。这实际上已经隐含在四类结论的设计里（OVERSTATED 和 DRIFT 都以代码为准），但**没有显式声明**。

**五、「文档债务容易不被发现」这个观察值得纳入设计。**

论文指出债务难以发现的原因是**资源和关注都投入在交付高质量软件上**。对本项目的含义：检测机制必须是**自动触发且低成本的**，否则会因为「没人在看」而形同虚设。

这支持把检测绑定到 Git Diff 事件上（你现有的设计），而不是让它依赖人工主动发起。

**六、自动化文档测试（ADT）是两条候选路线中更轻的。**

论文并列了动态生成与自动化测试。结合其他调研（`2406.14836` 的文档测试结论），**ADT 路线更值得本项目优先考虑**，因为它能给出可执行判定，而非文本相似度。

## 与本项目分类设计的对照

| 论文的缺陷大类 | 本项目应如何判定 |
|---|---|
| 缺失文档 | 用可枚举的改动清单核对（见覆盖率相关文档） |
| 内容过时 | 需要版本对比证据 |
| 错误代码示例 | **可确定性验证**（示例能否运行） |

第三行是唯一可以完全确定化的一类，值得单独设计。

## 局限

- **单一工业系统、101 个缺陷样本**，规模有限，分布比例可能有系统特性
- **论文是「迈向（towards）」性质的初步研究**，方案（DDG 与 ADT）是**建议**，未报告实施后的效果数据
- **场景是面向客户（customer-facing）的文档**，与本项目的内部技术卡片有差异。客户文档更强调可用性，内部卡片更强调准确性
- **未给出缺陷的严重性分级**，35 个缺失文档不代表它们同等重要
- **「既有文档缺陷分类法」的具体来源与适用性**需查原文确认
- **两项缓解方案的效果对比未提供**，无法判断应优先采用哪一个
