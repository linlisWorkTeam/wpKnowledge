# 无参考的评审质量指标

把质量评价锚定到代码声明与坏味，而非与参考答案比字面相似。

论文：CRScore: Grounding Automated Evaluation of Code Review Comments in Code Claims and Smells
标识：`2409.19801`
链接：[https://arxiv.org/abs/2409.19801](https://arxiv.org/abs/2409.19801)

## 要解决的问题

自动化代码评审近年受到很多关注，但**当前评审评论的评价指标依赖与人类撰写的参考答案做比较**。

论文指出的根本问题在于任务形状：

> 代码评审是一个**一对多问题**，就像生成和摘要一样，**一个 diff 存在许多「有效评审」**。

这个观察直接否定了「与标准答案比相似度」的评价方式：如果正确答案不唯一，那么「和参考答案像不像」衡量的就不是质量。

**这与你 Q5 的核心担忧是同一个问题**：如何避免模型仅凭关键词相似度做判断。

## 方法核心

### CRScore：无参考指标

论文开发了 **CRScore**，一个**无参考（reference-free）指标**，衡量评审质量的多个维度：**简洁性、全面性、相关性**。

（注：论文摘要的表述是「**conciseness**、**comprehensiveness**、**relevance**」，与后文提到的「覆盖度」是同一组维度的不同表述，具体维度命名以原文为准。）

### 关键设计：锚定到代码声明与坏味

CRScore 的评价方式有一个明确的设计选择：

> 我们设计 CRScore 以**锚定在由 LLM 和静态分析器检测到的代码声明（claims）与潜在问题**上来评价评审。

**「由 LLM 和静态分析器检测」**这一点很重要：锚点来自**从代码中可检测的信号**，而非人写的参考答案。这让评价有了客观落点：

- 评审是否提到了代码中**真实存在的问题**
- 评审的断言是否有**代码中的依据**

### 配套数据集

论文发布了 **2.9k 条人工标注的评审质量分数**语料，覆盖机器生成与 GitHub 真实评审评论。

## 关键数据

| 指标 | 数值 |
|---|---|
| 与人类判断的相关性 | **0.54 Spearman**（所有开源指标中最高） |
| 敏感性对比 | **比基于参考的指标更敏感** |
| 标注语料规模 | **2.9k** 条人工标注评审质量分数 |

「最高」的限定范围是**开源指标**，论文未声称超过所有闭源或商用方案。

「更敏感」的含义是：在质量差异较小的两组之间，无参考指标能区分出差异，而基于参考的指标不能。

## 对本项目的启发

### 方案要点

**一、卡片质量评价不该与标准答案比相似度。**

这是本条最直接的含义。如果你打算用「生成的卡片与某份人工撰写的理想卡片对比」来评分，会遇到与代码评审同样的问题：**同一段改动可以有许多张都正确的卡片**。

0.54 Spearman 是与人类判断的相关性上限参照。它说明这类自动指标**能反映趋势但不精确**，适合做诊断，不适合做发布依据。这与项目 `Evaluation.md` 的既有边界一致。

**二、「锚定到代码声明与坏味」是本项目 Q5 的直接解法。**

把这条设计原则翻译到知识卡片：

| CRScore 的锚点 | 本项目的锚点 |
|---|---|
| 代码中被检测到的声明（claims） | 代码中的行为、接口、分支 |
| 静态分析器发现的坏味 | 静态分析发现的结构异常 |
| LLM 检测到的潜在问题 | 模型识别的可疑改动 |

判定一张卡片时，问题应当是「**它的声明能否在这些锚点上找到对应**」，而不是「它和一参考文档有多像」。

**三、这同时是反捷径信号的手段。**

`2608.00884`（见「文档相似度」专题）已证明模型可能抓捷径信号，即不看文档也能判对。基于相似度的评价会被这类捷径欺骗（因为卡片与参考答案的词汇重合度高不代表它准确）。

锚定到代码信号的评价天然免疫这个问题：**锚点在代码里，不在文本里**。

**四、三个维度可以借用到卡片评分。**

简洁性、全面性、相关性这三个维度对知识卡片同样适用。其中「全面性」对应覆盖率的定性面，「相关性」对应卡片是否聚焦于本次改动。

**五、2.9k 条标注语料是构评测集的规格参照。**

如果你的项目要做卡片质量的人工标注，这个规模（约 2900 条）是一个可参照的量级。同时它覆盖了**机器生成与真实评论**两类来源，这个混合设计值得借鉴：只用机器生成样本会遗漏真实场景的分布。

### 与四类结论的映射

| 结论 | CRScore 式锚点 | 判定问题 |
|---|---|---|
| COVERED | 代码改动活动 + 卡片声明 | 每条活动的声明是否都在卡片中 |
| UNDERSERVED | 代码改动活动 | 哪些活动在卡片中找不到声明 |
| OVERSTATED | 代码中的存在性 | 卡片声明能否在代码中找到对应 |
| DRIFT | 跨版本代码 + 卡片声明 | 声明对应的代码是否已改变 |

**四类结论都可以表达为「锚点是否存在」的查询**，而不需要文本相似度计算。

### 一个可落地的实现顺序

1. 定义锚点类型（改动活动、符号、分支、接口）
2. 用确定性手段抽取锚点（解析器 + 静态分析）
3. 把卡片拆成声明清单
4. 做锚点与声明的匹配查询（允许「无法匹配」）
5. 对无法自动匹配的部分才调用模型

**这个顺序把模型调用限制在无法规则化的部分**，成本远低于「整张卡片丢给模型打分」。

## 局限

- **0.54 Spearman 是中等相关**，不是高相关。这个指标能反映趋势，不能作为精确评分使用
- **「所有开源指标中最高」的对比范围限于开源方案**，与闭源或商用指标的对比未提供
- **论文的任务是评审评论质量**，与本项目的卡片质量有差异：评审评论是「针对一个 diff 的一段话」，卡片是「描述模块行为的结构化文档」
- **锚点依赖 LLM 与静态分析器的检测结果**，如果这两者漏检，评价也会失真
- **2.9k 标注语料的标注者数量与一致性**未在摘要中说明
- **摘要未给出维度的具体计算方式**，无参考指标如何实现需要查原文
