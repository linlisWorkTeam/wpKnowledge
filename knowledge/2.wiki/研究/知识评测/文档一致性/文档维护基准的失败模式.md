# 文档维护基准的失败模式

文档生成与维护任务的真实失败分布，以及必须计入「正确弃权」的设计。

论文：DoGBench: Can Agents Meet Expert Standards for User-Facing Documentation?
标识：`2609.39909`
链接：[https://arxiv.org/abs/2609.39909](https://arxiv.org/abs/2609.39909)

## 要解决的问题

论文提出 **DoGBench（Documentation Generation Benchmark）**，声称是**首个面向真实用户文档的生成与维护基准**。

它问的问题很直接：**一个 Agent 能否产出有经验的技术写作者在评审中会接受的文档？**

这个问题的形状与本项目高度一致：都是让自动化系统产出文档，并需要专业标准来判定是否可接受。

## 方法核心

### 任务设计

基准包含 **292 个条目**，来自开源项目（论文列举 Helm、PostHog、Mautic）。

每个条目给 Agent：

- **一个改动前的仓库**
- **一个触发条件**，例如一个代码 Pull Request，或一份被报告的文档缺口

Agent 必须完成两步：

1. **先判断这份文档是否需要更新**
2. **需要更新的**：必须**一次尝试**就产出可接受的补丁
3. **不需要更新的**：必须**弃权（abstain）**

### 评分设计

**任务专属的评分标准（rubric）**，经**项目维护者验证**，从五个维度评分：**准确性、完整性、读者引导、位置、仓库惯例**。

**综合分**结合**补丁质量**与**正确弃权**，100 分表示 Agent 满足该任务的全部要求。

论文还给了一条明确的声明：**分数不应被解读为专家能力的百分比。**

## 关键数据

### 总体表现

- 评测了 **7 个 Agent**
- 最高分 Agent 在 **117 项留出集**上得 **47.3 / 100**

### 失败模式分布（审计 1267 个补丁）

| 失败模式 | 占比 |
|---|---|
| 任务完成缺口（task-completion gaps） | **45.5%** |
| 技术不准确（technical inaccuracies） | **36.6%** |
| 概念或参考覆盖不全（incomplete conceptual/reference coverage） | **32.5%** |

（注：多项可以同时出现，故合计超过 100%。）

### 三种轨迹模式（与上表失败相关）

| 轨迹模式 | 占比 |
|---|---|
| 只描述接口，**不考察读者如何使用它** | **36.0%** |
| **缺失决定性证据，用看似合理的假设填补空白** | **33.1%** |
| **找到第一个可行的文档面就停下**，让其他受影响的页面继续陈旧 | **30.1%** |

## 对本项目的启发

### 方案要点

**一、第 3 种轨迹模式就是 UNDERSERVED 的生成机制。**

「找到第一个可行的文档面就停下，其他受影响的页面继续陈旧」（30.1%）精确描述了本项目 UNDERSERVED 的成因：**一次代码改动往往影响多张卡片，而生成过程满足于第一处命中**。

这给出一个可直接落地的指标：**卡片波及率**（被更新的卡片数 / 受该改动影响的卡片数）。它独立于「改动覆盖率」，专门衡量这种「停得太早」的失败。

**二、必须把「正确弃权」计入评分。**

DoGBench 要求不需要更新的条目上 Agent **必须弃权**，并把正确弃权算进综合分。

对本项目的直接含义：**COVERED 的定位是需要被验证的正确输出，而非「什么都不做」**。如果流水线只统计「发现了多少问题」，就会激励系统多报问题，而正确的 COVERED 判定得不到任何反馈。

**三、失败模式要分类计数，不要只报总准确率。**

45.5% / 36.6% / 32.5% 这组分布比一个总分有用得多，因为它直接指向不同的修复方向：

| 失败模式 | 本项目对应 | 修复方向 |
|---|---|---|
| 任务完成缺口 | 卡片没做完该做的事 | 完善生成流程 |
| 技术不准确 | OVERSTATED 或 DRIFT | 一致性检测 |
| 覆盖不全 | UNDERSERVED | 覆盖率分析 |

**四、47.3/100 这个分数要正确解读。**

论文明确说分数**不等于专家能力的百分比**。这提醒一点：在向他人报告自动化系统的质量时，不要用「达到专家水平的 X%」这类表述。这个分数反映的是**在任务专属评分标准下的达标程度**。

**五、五个评分维度可以借鉴。**

准确性、完整性、读者引导、位置、仓库惯例。后两项尤其重要：它们说明文档质量不只看「说对没有」，还包括**放在哪里**和**是否符合仓库惯例**。

对本项目的含义：知识卡片的放置位置（哪张卡片该记这条改动）是一个真实的质量维度，而它对应的正是 Q2 的对应关系问题。

**六、一次尝试的限制是必要的。**

论文规定需要更新的条目必须**一次尝试**就产出可接受补丁。这避免了对同一任务反复尝试造成的评估失真。

对本项目的含义：如果卡片生成允许重试，评估时要固定重试预算，且不能按「最终最好结果」评分。

### 与本项目设计的直接对应

| DoGBench 的设计 | 本项目可借鉴 |
|---|---|
| 先判断是否需要更新 | 先判 COVERED，而非默认判定问题 |
|---|---|
| 不需要更新必须弃权 | COVERED 需要正向证据 |
| 综合分含正确弃权 | 评分函数不能只奖励发现问题 |
| 任务专属评分标准 | 不同改动类型的判据可以不同 |
| 维护者验证的 rubric | 判据应经人工确认，不自行设定 |
| 分数不等于能力百分比 | 报告时的表述纪律 |

## 局限

- **最高分只有 47.3/100**，说明这个基准目前没有方法接近达标，也因此难以区分方法间的细微差异（可能都在低分区间）
- **基准面向用户可见文档**（user-facing documentation，如 Helm、PostHog、Mautic 的文档），与本项目的内部技术知识卡片有差异。读者、惯例与评价标准都不完全一致
- **292 个条目、117 项留出集**，规模中等，跨项目泛化性有限
- **失败模式的百分比是审计 1267 个补丁的结果**，与 292 个条目不是同一批数据，两者关系需查原文确认
- **论文未给出各 Agent 的分项得分**，无法判断失败模式在不同 Agent 间的差异
- **未提供「正确弃权率」的单独数值**。这是本项目最关心的一项，但摘要中只提到它计入综合分
