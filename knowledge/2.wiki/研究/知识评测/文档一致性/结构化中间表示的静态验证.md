# 结构化中间表示的静态验证

不让模型直接对照冗长自然语言规格验证代码，而是先抽取可验证规则。

论文：LLM-Based Static Verification of Code Against Natural-Language Requirements: An Industrial Experience Report
标识：`2605.17926`
链接：[https://arxiv.org/abs/2605.17926](https://arxiv.org/abs/2605.17926)

## 要解决的问题

论文开篇指出一个被忽视的不对称：大模型被大量用于生成需求规格、设计文档、代码和测试用例，但**一个更难的问题受到的关注少得多**，即**静态验证已实现的代码是否满足用自然语言写成的需求**。

传统静态分析工具的边界被论文说得很清楚：

> 传统静态分析工具在检测编码缺陷和已知漏洞模式上有效，但**无法判断程序行为是否匹配预期的业务逻辑**。检测这类缺陷**需要在规格上推理，而非仅靠代码**。

软件测试能暴露部分不匹配，但效果**严重依赖测试设计、可执行工件与运行时环境**。

这正是本项目 Q4 的核心困境：Git Diff 提供的证据往往不足以判定 OVERSTATED 与 DRIFT，那么能否用当前完整代码、静态分析或测试来补？

## 方法核心

论文给出一个**两阶段 LLM 工作流**，场景是智能网联汽车的网络安全案例。

### 阶段一：AI 规则挖掘器

从自然语言需求中**提取可验证规则**，同时**显式识别模糊（ambiguity）、自相矛盾（self-contradiction）和其他不可验证的陈述**。

### 阶段二：AI 代码审计器

对照阶段一提取出的规则，检查实现证据。

### 关键设计决策

论文明确说明了为什么要分两阶段，这是全文最有价值的一句：

> 与其让**单个 LLM 直接对照冗长的自然语言规格来验证代码**，该工作流引入一个**结构化中间表示**，以减少幻觉、输出变异性、有限可解释性和上下文丢失。

四个被点名的问题（幻觉、输出变异、可解释性不足、上下文丢失）都是直接把长规格喂给模型的已知病症。

### 定位

论文把自己的方法定位为**需求感知与语义感知形式的静态分析**，作为软件测试的**补充**。它有一个重要的能力边界优势：

> 通过分析需求和源代码，**不要求编译、执行或运行时环境**，该方法把验证与确认活动在开发生命周期中左移。

论文还指出，这种基于 LLM 的静态分析**也是解决测试 oracle 问题的一种新方法**。

## 关键数据

这是一篇**工业经验报告**，因此数字少于实验论文。可确认的事实：

- 应用场景：智能网联汽车网络安全案例研究
- 两阶段结构：规则挖掘 + 代码审计
- 中间产物：结构化中间表示
- 运行条件：**不需要编译、执行或运行时环境**
- 定位：需求感知的静态分析，测试 oracle 问题的新解法

## 对本项目的启发

### 方案要点

**一、把「不可验证的陈述」作为显式的输出类别。**

这是本条最重要的可落地设计。阶段一在提取规则时**同时标注模糊、自相矛盾和其他不可验证的陈述**。含义是：判定流水线应当允许输出**第五类结论：无法判定**。

缺了这一类，四种结论的准确性会被不可验证的陈述污染。因为模型面对「这条卡片说系统性能良好」这类陈述时，只能强行归入某一类，产生噪音。

这与「知识关联」专题已确立的原则一致：关联输出必须允许「无法关联」。

**二、不要让模型直接对照长规格。**

论文的设计理由直接适用于本项目：不要用单个模型（或单次调用）同时处理「读 diff + 读卡片 + 判断四类结论」。应当先构造**结构化中间表示**，再在表示层做对照。

对本项目的具体做法：

| 输入 | 结构化产物 | 用途 |
|---|---|---|
| Git Diff | 带类型的改动活动清单 | 覆盖率分母、UNDERSERVED 候选 |
| 知识卡片 | 原子事实声明清单 | OVERSTATED 与 DRIFT 的核对对象 |

两张清单做对照，比「模型读两边做判断」可解释得多。

**三、静态分析的定位是证据提供者，不是判定者。**

论文明确说静态分析**不能**判断行为是否匹配业务逻辑。所以在本项目的四类结论里，静态分析不能单独支撑任何一类判定，它的角色是**提供实现证据**（存在性、引用关系、调用路径）。

**四、不需要运行环境这一点对本项目是实质优势。**

论文强调该方法不要求编译或执行。这意味着它可以在**提交时立即运行**，而不必等测试环境就绪。对「每次 Git Diff 增量生成卡片」的流水线而言，这个特性直接决定能否做前置拦截。

**五、这条路线补的正是测试覆盖不到的部分。**

论文指出测试能暴露部分不匹配，但依赖测试设计与运行环境。而需求感知的静态分析覆盖的是**测试没写到的行为**。两者是互补关系：测试管已覆盖路径，规格推理管未覆盖路径。

### 与四类结论的映射

| 阶段产物 | 支撑的结论 | 理由 |
|---|---|---|
| 可验证规则 | OVERSTATED | 规则可逐条在代码中查证存在性 |
| 不可验证陈述 | **第五类：无法判定** | 需显式标出，不参与四类判定 |
| 实现证据 | DRIFT | 证据须来自版本对比，静态分析提供当前证据 |
| 规则与实现的差集 | UNDERSERVED | 前提是规则集合可枚举 |

### 一个需要确认的落地前提

论文是工业经验报告，**未公开实现代码与结构化中间表示的格式**。所以「结构化中间表示怎么设计」需要自行确定。可参照的方向见「知识关联」专题的符号锚定级联策略。

## 局限

- **这是经验报告，没有受控实验与量化指标**。因此无法给出可对照的准确率数字，也无法验证方法在其他领域的泛化性
- **单案例研究**（智能网联汽车网络安全），领域特性强，需求本身有较高的规整度
- **未公开实现**，中间表示格式与提示词设计需要自行推导
- **「不可验证陈述」的识别准确率未知**。阶段一识别模糊与自相矛盾的能力没有量化，如果这一步漏判，下游会出现强行归类
- **不要求编译执行是优势也是限制**：没有执行证据，行为层面的判定仍可能不准
- **论文未讨论成本**。两阶段意味着至少两次模型调用，长规格的 token 消耗未说明
