# 异构追溯图与知识图谱

用显式关联图替代相似度配对，以及从 Pull Request 增量构建知识图谱的做法。

论文一：TraceDev: A Traceability-Driven Multi-agent Framework for Requirement-to-Code Development
标识：`2607.18886`
链接：[https://arxiv.org/abs/2607.18886](https://arxiv.org/abs/2607.18886)

论文二：CODENS: Transforming Code Changes into Living, Accessible, and Queryable Documentation
标识：`2607.18356`
链接：[https://arxiv.org/abs/2607.18356](https://arxiv.org/abs/2607.18356)

## 要解决的问题

两篇论文处理同一个结构性问题：**自然语言描述与代码工件之间的对应关系如何建立和维护**。

TraceDev 的诊断：现有方法依赖简化指令（例如单句描述），无法反映复杂软件开发场景；更关键的是**缺乏显式的需求追溯机制**，导致**难以将生成代码与原始需求精确对齐和验证**。

CODENS 的诊断：在快速迭代的仓库里维护最新文档很难，因为**设计知识散落在源文件与 Pull Request 中**。

## 方法核心

### TraceDev：异构追溯图作为协同面

TraceDev 是一个**多智能体框架**，包含五个角色：需求精化者、设计者、开发者、测试者、验证者。

核心在**验证者 Agent**：

> 构建并维护一个**异构追溯图（heterogeneous traceability graph）**，连接**需求、设计模型与代码工件**，用于与前四个 Agent 交互。

这个图的三个用途：

1. **维护跨工件的一致性**
2. 作为**结构化上下文**用于**高效记忆管理**
3. 支撑**可靠的仓库级代码生成**

它的评测数据：两个广泛使用的数据集（含 **125 个用例**），对比两个最先进方法。

- ETOUR 数据集：成功率 **53.63%**，比基线**最高提升 186.63%**
- SMOS 数据集：成功率 **56.82%**，比基线**最高提升 340.80%**

### CODENS：从 Pull Request 增量构建类型化知识图谱

CODENS 的形态与本项目的增量知识生成**高度对应**。它的流程：

1. **从 Pull Request 增量构建类型化的软件知识图谱**
2. 通过 **schema 驱动的语义抽取**富化组件
3. 推导组件之间的**类型化关系**
4. 通过**三种检索模式**暴露知识，包括**智能体引导的图遍历**用于仓库级问答
5. **保留跨 Pull Request 的语义变更历史**
6. 集成**答案质量与运营两类评估指标**

评测场景：一个**生产环境的 Ruby on Rails 客户项目**。

结果：CODENS 产出的答案**高度相关且依据充分**；定性反馈指出**剩余挑战在于简洁的、面向文档的综述合成**。

## 对本项目的启发

### 方案要点

**一、卡片定位该靠图上的边，而不是相似度分数。**

这是两篇论文共同的核心含义。当前本项目的形态是「给定 diff 与卡片，判断是否一致」，隐含假设是**配对关系可以每次重新判断**。

TraceDev 与 CODENS 的做法说明：对应关系应当**显式建图并持续维护**。一对多与多对一在图上都是自然形态 —— 一条改动连向多张卡片，一张卡片被多条改动指向。

**二、CODENS 的「从 PR 增量构建」正是本项目的形态。**

CODENS 的输入单位是 Pull Request，本项目是 Git Diff（PR 是 Diff 的集合）。它的三步流程可以直接映射：

| CODENS 步骤 | 本项目对应 |
|---|---|
| 从 PR 增量构建知识图谱 | 从 Diff 增量更新卡片与关联图 |
| schema 驱动的语义抽取 | 从代码抽取行为声明 |
| 推导类型化关系 | 建立改动与卡片的对应边 |
| **保留跨 PR 语义变更历史** | **卡片版本历史** |
| 三种检索模式暴露知识 | 卡片检索与问答 |

第四行是**本项目目前缺失的一环**：CODENS **保留跨 PR 的语义变更历史**，这意味着「这条改动相对上次改了什么」可以在图里查到，而不需要重新推断。

**三、CODENS 在生产项目上验证过，这比实验室数据集更有参考价值。**

论文用的是**生产环境的 Ruby on Rails 客户项目**，并同时集成**答案质量与运营两类指标**。后者（运营指标）在本项目的语境里对应延迟、成本、更新频率这类工程指标，而不是只有准确率。

**四、TraceDev 的 53.63% 提醒要保守设定预期。**

即便建了显式追溯图并用五个专职 Agent，端到端成功率也只有约一半。所以对本项目的四类结论，应当预期**仍有相当比例需要人工接续**。

**五、验证者角色的位置值得借鉴。**

TraceDev 把「一致性维护」与「验证」放在**单独一个 Agent** 上，让它**同时承担图的维护与和前序 Agent 的交互**。这个设计说明一致性维护不该是流水线末端的一个检查点，而应当是**贯穿全程且在线的服务**。

**六、CODENS 未解决的问题恰是本项目要解决的部分。**

论文明确说剩余挑战是「**简洁的、面向文档的综述合成**」。这一条指向：从图谱到可读文档的转换仍不易。对本项目而言，这意味着卡片正文的生成质量与关联图质量是**两个独立的难点**，不能指望后者自动解决前者。

### 落地形态建议

| 层 | 内容 | 是否需要模型 |
|---|---|---|
| 图结构 | 节点（改动活动、卡片、符号）+ 边（覆盖、依据、冲突） | 否 |
| 图的增量维护 | 每次 Diff 后更新节点与边 | 部分 |
| 语义变更历史 | 每个节点的版本链 | 否 |
| 判定 | 在图上做覆盖与冲突查询 | 部分 |

关键点：**图结构与查询不需要模型**。模型只用于无法规则化的判定。

## 局限

**TraceDev**：

- **成功率绝对值低**（53.63% / 56.82%），未达到可自动化的水平
- **五个 Agent 的编排复杂度高**，本项目的目标之一是避免过度架构
- **场景是需求到代码生成**，与本项目的「代码改动到文档更新」方向相反（前者从头生成，后者修改已有）
- 论文未报告**图的规模、更新成本与一致性维护开销**
- 两个数据集各含 125 个用例，规模有限

**CODENS**：

- **单案例研究**（一个生产 Rails 项目），泛化性有限
- **定性反馈为主**，摘要中未给出量化的答案质量分与运营指标数值
- **明确存在未解决的合成问题**（简洁综述的生成）
- 论文未说明**图的更新成本**与随仓库增长的扩展性
- 检索模式包含智能体引导的图遍历，**成本未报告**
