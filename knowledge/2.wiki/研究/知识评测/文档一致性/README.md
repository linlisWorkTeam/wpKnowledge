# 文档一致性：四类结论的方法依据

本项目「文档相似度判断」环节的方法调研：从 Git Diff 识别真实行为变化、建立改动与知识卡片的对应、量化覆盖率、验证卡片声明、评估四类结论（COVERED / UNDERSERVED / OVERSTATED / DRIFT）的可靠性。

## 为什么单独立一题

「语义相似度与事实一致性」专题回答的是**通用方法层**（去重用什么、事实对齐用什么）。本专题回答的是**落地层**：给定一条 Git Diff、一份 Markdown 卡片、一次 LLM 调用，四类结论该怎么算出来。

两者的分工：

| 专题 | 回答的问题 | 输出 |
|---|---|---|
| 语义相似度与事实一致性 | 有哪些技术路线可用 | 方法清单与适用边界 |
| **文档一致性（本专题）** | 本项目的流水线该怎么接 | 每类结论的判据、证据来源与可靠性上限 |

## 先看结论

### 五条最重要的发现

**一、朴素提示词做一致性检测会把几乎所有卡片判为不一致。** `2511.00215` DocPrism 的实测：**超过 90% 的函数被标记为与文档不一致**，用标准提示词时标记率高达 **98%**。原因是模型把高层文档与代码之间的**自然抽象间隙**当成了「文档不完整」。改用局部补全能力（不让模型做长程推理）后，标记率降到 **14%**，F1 从 **0.22 升到 0.77**。跨四种语言的评测给出保守下界：**真实不一致只存在于 11% 的代码-文档对中**。

**这意味着 UNDERSERVED 的默认判据必须先校准，否则这个类别会淹没其他三类。**

**二、过滤重构不是可选项，它是假阳性的头号来源。** `2510.01960` RefFilter 明确指出，轻量静态分析做语义冲突检测**假阳性高的主因就是「行为保持的重构无法与影响行为的改动区分开」**。加入重构检测后**假阳性降低近 32%**，假阴性增加不显著。同时 `2508.11993` 给出分解上限的量化：现有重构检测器**只能识别 33.9%** 的行为保持改动。

**三、静态分析能判「有没有」，判不了「对不对」。** `2605.17926` 的工业经验报告把这条边界说得最清楚：传统静态分析擅长检测编码缺陷与已知漏洞模式，**但无法判断程序行为是否匹配预期业务逻辑**，因为这类缺陷「需要在规格上推理，而非仅靠代码」。它的方案是两阶段结构化中间表示：先挖可验证规则，再对照规则审计代码。

**四、覆盖率与一致性的分母都可以枚举，前提是先做结构化分解。** `2606.22247` 把「文档-代码等价」定义成一个可度量的性质（准确**且完整**），实测自动生成的等价文档只占 **53.4%**。`2607.16024` DiffTestGen 用 **union coverage**（新旧版本修改代码的合并覆盖）作指标，在 463 个 PR 上暴露行为差异的比例达 **78.2%**，平均 union coverage **90.7%**。

**五、四类结论的可靠性有实测上限，且误报分布不均。** `2511.19875` CommitEval 的同构任务（提交信息与代码变更不一致检测）实测：**Recall 85.95%、Precision 80.28%、Specificity 63.8%**。特异度只有 63.8% 意味着**约 1/3 的一致样本被误报**。`2609.39909` DoGBench 审计 1267 个补丁给出失败模式分布：任务完成缺口 **45.5%**、技术不准确 **36.6%**、概念或参考覆盖不全 **32.5%**。

## 一、代码变更理解：区分行为变更与非行为变更

### 为什么不能只让模型读 Diff

`2510.01960` RefFilter 点出根因：当前轻量静态分析技术**无法有效区分行为保持的重构与影响行为的改动**，这正是误报的主要来源。这个问题在纯模型路线上同样存在，`2508.11993` 的量化说明它有多难：现有重构检测器**只能识别 33.9%** 的行为保持改动，即便作者新增 67 个功能等价操作把覆盖率提升 128%，**仍有大量改动无法解释**。

### 三层做法

**第一层：重构检测前置（确定性，不依赖模型）**

先用重构检测器（如 RefactoringMiner 一类工具线）标出行为保持的改动并**从报告中剔除**。`2510.01960` 的实测收益：**假阳性降低近 32%**，代价是假阴性不显著增加。

这一层的产物有两重身份：既是过滤依据，也是覆盖率的**结构化改动清单**来源。

**第二层：模型在 diff 上判行为变更（有外部验证证据）**

`2608.09919` 用基础模型作 oracle **直接分析 git-style diff**，识别 Python 重构实现引入的行为变更。实测在 1152 次重构尝试、217 个变换对中找出 **13 个真 bug**，**全部提交给开发者，其中 12 个被接受**（有 issue tracker 证据）。这条证据链的价值在于它**不是自评**。

`2605.02096` 给出准确率量级：零样本提示、226 个真实 Java 重构 bug（跨 47 种重构类型、三个主流 IDE）上，**GPT-5.4 达 93.8%**，开源 **GPT-OSS-20B 达 80.5%**。论文同时做了蜕变测试，但**自己声明这只是鲁棒性证据，不能证明模型没有记忆或数据污染**。这条声明应当被继承。

**第三层：用差分测试验证「行为是否真的变了」**

`2607.16024` DiffTestGen 用静态调用图加项目文档识别**有效入口点**，引导模型抵达被改动的代码，并用 **union coverage** 反馈迭代。实测在 463 个 PR 上：**78.2% 的 PR 暴露了行为差异，平均 union coverage 90.7%**，比基线多暴露 99 个 PR，代码覆盖提升 12.5 与 15.6 个百分点。与回归检测器集成后**能发现现有最佳方法漏掉的回归 bug**。

**对本项目的含义**：第三层给出的是「这条改动是否值得文档更新」的**客观判据**，比让模型主观判断可靠。但它要求代码可执行且能生成测试，成本高于前两层。

### 可直接复用的判据

| 改动类型 | 判据来源 | 是否需更新文档 |
|---|---|---|
| 行为保持的重构 | 重构检测器 | 否，剔除 |
| 重命名（内部符号） | 重构检测器 / 调用图 | 否，但对外接口改名需 |
| 格式调整 | 语法树比较 | 否 |
| 行为差异（差分测试暴露） | DiffTestGen 式差分测试 | 是 |
| 新入口点或新分支 | 调用图静态分析 | 是 |

## 二、代码与文档的语义对齐

### 一对多、多对一是结构问题，不是相似度问题

`2603.16208` SoK 给出一张全局地图：**22 种工件类型、23 种关联**构成的追溯图，并指出研究严重偏向代码侧。它的两条诊断对本项目直接有用：追溯技术正转向深层语义模型，但**可复现性危机持续（仅 37% 的研究公开代码）**，且**95% 的工具仍停留在学术**。

`2409.19801` CRScore 明确点出这类任务的形状：**代码评审是「一对多」问题**，一个 diff 存在许多「有效结论」。所以用「最相似的那个」来配对本身就是错的建模方式。

### 三条可落地的路线

**路线一：异构追溯图（`2607.18886` TraceDev，`2607.18356` CODENS）**

TraceDev 用五个角色 Agent，其中验证者 Agent **构建并维护连接需求、设计模型与代码工件的异构追溯图**，该图既做一致性维护，也作为**结构化上下文**做高效记忆管理，支撑仓库级生成。

CODENS 的做法更贴近本项目：**从 Pull Request 增量构建类型化软件知识图谱**，经 schema 驱动的语义抽取富化组件、推导类型化关系，提供三种检索模式（含智能体引导的图遍历），并**保留跨 PR 的语义变更历史**。

**对本项目的含义**：卡片的定位不该靠「哪段代码最像这段文字」，而该靠**一张显式的关联图**。图的边就是「改动 ↔ 卡片」的对应关系，一对多与多对一都是图上的自然形态。

**路线二：结构化中间表示（`2605.17926`）**

这篇的工业经验是：**不要让单个模型直接对照冗长自然语言规格验证代码**，而要引入**结构化中间表示**来减少幻觉、输出变异、可解释性不足与上下文丢失。

**对本项目的含义**：Diff 不该原样喂给模型。先转成「带类型的改动清单」，再把清单与卡片声明做对照，这是可解释性的来源。

**路线三：把追溯嵌进代码库（`2603.13999` ReqToCode）**

ReqToCode 的诊断是：外部维护的追溯**会随需求、代码、测试各自独立演化而静默退化**，且基于 LLM 的追溯恢复是**事后补救（回顾式）**。它的做法是把可追溯元素**直接嵌入代码库**，使追溯成为**编译期可验证的属性**，并通过渐进生命周期（弃用警告 → 构建失败）给出可操作信号。

**对本项目的含义**：这条路线对本项目过重（需要改被测代码），但**它的诊断值得吸收**：只做事后比对而不留锚点，卡片会持续静默退化。可行的折中是让卡片记录**它所依据的符号与位置**，即使不侵入代码，也能在符号消失时立刻报警。

### 与既有工作的关系

「知识关联」专题已调研过符号锚定的级联策略（确定性优先、模型补长尾）。本专题的增量在于：**锚定要输出到一张图上，而不是输出到一组相似度分数上**。

## 三、变更覆盖率与 UNDERSERVED 识别

### 覆盖率的分母必须枚举

`2606.22247` 把「文档-代码等价」定义成**准确且完整**两个维度的合成性质，并给了实测：自动方法只能为 **53.4%** 的函数级片段生成等价文档。这个 53.4% 说明**完整覆盖本身极难达到**。

`2607.16024` 的 **union coverage** 是一个可以直接借用的指标设计：它同时覆盖**旧版本与新版本中被修改的代码**，避免只测新代码导致的偏差。实测平均 **90.7%**。

### UNDERSERVED 的判据

`2609.39909` DoGBench 给出的失败模式分布是判定 UNDERSERVED 的关键参照。审计 1267 个补丁后，三种轨迹模式及其占比：

1. **只描述接口，不考察读者如何使用**（36.0%）
2. **缺决定性证据时用看似合理的假设填补**（33.1%）
3. **找到第一个可行的文档面就停下，其他受影响的页面继续陈旧**（30.1%）

第 3 条是 UNDERSERVED 的**主要生成机制**：一处改动往往影响多张卡片，而生成过程满足于第一处命中。

对应的覆盖率指标应当有三项，而不只是一项：

| 指标 | 定义 | 对应失败模式 |
|---|---|---|
| 改动覆盖率 | 被记录的行为改动 / 全部行为改动 | 漏覆盖 |
| 卡片波及率 | 被更新的卡片 / 受该改动影响的卡片 | 模式 3（停得太早） |
| 声明完整度 | 卡片中已记录的声明 / 该改动应有的声明 | 模式 1、2 |

### 覆盖率之外的判据：文档债务的类型学

`2402.11048` 对 101 个缺陷的归类给出类型分布：信息内容类占绝大多数（86），其中**缺失文档 35、错误代码示例 23、内容过时 19**。

**对本项目的含义**：UNDERSERVED 与 DRIFT 在此有清晰分野。**缺失**对应 UNDERSERVED，**过时**对应 DRIFT，**错误示例**是 OVERSTATED 的一种具体形态。这个类型学比让模型自由发挥更稳定。

### 避免把重构误判为遗漏

按照第一节的做法，覆盖率的分母应当**先剔除行为保持的改动**。`2510.01960` 与 `2508.11993` 共同说明：不做这一步，分母会被重构灌水，覆盖率失去意义。

## 四、声明级事实验证与 OVERSTATED / DRIFT 区分

### 先拆声明，再验证

`2605.17926` 的两阶段设计给出了完整链条：

1. **AI 规则挖掘器**从自然语言需求中提取**可验证规则**，同时**显式标注模糊、自相矛盾和其他不可验证的陈述**
2. **AI 代码审计器**对照提取的规则检查实现证据

**这个设计里最重要的一点是第 1 步的副产品**：不可验证的陈述被单独标出，而不是被硬塞进判定类别。对本项目的含义是，四类结论之外应当允许**第五种输出：无法判定**。这与已在「知识关联」专题确立的原则一致（关联输出必须允许「无法关联」）。

论文的位置也很关键：这种方法**不需要编译、执行或运行时环境**，因此把验证活动整体左移，且它同时是**测试 oracle 问题的一种新解法**。

### OVERSTATED 与 DRIFT 的分野

两者的证据需求不同：

| 结论 | 文档侧的问题 | 需要的证据 | 可用手段 |
|---|---|---|---|
| **OVERSTATED** | 声称了代码没有的行为 | 代码中**不存在**该行为的存在性证据 | 符号级检索 + 静态分析 + 入口点枚举 |
| **DRIFT** | 描述的旧行为已不再成立 | 行为**曾经存在、现已改变**的变更证据 | Git 历史 + 差分执行验证 |

判据差异的来源：OVERSTATED 只需**当前代码**（存在性判定），DRIFT 需要**版本对比**（变更判定）。把两者混为一类会丢掉版本这个关键证据。

`2509.20837` 的标题点出了另一个可用信号：**验证难度本身会限制模型训练**，说明「可验证性」是一个需要显式建模的属性，而不是隐含假定。

### 用执行验证补足证据

`2406.14836`（见「文档相似度」专题）已确立核心结论：**用代码-注释一致性检测技术判断事实准确性，实测无效**（无统计显著关系）；替代路线是**文档测试**（按文档生成测试再执行）。本专题补充 `2510.25406` 的实证：**临时性地对代码施加重构**（分解再重组）能显著提升验证效果，在自建数据集上验证成功率 **86%（基线 68%）**；规格越复杂收益越大，在复杂程序上从 **25% 提升到 87%**。

**对本项目的含义**：DRIFT 的判定可以借这条思路，把「验证某条声明是否成立」转化为「为这条声明构造可执行检查」。

### 静态分析补证的边界

`2605.17926` 明确界定了静态分析的位置：它**能**给出实现证据（不需要运行环境），但**不能**判定行为是否匹配业务逻辑。所以静态分析在四类结论中的角色是**证据提供者**，而非**判定者**。

## 五、四类结论的可靠性评估

### 误报与漏报的实测基线

`2511.19875` CommitEval 构建了首个同类基准（提交信息与代码变更不一致检测），用规则引导的变异生成**七种不一致类型**，并做双重验证：

| 指标 | 实测值 | 含义 |
|---|---|---|
| Recall | **85.95%** | 不一致样本的检出率 |
| Precision | **80.28%** | 报告的不一致中真为不一致的比例 |
| Specificity | **63.8%** | 一致样本被正确放行的比例 |

**特异度 63.8% 是这份数据里最重要的一项**：约 **1/3 的一致样本会被误报**。这是同类任务在零样本条件下的现实水平。

论文还有两条对本项目有用的分类发现：

- **组件、文件路径、操作类不一致可检出性高**
- **意图层（purpose）不一致准确率更低、token 成本更高** —— 这对应你四类结论中最难的一类
- 三种增强策略的效果**并不一致**：相邻上下文对大模型有益、对小模型是噪声；few-shot 提升准确率并降低 token 用量，但**普遍增加错误预测**；思维链提升 precision 与 specificity，**代价是 recall 下降**且 token 消耗更高

**最后这条很关键**：增强策略不是单调的。选择策略等于在 precision 与 recall 之间做显式取舍，不能默认「加思维链更好」。

### 失败模式的分布

`2609.39909` DoGBench 的做法值得借鉴：它要求 Agent **先判断是否需要更新文档**，需要更新的产出补丁，**不需要更新的必须弃权（abstain）**；评分综合补丁质量与**正确弃权**，并明确声明**分数不等于专家能力的百分比**。

实测的失败模式分布（1267 个补丁）：任务完成缺口 45.5%、技术不准确 36.6%、概念或参考覆盖不全 32.5%。最高分 Agent 在 117 项留出集上仅 **47.3/100**。

**对本项目的三条直接含义**：

1. **必须把「正确弃权」计入评分**。COVERED 类的定位是需要被验证的正确输出，而非「什么都不做」
2. **失败模式要有分类计数**，而不是只报一个总准确率，否则无法定位问题
3. **不要声称基准分数等于专家能力**

### 避免模型只看关键词相似度

`2608.00884`（见「文档相似度」专题）已证明：删掉文档中的依据后模型准确率几乎不变，说明它在抓**捷径信号**。`2409.19801` CRScore 提供了对抗手段：**无参考（reference-free）指标**，把评审质量的评价**锚定到代码声明与静态分析器探测到的问题**上，而非与人工参考答案比字面相似。实测它与人类判断的相关性在所有开源指标中最高（**0.54 Spearman**），且比基于参考的指标更敏感。

**对本项目的含义**：卡片质量的评价不该与「某份标准答案」比相似度，而该看**它的声明能否在代码中找到对应证据**。

### 置信度校准

`2402.02047` 的结论很直白：**生成式代码模型开箱即用普遍校准不良**。作者提出用 Platt scaling 一类标准方法改善，但**明确讨论了适用与不适用的场景**，因为该方法依赖先前的正确性数据。

`2606.17203` 把校准放到多智能体协同里：共享知识图谱作为中心语义记忆与协同面，引入**两阶段追溯链接预测**（嵌入检索 + 多标准分析）、**追溯播种机制**（比较推导时与验证时的置信度）、以及包含**置信阈值门控、置信分歧检测、冲突消解**的一致性协议。消融**确认置信度校准对流水线协同是必要的**。

**对本项目的含义**：如果四类结论要驱动任何自动化动作，置信度必须先校准，且**校准需要历史正确性数据**。项目当前不具备这份数据，所以四类结论**保持人工评审定位是正确的**，这与 `Evaluation.md` 的既有门禁边界一致。

## 六、四类结论的判据汇总

| 结论 | 核心问题 | 主判据 | 证据来源 | 主要失败模式 |
|---|---|---|---|---|
| **COVERED** | 改动已被正确记录 | 改动集合中被覆盖的比例 | 结构化改动清单 + 卡片声明对照 | 误报覆盖（默认判据把一切判为未覆盖） |
| **UNDERSERVED** | 重要行为未被记录 | 未匹配的行为改动活动 | 改动清单减去已覆盖，**且已剔除重构** | 把重构当遗漏；停在第一个文档面 |
| **OVERSTATED** | 声称了不存在的行为 | 存在性判定的失败 | 符号检索 + 静态分析 + 入口点枚举 | 把抽象层差异当成编造 |
| **DRIFT** | 描述的旧行为已改变 | 版本间的行为差异 | Git 历史 + 差分执行验证 | 版本证据缺失时误判 |

**外加第五类：无法判定。** `2605.17926` 的做法说明，模糊与自相矛盾的陈述必须被显式标出。缺了这一类，前四类的准确性会被不可验证的陈述污染。

## 与本项目的衔接

### 直接对应的既有职责

- **`CheckAgent.md` 第 133 行**：「**相似度算法、评分、权重和阈值按 2026-09-10 的决定留待研究，尚未实现，也没有已确认的量化验收阈值**」。本专题给出可用的判据与实测参照值
- **`CheckAgent.md` 第 16 行**：Check 解释代码差异及其与规则的关系，Review 结合比较报告定位知识文档问题
- **`Evaluation.md`**：相似度、模型自评分和自然语言「通过」**不能覆盖门禁条件**

### 三条必须遵守的既有边界

1. **「不把编号索引、相似度算法或新的代码检测系统作为实现前提」**（`CheckAgent.md` 第 64 行）。本专题推荐的重构检测与结构化改动分解属于**程序提取**，但在落地时需要显式说明它与「新检测系统」的边界
2. **「不能把简单名称搜索等同于行为一致性判定」**（同处）。这条支持把一致判定交给执行验证，而不是文本匹配
3. **「实现和评测不能自行给出一个相似度分数作为发布依据」**（第 133 行）。本专题的所有量化输出都应当定位为**归因与诊断信号**

### 一个必须声明的设计边界

你现在描述的四类结论（COVERED / UNDERSERVED / OVERSTATED / DRIFT）在项目现有 specs 中**尚不存在**。CheckAgent 当前的报告结构是 `ruleId / original / generated / message / severity` 的 finding 列表，侧别为 `present / missing`。

这意味着本专题是为**新增的四类结论设计**提供方法依据，而不是为现有实现的参数调优。两者之间需要有一步显式的映射，否则会出现两套并行的判据。

### 三条最直接的落地建议

1. **先校准默认判据，再谈四类输出**。DocPrism 说明标准提示词会把 98% 的函数判为不一致。若不做局部化改造，UNDERSERVED 类会吞掉其余三类
2. **把重构检测前置**，既做假阳性过滤，也做覆盖率分母的清洗。这一步是确定性的，不依赖模型
3. **补齐「无法判定」这一输出类别**。`2605.17926` 的设计说明不可验证的陈述必须被显式标出，否则会污染四类的准确性
