# 提交信息不一致检测基准

同类任务的实测可靠性基线：recall、precision 与特异度。

论文：CodeFuse-CommitEval: Towards Benchmarking LLM's Power on Commit Message and Code Change Inconsistency Detection
标识：`2511.19875`
链接：[https://arxiv.org/abs/2511.19875](https://arxiv.org/abs/2511.19875)

## 要解决的问题

版本控制依赖提交信息传达改动理由，但这些信息往往质量低下，更严重的是**与它们的 diff 不一致**，论文称之为 **message-code inconsistency（MCI）**。

论文列出的后果：误导评审者、阻碍维护、**污染研究数据集**、可能**掩盖安全补丁**。

**这个任务与本项目的 UNDERSERVED / OVERSTATED 是同构问题**：都是判断「一段自然语言描述」与「一段代码变更」是否一致。差别只在描述的对象（提交信息 vs 知识卡片）。

论文指出此前**没有专门的基准**来评估模型做 MCI 检测的能力。

## 方法核心

### 基准构造

论文基于 **ApacheCM 数据集**（论文强调其多样性与质量），构造方法是：

1. 对原本一致的提交做**规则引导的变异**，生成**七种类型**的不一致信息
2. 用**双重验证（two-fold validation）**验证正样本与负样本

这个构造方法有其用意：**用变异生成不一致样本**，而不等真实世界出现。好处是类型可控、标注可靠；代价是分布可能与真实不一致有差距。

### 评测设置

在带标注的 message-diff 对数据集上，评估**六个最先进的开源模型**：

- **vanilla 设置**（无增强）
- 三种增强策略：**few-shot 提示、思维链（CoT）、扩展上下文**

### 七种不一致类型

论文没有在摘要中逐一列出七种类型，但从结果分析可知其中至少包括：**组件（component）、文件路径（file-path）、操作（operation）**，以及**意图层（intent-level）的「目的（purpose）」**。

## 关键数据

### 总体指标（六个模型平均）

| 指标 | 实测值 |
|---|---|
| Recall | **85.95%** |
| Precision | **80.28%** |
| Specificity | **63.8%** |

### 三条关键解读

**第一，特异度 63.8% 是全部数字里最重要的一项。**

特异度衡量的是**一致样本被正确放行的比例**。63.8% 意味着约 **1/3 的一致样本会被误报为不一致**。

对本项目的直接含义：如果直接接入模型判定，**约三分之一的正确卡片会被报为有问题**。这个误报率决定了四类结论只能作为人工评审的输入。

**第二，召回高于精确，且模型在不一致样本上表现更好。**

论文明确说：「模型检测**不一致**提交比检测**一致**提交更可靠」。这是一个系统性偏差：模型倾向于报「有问题」。

这与 DocPrism 的发现方向一致（默认判据会把大量样本判为不一致），说明这是同类任务的**共性偏差**，不是单个模型的问题。

**第三，按类型看差异很大。**

- **可检出性高**：组件、文件路径、操作类不一致
- **表现较差**：**意图层「目的」类不一致**，准确率更低，**token 成本更高**

对本项目的含义：四类结论中涉及**高层意图**的判定（例如卡片描述的业务目的与改动意图是否一致）会比结构层面的判定难得多，且更贵。

### 三种增强策略的效果

论文的结论是**效果因策略而异，且并非单调改善**：

| 策略 | 收益 | 代价 |
|---|---|---|
| **相邻上下文** | 对**大模型**有帮助 | 对**小模型**是**噪声** |
| **Few-shot** | 提升准确率，**降低 token 使用** | **普遍增加错误预测** |
| **思维链** | 提升 precision 与 specificity | **recall 下降**，token 消耗更高 |

**这是本条信息量最大的一组数据。** 它说明增强策略的效果取决于目标，本质上是在 precision 与 recall 之间做显式取舍：

- 想减少误报（提升 precision 与 specificity）→ 用思维链，代价是漏报增多
- 想省 token 且提高准确率 → 用 few-shot，代价是错误预测增加
- 模型规模决定相邻上下文是否有益

### 模型层面的观察

- **gpt-oss-20B 总体表现最好**
- 但它**使用的 token 超过其他模型两倍以上**

这给出一个成本与质量的明确取舍点。

## 对本项目的启发

### 方案要点

**一、把 63.8% 特异度当作 UNDERSERVED 误报率的参照基线。**

在你的流水线里，UNDERSERVED 是「报告有遗漏」的类别，它对应这里的「判为不一致」。所以 **1/3 的误报是同类任务的现实水平**。

落地的含义是：

- 报出 100 条 UNDERSERVED，其中约 30 条可能在人工复核后被推翻
- 这个噪音水平要求流水线提供**每条结论的证据定位**，否则人工复核成本会失控
- 不能把 UNDERSERVED 的数量直接作为质量指标使用

**二、模型有「倾向报有问题」的系统性偏差，需要对称设计。**

论文发现模型在不一致样本上比在一致样本上表现更好。对本项目的含义是：**COVERED 的判定需要额外的验证机制**，不能依赖模型在其中立地判断。

可行的做法是让 COVERED 也要求正向证据（见「文档-代码等价与完整覆盖」的等价性定义）。

**三、增强策略要按目标选，不能默认叠加。**

| 你的优先目标 | 选用的策略 | 需接受的代价 |
|---|---|---|
| 降低误报 | 思维链 | recall 下降，token 增加 |
| 控制成本 | few-shot | 错误预测增加 |
| 提升召回 | 谨慎使用思维链 | precision 与 specificity 下降 |

**相邻上下文的效果取决于模型规模**：如果你用的是中小模型，加相邻上下文可能反而引入噪声。这一点在本地部署小模型的场景下尤其重要。

**四、意图层判定最难，应当单独设计。**

论文的意图类不一致准确率最低、token 成本最高。对应到本项目：**卡片中描述「为什么这样设计」的部分，判定难度显著高于描述具体行为的部分**。

可行的策略是分层处理：结构层（接口、参数、路径）用确定性手段，行为层用执行验证，意图层**允许输出「无法判定」**。

**五、七种类型的构造方法可以借用。**

用**规则引导的变异**从一致样本生成不一致样本，是构造自建评测集的低成本方法。项目已有生成流水的真实输出，可以对它们做定向变异来构造评测集。

但要注意论文自己的观察：**MCI 会污染研究数据集**。所以构造评测集时要保证变异样本与自然样本分开管理。

### 可以直接借鉴的基准设计

- 用规则引导变异生成**多类型**的不一致样本，而非单一类型
- 做**双重验证**确认正负样本标注
- 评测时区分 **vanilla 与增强**设置，分开报告
- 按**不一致类型**分组报告结果，而不是只报总体

最后一条尤其重要：只报总体准确率会掩盖类型间的巨大差异。

## 局限

- **变异生成的样本与真实不一致的分布可能有差距**。论文用规则引导变异构造负样本，这保证了标注可靠性，但真实场景的不一致类型分布可能不同
- **基准基于 ApacheCM**，语言与技术栈有特定偏向，对本项目的语言需核对
- **只评测开源模型**。论文未给出闭源模型的结果，本项目若用其他 provider 需自行验证
- **特异度 63.8% 是六个模型的平均或范围**，摘要未明确是均值还是特定模型的数值，具体口径需查原文
- **未给出误报的具体类型分布**。63.8% 的特异度无法说明误报集中在哪些情况
- **论文未提供检测证据定位的评估**。它评测的是「判对没有」，不是「定位准不准」，而后者是本项目 Q5 的重点
