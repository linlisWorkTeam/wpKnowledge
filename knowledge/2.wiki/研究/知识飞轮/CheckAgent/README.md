## 这批材料回答的问题

Check 这一段的核心困难是**判断标准从哪来**。把两份代码放在一起，模型可以指出很多不同之处，但绝大多数差异无关行为。判断哪些差异重要，需要一个独立于两份实现的参照。

材料给出的路线可以分成三条：

**第一条：靠给定规则**。项目当前的做法，用外部提供的比较规则约束检查范围，规则缺位就拒绝执行。规则驱动的做法在合规检查领域有成熟参照。

**第二条：靠找反例**。不判断两份实现是否相似，而是试图找出一个输入让它们的输出不同。找到就证明不等价，找不到只是没找到。这条路线的优势是判定是确定的，弱点是不完备。

**第三条：靠规格重建**。让规格足够精确，精确到能从它重建出源码。重建结果与原件一致就说明规格捕获了行为。这条路线最重，但提供了形式化的信任基础。

三条路线不互斥。项目当前在第一条上，另两条提供了扩展方向。

## 对本项目的核心结论

1. **相似度打分这条路线可以放弃**。项目文档把相似度算法、评分、权重与阈值列为待研究，并明确不能给出一个相似度分数作为发布依据。论文给出的替代路线是「找反例」，它的输出是具体的输入与两组不同的输出，比一个分数更适合进入门禁判定。

2. **差异报告需要区分「不同」与「不等价」**。项目已经有 BLOCKER 与 INFO 的严重程度划分，也明确不能仅因实现写法不同就宣布行为不一致。论文的做法把这条原则推进了一步：判断的落点从「看起来是否相同」移到「是否存在行为差异的证据」。

3. **规则驱动的判据来自项目现有设计**。规则必须唯一编号、非空说明、缺位则不调用模型，这套约束在规则合规检查系统里有对应实现，可以参考它们的审计链组织方式。

4. **检查本身也需要防作弊**。模型可以只满足表层检查而不真正执行规则。同构扰动测试提供了一个识别方法：对检查对象做保持语义不变的变换，真正的检查结果应当不变。

## 怎么用这批材料

- **要改差异判定方式**：反例篇与差分模糊篇，从打分转向找反例
- **要设计检查规则的结构**：规则驱动篇的规则组织与审计链
- **要防检查被应付**：验证器博弈篇的同构扰动方法
- **要组织更强的参照**：规格验证层篇的重建验证思路
