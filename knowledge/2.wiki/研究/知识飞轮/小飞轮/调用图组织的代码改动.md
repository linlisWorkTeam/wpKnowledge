# 调用图组织的代码改动

按调用关系而非文件组织改动，用于间接影响的传播判断。

论文：CG-Diff: Organizing Code Changes Around Call Graphs
标识：`2609.32057`
链接：[https://arxiv.org/abs/2609.32057](https://arxiv.org/abs/2609.32057)

## 要解决的问题

代码改动的组织方式决定了人能看懂多少、以及机器能否判断影响范围。

常规的组织方式是**按文件罗列**（这也是 Git Diff 的默认输出）：哪些文件改了、每个文件改了多少行。

论文提出 **CG-Diff**，把代码改动的组织方式改为**围绕调用图**。

## 方法核心

### 从「文件视图」到「调用视图」

| 视图 | 组织单位 | 回答的问题 |
|---|---|---|
| Git Diff 默认 | **文件** | 哪些文件改了 |
| CG-Diff | **调用关系** | 一次改动沿调用链影响了哪些函数 |

### 与小飞轮 Q3 的关系

你 Q3 问「如何建立代码变更与知识卡片之间的关联，并识别间接影响」。

**「间接影响」的传播路径就是调用关系**：函数 A 的行为变了，调用 A 的函数 B 的行为可能随之改变，而 B 对应的卡片也需要更新。

**按文件组织看不出这条传播路径**：如果 B 和 A 在不同文件，diff 会把它们列为两个独立改动，看不出因果关系。按调用图组织则能直接呈现「A 的变化传导到 B」。

## 对本项目的启发

### 方案要点

**一、调用关系是「间接影响」的天然传播路径。**

这是本条的核心价值。对小飞轮的含义：

| 改动层次 | 传播路径 | 卡片影响 |
|---|---|---|
| 函数内部实现变化 | 无传播 | 该函数的卡片 |
| 函数签名变化 | 沿调用边向上 | 所有调用方卡片 |
| 被调用函数行为变化 | 沿调用边向上 | 调用方卡片（可能） |

**第二、三类就是「间接失效」**：卡片描述的是调用方，但改动发生在被调用方。

**二、判断传播要用「签名变化」与「行为变化」区分。**

- **签名变化**（参数、返回值）：**确定性地传导**到所有调用点 → 直接判定需要检查调用方卡片
- **行为变化**（内部逻辑）：**不必然传导**，取决于调用方是否依赖该行为 → 需要语义判断

**第一类是确定性的**，应当由程序完成；第二类才需要模型。这与 README 的「确定性优先」原则一致。

**三、这个视角解释了为什么「按文件看 diff」会漏掉间接影响。**

`2608.21964` 的实测显示「对受影响文件的覆盖不完整」是主导错误之一。**按文件组织改动正是这个错误的成因**：文件的边界与影响的边界不一致。

**四、实现成本需要评估。**

CG-Diff 需要**调用图的构建能力**。这对项目而言是一个增量依赖：项目的 `CheckAgent.md` 第 131 行已声明「**词法提取不代替完整 C/C++ 编译器，无法识别的边界不猜测**」，说明项目当前用的是词法级提取。

**所以调用图的能力边界需要明确**：

| 手段 | 能得到的 | 局限 |
|---|---|---|
| 词法提取（项目现有） | 函数定义、调用文本 | 无法解析函数指针、重载、宏 |
| 完整编译器 | 准确调用图 | 需要可编译环境 |

**对本项目的建议是保守的**：先用词法级可识别的调用做传播，**无法识别的边界不猜测**（与项目既有约束一致）。

**这是本分析提出的建议，论文未涉及词法级实现的可行性。**

**五、优先级判断。**

在 README 列的分级验证范围（Q9）里，调用关系传播属于**第二、三级**。它的价值是确定性地扩大检查范围。

但要注意：如果词法级调用图不可靠，**传播会引入误报**（把无关卡片拉进检查范围）。所以这一级应当**先验证准确率再启用**。
