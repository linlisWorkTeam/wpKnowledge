# 小飞轮：知识卡片增量更新与一致性验证

针对「Git Diff 触发的知识卡片增量更新」这一轻量场景的调研。约束是**低成本、快速执行、尽量保持一次 LLM 调用、不引入多 Agent 与知识图谱与大规模测试**。

## 什么是小飞轮

小飞轮与大飞轮的分工：

| | 大飞轮 | 小飞轮 |
|---|---|---|
| 触发 | 人工意见 / 整体质量反馈 | **Git Diff** |
| 动作 | 全流程生成、评测、门禁 | **检查卡片与改动是否一致** |
| 代价 | 多角色、多轮次 | **一次 LLM 调用** |
| 输出 | 候选知识 + 门禁判定 | **一致性结论** |

论文：Natural Language-Focused Software Engineering via Code-Documentation Equivalence（`2606.22247`）与 Knowledge Pull Requests（`2609.26634`）都指出同一个现状：**现有方法要么在不考虑知识变了什么的情况下编辑，要么从头重新生成**。小飞轮要补的正是中间那条路。

## 先看结论

### 与项目现有能力的衔接（动手前必须先知道）

项目**已经具备小飞轮的骨架**，但缺两个环节：

- **已有：定向修订机制。** `DocGenAgent.md` 第 20 行把「上一版文档、纠正意见」列为修订输入；第 61 行要求「有纠正意见或质量反馈时必须提供非空上一版」；IO-18 就是这个能力
- **已有：最小性的程序化校验。** 第 43 行给了一个具体判据：假设上一版有「创建订单」「取消订单」「退款」三节，Review 只指出退款章节有错，则「**DocGen 只能修改退款章节，其余正文必须逐字保留。框架接收结果时检查这一点**」
- **已有：共用定位规则。** 第 63 行支持「当前文档路径 / 路径加章节标题 / 唯一章节标题 / 唯一原文片段」，且「**不存在、无法唯一定位或指向另一文档都拒绝**」；「仅允许修改部分章节时，**范围外正文变化同样拒绝**」
- **缺：Git Diff 作为触发源。** 现在的修订输入是**人工给的纠正意见**，不是自动的代码改动
- **缺：证据不足状态。** 「证据不足 / 无法判定 / 弃权」在 `docs/specs/` 里**零命中**（已 grep 核实）

**这意味着小飞轮的设计要点落在「把人工意见触发换成 Git Diff 触发」，并补上证据判定。** 存量资产（定向修订、最小性校验、定位规则）可以直接复用。

### 六条最重要的发现

**一、过度编辑是普遍现象，且有可直接采纳的量化标准。**

`2609.04061` 把「过度编辑」定义为模型重写超出所需的范围。它用 **400 个 BigCodeBench 问题注入 AST 级受控损坏**，让每个任务都有**已知的最小补丁**，从而「最小性」才有基准可对照。

实测：**即使 GPT-5.5 这类强模型，过度编辑也普遍存在，高 Pass@1 可以与不必要的大改动并存**。加一句**保留指令**后 excess Levenshtein distance 从 **0.195 降到 0.131**，认知复杂度降 **26.6%**，Pass@1 反而升 **2.3 点**。

**二、模型「不弃权而猜」有结构性原因，不能靠提示词解决。**

`2609.32964` 把幻觉定义为 **unsupported commitment**：**模型在已经出现「无法回答」信号的情况下仍然作答**。机制分析发现一个反复出现的模式：**承诺促进组件在浅层累积，弃权促进组件在深层才起作用，往往不足以推翻累积的承诺**。

**三、陈旧是静默的，而且前沿 agent 也维护不好。**

`2608.21964` 把「每次版本发布」当作一次技能维护任务：给 V1 技能集 + V1→V2 补丁，要求**更新过时内容同时保留仍有效的指导**。在 **57 个真实仓库、105 次发布转换**上，**每一次转换都使部分 V1 失效**，而**六个前沿 agent 只有 29.9%~69.7% F1**。

论文的核心诊断：**「让技能有用的版本特异性同时让它脆弱」**，而**「把知识外化到技能里，可能反而让它的衰减变得不可见」**。

**四、「知识变了什么」与「文本怎么变」必须分开。**

`2609.26634` 的 Knowledge Pull Requests 产出 **ChangeLog**，明确**分离 claim proposal（知识变化）与 document diff（文本变化）**。这正是三方对比（diff + 旧卡片 + 新卡片）比两方对比更可靠的原因。

**五、两种相反的错误同时存在，且互相拉扯。**

`2608.21964` 明确指出主导错误是成对的：**对受影响文件的覆盖不完整 → 陈旧内容原封不动留下**，与**编辑过宽 → 召回更高但精确更低**。这两者正对应你的 Q9（验证范围）与 Q4（最小性），且**不能同时优化到极致**。

**六、不要喂原始 unified diff。**

`2604.27296` 系统研究了 diff 格式后发现**脆弱的偏移量与碎片化的 hunk 让生成对 LLM 极不自然**。它提出的 BlockDiff 与 FuncDiff 把改动表示成**语法连贯单元的块级重写**（控制结构、函数级）。配合自适应策略后**准确率与全代码生成持平，长代码编辑的延迟与成本降低 30% 以上**。

## 一、Q1：Git Diff 是否一定需要触发卡片更新

### 判断标准应当落在「可观察行为」上

`2510.01960` 指出，行为保持的重构**无法与影响行为的改动有效区分**是误报的主要来源。所以第一步是把 diff 分成两类：

| 改动类型 | 是否需更新卡片 | 判据 |
|---|---|---|
| 行为保持的重构（改名、提取、移动） | 否 | 重构检测 |
| 格式调整、注释调整 | 否 | 语法树比较 |
| 对外接口变化（签名、默认值、可见性） | **是** | 接口比对 |
| 可观察行为变化（分支、校验、错误码） | **是** | 差分测试 |
| 内部实现细节（临时变量、循环写法） | 否 | 语法树加语义等价判断 |

**这就是你 Q1 的「判断标准」**：判据是**「改动是否改变了外部可观察行为或对外契约」**，而不是「改动大不大」。这与 `2606.22247` 的等价性定义一致（文档只需准确且完整地描述**它记录的代码**的行为）。

`2502.00519` CoDocBench 提供了这套判定的**真实数据形态**：它挖掘**代码与 docstring 在同一个 commit 里一起改动**的样本，每个样本是一次「耦合变更」。这类样本天然就是「什么改动确实引发了文档更新」的正例。

### Q1 的完整判据链

1. **重构检测前置**（确定性、不依赖模型）：剔除行为保持的改动。`2510.01960` 实测假阳性降低近 32%
2. **契约比对**（确定性）：公开接口的签名、默认值、可见性变了就必须更新
3. **行为差异判定**（需模型或执行）：剩余改动是否需要文档
4. **强制触发规则**：接口变更、错误处理变更、新增公开行为一律触发

**第 4 条是低成本的关键**：它让大部分情况不需要模型判断。

### 一个必须承认的限制

`2508.11993` 实测：**现有重构检测器只识别出 33.9% 的行为保持改动**。所以第 1 步的剔除不可能完备，必然有行为保持改动被误判为需要更新。这决定了**小飞轮的判断只能是分流参考，不能是硬门禁**。

## 二、Q2：增量修改是否可靠

### 「增量 vs 重生成」不是二选一

`2609.26634` 指出**现有方法要么无视知识变化直接编辑，要么从头重新生成**，两者都有代价。它的方案是把知识变化与文本变化分离后**定向整合**。实测 KPR **比「从源头重写」和「从头重新生成」整合了更多信息、更好地保留了既有内容，且「每生成一个 token 增加的信息量最多」**。

### 增量修改的三个可靠性来源

**来源一：结构化输出格式（`2604.27296`）**

不要在提示词里要求模型「输出 diff」。改让模型输出**块级重写**（某个章节、某个语法单元），由程序负责生成实际差异。论文实测这种方式**准确率与全代码生成持平，成本降 30% 以上**。

**来源二：保留指令（`2609.04061`）**

**一句「保留」指令就把 excess Levenshtein distance 从 0.195 降到 0.131**，且 Pass@1 提升 2.3 点。这是**零成本**的干预，必须加。

**来源三：程序化最小性校验（项目已有）**

`DocGenAgent.md` 第 43 行的判据是现成的：只允许修改指定章节，**范围外正文逐字保留，框架接收结果时检查**。`2609.04061` 的 excess edit distance 可以作为这个校验的量化补充。

### 增量修改的四个局限

1. **陈旧会继承**。若旧卡片本身有错，增量更新继续保留它。见第七节
2. **间接失效会被遗漏**。改动影响的其他章节不会被自动检查。`2608.21964` 的「覆盖不完整」就是这一条
3. **编辑过宽与过窄的取舍不可避免**。论文明确两者是相反错误，不能同时最优
4. **缺少可对照的最小补丁**。`2609.04061` 用受控注入构造已知最小补丁才使最小性可测量；真实 diff 没有这个基准，所以**最小性只能近似评估**

### 与项目现有机制的关系

| 小飞轮需要的 | 项目已有 | 差距 |
|---|---|---|
| 定向修改指定章节 | IO-18 修订机制 | 无 |
| 范围外逐字保留 | 第 43 行程序化校验 | 无 |
| 唯一定位 | 第 63 行定位规则 | 无 |
| 保留指令 | 第 69 行 prompt 已含「保留范围外正文」 | 无 |
| 量化最小性 | 无 | **缺**（可用 excess edit distance 补） |

**结论：Q2 的机制层面项目已经基本具备，缺的是「用 Git Diff 代替人工意见作为触发」以及最小性的量化指标。**

## 三、Q3：如何定位需要更新的卡片与内容

### 结构定位优先于语义检索

项目第 63 行的定位规则已经给出了比语义检索更可靠的答案：**当前文档路径、路径加章节标题、唯一章节标题、唯一原文片段**，且「不存在、无法唯一定位或指向另一文档都拒绝」。

**这套规则的关键性质是它拒绝模糊匹配。** 相比用 embedding 找「最相似的卡片」，它在无法唯一定位时**直接失败**，避免改错地方。

### 代码侧的定位：从符号出发

`2511.05205` CodeMapper 提供了跨 commit 映射代码区域的语言无关方法。更轻量的做法是**符号级反向索引**：卡片在生成时记录它依据的符号，改动触及这些符号即触发。

`2609.32057` CG-Diff 的思路可参照：**围绕调用图组织代码改动**，而按文件罗列。对本项目而言，这意味着**一条改动可能影响多个文件，应按调用关系而非文件名传播**。

### 间接影响怎么处理

这是 Q3 最难的部分。三个层次的答案：

1. **符号引用反向索引**（确定性）：改动触及的符号被哪些卡片引用
2. **调用关系传播**（确定性）：被调用方的改动影响调用方卡片
3. **语义相似检索**（需模型）：仅在上述两层失败时兜底

**注意第 3 层要慎用**。`2608.21964` 的失败模式表明「覆盖不完整」是主导错误之一，而语义检索**恰恰擅长找到显式相关的、会漏掉间接相关的**。所以前两层确定性手段覆盖不到的部分，更可能被静默漏掉，而不是被语义检索救回来。

## 四、Q4：修改内容是否正确

### 五个指标的可执行化

你列的五个指标（事实正确性、变更覆盖率、修改必要性、修改最小性、内容一致性）需要转成判据。`2505.19757` CIDRe 提供了一个已验证的四维框架，可以直接对照：

| 你的指标 | CIDRe 对应维度 | 可执行的判据 |
|---|---|---|
| 事实正确性 | **相关性**（语义对齐） | 卡片声明能否在代码中找到对应实体 |
| 变更覆盖率 | **信息量**（功能覆盖） | 改动活动清单中被卡片提及的比例 |
| 修改必要性 | - | 该改动是否属「强制触发」类别 |
| 修改最小性 | **描述长度**（细节充分性） | **excess edit distance**（`2609.04061`） |
| 内容一致性 | **完整性**（结构小节齐全） | 章节结构是否完整、无遗留占位 |

CIDRe 是**无参考（reference-free）**判据，这点对本项目关键：不需要人工标准答案就能算。

### 最小性的量化（最实用的一条）

`2609.04061` 给的算法：构造**已知最小补丁**，然后测模型补丁与它的**excess Levenshtein distance**。

对本项目：虽然真实 diff 没有「已知最小补丁」，但可以**用一个两段式近似**：

1. 让模型只改被点名的章节（项目第 43 行机制已保证）
2. 测改动后的章节与改动前的 **token 级编辑距离**，与「该章节应有的改动量」比较

第 2 步的「应有改动量」可以用 `2512.19883` 的结构化改动活动数近似（见「文档相似度」专题）。

### 必要性的判定

必要性不该由模型判断，而应由**触发规则**决定（第一节的第 4 条）。理由：`2609.04061` 证明模型在正确性达标时仍会大幅过度编辑，说明模型对「必要」的自我判断不可靠。

### 一个交叉验证：CIDRe 可用于过滤

`2505.19757` 的额外发现：**用 CIDRe 过滤数据后微调的模型质量有统计显著提升**。对本项目的含义：这套判据不仅能评估卡片，还能**筛掉低质量卡片进入后续流程**。

## 五、Q5：三方对比是否更可靠

### 更可靠，原因是它能分离两类变化

`2609.26634` 的 Knowledge Pull Requests 明确把 ChangeLog 分成**两部分**：

- **claim proposal**：知识层的变化（哪些事实被新增、修改、废弃）
- **document diff**：文本层的变化（哪些句子被改动）

**这正是三方对比优于两方对比的根本原因**：给模型「Git Diff + 旧卡片 + 新卡片」，它就能判别**文本变化是否恰好对应知识变化**。

- 有代码改动、有知识变化、无文本变化 → **UNDERSERVED**（漏覆盖）
- 有代码改动、无知识变化、有文本变化 → **UNNECESSARY**（不必要的修改）
- 有文本变化但知识未变 → **表达层改写**（可能是过度编辑）
- 有知识变化但无对应代码改动 → **OVERSTATED**（凭空声称）

**这四种组合是三种输入的自然产物**，而两方对比（diff + 新卡片）拿不到「旧卡片」这一维，就无法区分「本来如此」与「改坏了」。

### 还需要哪些上下文

`2502.00519` CoDocBench 给出的样本形态是**代码与文档在同一 commit 一起改**。这说明三方对比的天然数据单位是**单次 commit**，而不是累积的 diff。

除三方之外仍需补充的：

1. **改动涉及的符号清单**（用于锚定，而非语义检索）
2. **改动前后该符号的完整定义**（Diff 只有片段，判定行为需要完整上下文）
3. **被影响的其他章节清单**（应对 Q9 的间接失效）

**第 2 条对应你 Q6 的「Git Diff 不等于完整代码」**，是必需项。

### 一个限制

`2502.00519` 实测**当前模型（Llama-3.1 405B、Mixtral 8×22B）确实觉得这类「代码-文档耦合变更」任务困难**。所以三方对比虽更可靠，但**不能假设模型一定能用好它**。

## 六、Q6：如何证明行为确实被实现

### Diff 不是证据，完整代码也不是

论文 `2605.17926`（见「文档一致性」专题）已确立：**静态分析能给出实现证据，但无法判断行为是否匹配预期业务逻辑**。`2607.16024` DiffTestGen 则证明只有**执行**才能给出「行为是否真的存在」的客观证据。

对低成本约束下的本项目，证据强度分三级：

| 级别 | 证据 | 成本 | 能证明什么 |
|---|---|---|---|
| 一 | 符号是否存在、调用关系 | 极低（确定性检索） | 「这个接口存在」 |
| 二 | 完整函数体的控制流与分支 | 低（读文件） | 「这条分支存在，条件是 X」 |
| 三 | 执行结果 | 高 | 「行为确实如此」 |

**小飞轮应当只承诺级别一与级别二**，并明确声明**级别三不在范围内**（这与你「不引入大规模测试」的约束一致）。

关键点：**级别二的证据必须来自完整代码，不是 diff**。Diff 只告诉你「这里变了」，不告诉你「现在是什么」。

### 共同误判风险的三个缓解手段

**手段一：让不同判断走不同证据路径（不是换提示词跑两遍）**

「文档相似度」专题已指出：若几个判定都依赖同样的捷径信号，交叉也挡不住偏差。可行的做法是让**事实正确性**走符号检索、**覆盖率**走改动清单核对、**最小性**走编辑距离计算。三者证据来源不同，共同误判的概率大幅降低。

**手段二：依据消融（遮住材料重跑）**

`2608.00884`（见「文档相似度」专题）证明：删掉卡片依据后模型准确率几乎不变，说明它在抓捷径信号。检验法是**把模型声称引用的材料遮住重跑**：结论不变 = 没真依赖该材料。

**手段三：程序可推导的不交给模型**

`CheckAgent.md` 第 64 行的既有约束已经说了这点：**「程序可以推导的内容不要求模型重复手填」**。最小性、覆盖率分母、符号存在性都可程序化，模型只做「语义是否等价」这类判断。

### AURORA 一类方法的定位

`2606.29545` 提出从**权重梯度动态**检测幻觉（幻觉样本触发不对称、结构失配的梯度）。这类方法理论上更稳，但需要模型内部访问与额外推理，**与本轮「低成本、一次调用」的约束不符**，此处仅作方向记录。

## 七、Q7：如何避免继承历史错误

### 旧卡片不能视为可信基线

`2608.21964` 的核心诊断直接回答这个问题：**「把知识外化到技能里，可能反而让它的衰减变得不可见」**，且**「发布后它可能变得陈旧而不发出任何显式信号，同时继续提供过时指导」**。

对本科项目的含义：**必须假设旧卡片的某些内容是错的**。增量更新会保留它们，而且在很多版本内不会被发现。

### 两种机制的分离

`2610.05281` Concord 给出的做法可以借用：**把每个观测链接到它的来源，检测来源变化，用可配置策略在使用前更新、标注或抑制陈旧上下文**。实测令牌用量比最强的非 oracle 基线**少 46.4%**。

对本项目的映射：

| Concord 的机制 | 本项目对应 |
|---|---|
| observation 链接到 source | **卡片声明链接到符号与位置** |
| 检测 source 变化 | 提交时校验符号是否仍存在 |
| 更新 / 标注 / 抑制策略 | 失效声明的三态处置 |

**关键字是「检测来源变化」而不是「重新判断内容对不对」**：前者是确定性的，不消耗模型调用。

### 三条可操作的做法

**做法一：区分「本轮新增的声明」与「继承的声明」。**

在卡片里标记每条声明的来源轮次。检查时对继承声明只做**失效检测**（它所依据的符号是否还在），对新增声明才做**正确性检查**。这把检查成本集中在真正的新内容上。

**做法二：允许「无法验证的继承声明」存在，但隔离它们。**

不要因为无法验证就删除（可能造成信息损失），也不要默认它们正确。标记为**未经本轮验证的继承内容**，与已验证内容在卡片里**分段展示**。这与 `2605.17926` 的「显式标注不可验证陈述」是同一原则。

**做法三：定期做一次全量复核，而不是每轮都做。**

这直接回答你 Q9。见下一节。

### 一个必须接受的事实

`2608.21964` 的实测很冷静：**在 105 次真实发布转换中，每一次都使部分 V1 失效，而前沿 agent 只有 29.9%~69.7% F1**。所以**不要设计一个声称能完全避免错误继承的机制**，应当设计一个**能把错误暴露得足够早**的机制。

## 八、Q8：如何处理证据不足

### 为什么模型不会自觉弃权

`2609.32964` 给出了机制层面的答案：**commit-abstain 的决定由一组稀疏的注意力头与 MLP 子层承担**，且呈现**「累积却不纠正」的模式**：**承诺促进组件在浅层累积，弃权促进组件在深层才起作用，往往不足以推翻已经累积的承诺**。

**关键含义：弃权不是提示词能可靠解决的问题。** 模型内部结构性地倾向作答，所以在提示词里加「如果证据不足就说不确定」，效果有限。

### 可以借用的方案

论文用一个小策略解决了这个问题：**在 CAC 激活上训练轻量策略**，决策准确率比模型自身的 commit-abstain 边界**提升 12.2 点**，**假弃权减少 2.5 倍**。

不过这对本项目**成本偏高**（需要激活访问与训练）。更可行的是**外部强制**：

| 方案 | 做法 | 成本 |
|---|---|---|
| **三段式输出强制** | 要求模型对每条声明输出「有依据 / 无依据 / 证据不足」三态之一，**且必须给出依据位置** | 零（提示词） |
| **程序化证据预填** | 程序先填好「该符号存在 / 不存在」，模型只判断语义等价 | 零（确定性） |
| **证据不足即降级** | 证据不足的声明进入「待人工确认」，不阻塞流水线 | 零 |

**第一段的「必须给出依据位置」是关键**：无法给出位置 = 无依据，这比让模型自评「我有多确信」可靠得多（`2402.02047` 已证明生成式模型开箱即用**校准不良**）。

### 证据不足状态的落地形态

结合 `2605.17926`（见「文档一致性」专题）的做法与项目现状：

项目当前**没有**证据不足状态（已 grep 核实）。建议的三态：

1. **已确认**：有代码位置证据，且语义判定通过
2. **已否定**：有代码位置证据，语义判定不通过
3. **证据不足**：无法定位证据，或定位到但语义无法判定

**第 3 类必须能被表达出来**，否则模型只能在 1、2 之间硬选，产生噪音。

## 九、Q9：验证整张卡片还是只验证增量部分

### 两种错误同时存在，所以答案不是二选一

`2608.21964` 明确给出主导的两种相反错误：

- **对受影响文件覆盖不完整 → 陈旧内容原封不动留下**（验证范围太小）
- **编辑过宽 → 召回更高但精确更低**（验证范围太大或改动过多）

论文用的指标是 **patch-grounded removal metric**，**平衡陈旧内容召回与过度编辑精确**，这个设计本身就说明两者需要同时考虑。

### 分级答案

| 范围 | 触发条件 | 成本 |
|---|---|---|
| **只验证被改动章节** | 默认 | 最低 |
| **验证同卡片的引用章节** | 改动触及的符号被其他章节引用 | 低（确定性） |
| **验证所有引用该符号的卡片** | 符号级反向索引命中 | 低（确定性） |
| **全卡片复检** | 定期 / 卡片累计 N 轮未全检 | 最高 |

**关键设计：前三级的范围扩大都由确定性信号驱动，不需要模型判断。** 只有第四级是主动的。

### 陈旧的三种来源与对应检查

`2610.05281` 与 `2608.21964` 合起来给出陈旧的三类来源：

1. **直接改动**：本次 diff 触及 → 第一级检查覆盖
2. **间接影响**：被调用方或依赖方变化 → 第二、三级覆盖
3. **时间衰减**：无改动但外部约定变了 → 第四级覆盖

**第 3 类是小飞轮最容易漏的**，因为没有任何 Git 事件触发它。`2608.11095`（见「增量维护」专题）已证明这类积累会导致**知识文件无界膨胀**。

### 一个务实的起点

先用**全卡片检查 + 一次调用**起步，把「被改动章节」与「其他章节」分成两段输入，要求模型对两段分别给出结论。这比拆分多次调用便宜，又能拿到间接失效的信号。

`2609.04061` 的发现支持这个设计：**加保留指令后 Pass@1 反而提升**，说明「提醒模型哪些内容不该动」不仅不增加成本，还能提升质量。
