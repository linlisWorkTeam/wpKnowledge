# 小飞轮：四元组增量更新与正确性证明

对应问题图的四节点结构：旧代码 →（Diff）→ 新代码，旧卡片 → 新卡片，核心在末端的「怎么证明改对了」。

说明：本专题按**问题图的拓扑**组织，不按提问编号。图里有四个信息源（旧代码、新代码、旧卡片、新卡片）与两条平行变化通道（代码通道、文档通道），末端的箭头落在**正确性证明**上。文档围绕这条链路展开，每篇标注它对应图的哪一部分。

## 问题图

```
旧代码 ── Diff ──→ 新代码
   │                  │
   ▼                  ▼
旧知识卡片 ──→ 新知识卡片
                    ↓
             怎么证明改对了？
```

**图的三个要点**（决定了检索方向）：

1. **旧代码与新代码是两个独立节点**，Diff 只是它们之间那条边的载体。这意味着验证时**四个源都在手**，不是「拿 diff 去查卡片」的三元问题
2. **旧卡片与新卡片也是一条边**，与上方代码通道**平行**。两条通道的变化可以不同步，这个不同步本身就是判据
3. **末端箭头指向证明**，不是指向「生成新卡片」。生成不是难点，证明改对了才是

## 与本项目既有设计的衔接

项目已经具备小飞轮的骨架，本专题是在补两个缺口。

**已有（读 `DocGenAgent.md` 核实）**：

- 修订输入已包含**上一版文档**与纠正意见，即项目本就是持续修订
- 一套共用定位规则（路径、路径加章节标题、唯一章节标题、唯一原文片段），无法唯一定位即拒绝
- 一条可直接引用的最小性判据：「只指出退款章节有错，则只能修改退款章节，其余正文必须逐字保留。**框架接收结果时检查这一点**」。注意这是程序化校验，不是模型自评

**缺口一：缺 Diff 触发源**。现有触发是人工给的纠正意见，不是代码变更。

**缺口二：缺「证据不足」状态**。「证据不足 / 无法判定 / 弃权」在 `docs/specs/` 中零命中。

**缺口三（本轮新增）：缺代码版本与卡片版本的对应关系**。`Source.schema.json` 已有 `revision`（注册版本）与 `observedRevision`（观察到的当前版本），`status` 枚举含 `STALE`，且有 `drift` 字段；`KnowledgeLineage.schema.json` 已有 `versionId` 与 `parentVersionId`。**这些字段足以支撑问题图里「旧代码」与「旧卡片」两个节点**，但目前没有把它们连起来做一致性判定的设计。

## 收录标准

- **不引入多 Agent、知识图谱、大规模测试、复杂评测流水线**
- **尽量保持一次 LLM 调用**
- 每篇明确区分**论文已验证**与**本分析建议**
- 论文限 2024 年后（本轮检索范围 2024 至 2026）
