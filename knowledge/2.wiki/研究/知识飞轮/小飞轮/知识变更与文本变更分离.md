# 知识变更与文本变更分离

把「知识变了什么」与「文本怎么变」分开记录，以及为什么这比整篇重生成更好。

论文：Knowledge Pull Requests for Continual Document Authoring
标识：`2609.26634`
链接：[https://arxiv.org/abs/2609.26634](https://arxiv.org/abs/2609.26634)

## 要解决的问题

论文开篇描述的场景与小飞轮几乎重合：

> 文档需要随着新知识从其他来源、语言或时间浮现而**持续修订**，但**现有方法要么在编辑时不考虑什么知识变了，要么从头重新生成**。

**这句话精确描述了你 Q2 的两难**（增量修改 vs 重新生成整张），并指出第三种可能：**在知道「知识变了什么」的前提下编辑**。

## 方法核心

### Knowledge Pull Requests（KPR）

论文提出 **KPR**，一个**持续文档编写框架**，目标是让**每一次变化都可解释**。

三步流程：

1. **抽取 claims**（声明）
2. **过滤并路由到章节**
3. **标记与既有内容的冲突**

### 核心机制：ChangeLog

KPR 的产出是一个 **ChangeLog**，它的关键设计是**分离两件事**：

| ChangeLog 的两个部分 | 内容 |
|---|---|
| **claim proposal** | **知识变成了什么**（哪些事实被新增、修改、废弃） |
| **document diff** | **文本变成了什么**（哪些句子被改动） |

**这个分离是全文最有价值的设计。** 它使「修改是否正确」有了两个独立的检查维度：

- 知识层：claim 的变化是否正确反映了代码变化
- 文本层：文本的变化是否恰好对应 claim 的变化

**这正是你 Q5 三方对比的根本原理**（详见 README 第五节）。

### 评测场景

- **跨语言修订 Wikipedia**
- **更新 RAGTIME 上的查询驱动报告**

## 关键数据

| 对比对象 | KPR 的表现 |
|---|---|
| vs「从源头重写」 | 整合**更多信息**，**更好保留既有内容** |
| vs「从头重新生成」 | 同上，且**「每生成一个 token 增加的信息量最多」** |
| 下游问答 | KPR 修订后的文章**比带搜索的前沿模型更好地支持问答**，且该模型**无法呈现只存在于其他语言的知识** |

### 「每 token 信息量最多」这个指标

这个指标的构造思路很实用：它同时衡量**信息增量**与**生成成本**。

对小飞轮的含义：如果小飞轮的约束是「一次 LLM 调用」，那么**单位调用产出的有效信息量**就是一个合适的效率指标。这比单纯看「改对了没有」更贴合低成本目标。

### 「只存在于其他语言的知识」这条

论文最后一个发现的含义：**KPR 修订后的文章能支持前沿模型加搜索所不能支持的问答**，因为有些知识**只存在于其他语言的版本里**。

对小项目的含义：**同一份代码的不同语言文档可能各有信息**。如果知识库是多语言的，跨语言的知识汇总本身就是一个信息源。

## 对本项目的启发

### 方案要点

**一、把「知识变化」与「文本变化」作为两个独立输出。**

这是本文最可直接采纳的设计。小飞轮的输出不应当只有「一致 / 不一致」，而应当分两层：

| 层 | 输出 | 检查对象 |
|---|---|---|
| 知识层 | 本次代码改动涉及哪些行为声明 | 代码 Diff |
| 文本层 | 卡片文本的哪些部分对应这些声明 | 旧卡片与新卡片 |
| **对照** | 两层是否匹配 | 两者的交叉 |

**这个双层结构让「不必要的修改」变得可识别**：文本层有变化但知识层没有对应变化，就是过度编辑。

**二、「路由到章节」与项目的定位规则是同一件事。**

KPR 的第二步是「过滤并路由到章节」。项目 `DocGenAgent.md` 第 63 行已有更严格的对应机制：**当前文档路径 / 路径加章节标题 / 唯一章节标题 / 唯一原文片段，且无法唯一定位就拒绝**。

**项目的规则比 KPR 更保守**（KPR 是路由，项目是拒绝模糊匹配）。对小飞轮而言，项目既有的规则更适合作为基础。

**三、「标记与既有内容的冲突」这一环是本项目的缺口。**

KPR 的第三步是标记冲突。项目当前的能力是「修订到指定章节」，**没有专门标记「这次改动与既有描述冲突」的环节**。

这与 README 第七节（错误继承）相关：标记冲突是发现旧卡片错误的手段之一。

**四、ChangeLog 是可解释性的载体。**

论文的目标是「让每一次变化都可解释」。对小飞轮的含义：**输出应当包含「为什么改这一句」的依据**，而不只是「改了什么」。

这与项目第 61 行已有要求一致：意见必须保留 `correctionId`、`criterion`、`evidenceRefs` 和 `risk`，**证据不能为空**。

**五、「增量 vs 重生成」的答案倾向增量，但要有理由。**

论文实测 KPR 比重生成**整合更多信息、更好保留既有内容**。这是支持增量路线的直接证据。

但要注意：论文的对比对象是「从源头重写」与「从头重新生成」，**没有与「简单地在旧文本上让模型随意改」对比**。所以这个结论支持的是「**有 claim 层的受控增量**」，而不是「任意形式的增量」。

**六、单位 token 的信息量可以作为一个效率指标。**

如果小飞轮要证明自己比全量重生成划算，这个指标（新增有效信息 / 生成 token 数）比单纯的准确率更贴合目标。

### 与小飞轮 Q2、Q5 的对应

| 你的问题 | 本文的贡献 |
|---|---|
| Q2 增量修改是否可靠 | **给出「有 claim 层的增量」这个可靠形态，并实测比重生成更好** |
| Q5 三方对比是否更可靠 | **ChangeLog 的 claim/diff 分离就是三方对比的分析框架** |

## 局限

**论文实测部分**（可信）：

- KPR 与「从源头重写」「从头重新生成」的对比结论
- 「每 token 信息量最多」
- 跨语言 Wikipedia 修订与 RAGTIME 报告更新的场景

**论文提出但未量化效果的部分**：

- claim 抽取的具体准确率未报告
- 「冲突标记」的准确率与召回率未报告

**本分析提出的建议**（未经验证）：

- 把知识层与文本层作为两个独立输出来设计小飞轮的校验
- 用「单位 token 信息量」作为效率指标
- 这两条在知识卡片场景下未验证

**其他限制**：

- **场景是 Wikipedia 与查询驱动报告，不是代码知识卡片**。Wikipedia 的「知识来源」是外部资料，卡片的来源是代码。**代码有确定的结构（符号、调用），所以卡片场景可以做更多确定性校验**，这一点论文未覆盖
- **「从源头重写」与「从头重新生成」的具体实现**未在摘要中说明，对比的公平性需查原文
- **claim 抽取依赖模型**，而 claim 抽取错误会向下传播：论文未报告这层传播的影响
- **未报告成本数据**（token 消耗、调用次数）。「每 token 信息量最多」是相对指标，绝对成本未知
- **LAGTIME 疑为 RAGTIME**，具体数据集名称需查原文
- 论文未讨论**多次增量累积后的质量衰减**，而这正是 `2608.21964` 与「增量维护」专题关心的问题
