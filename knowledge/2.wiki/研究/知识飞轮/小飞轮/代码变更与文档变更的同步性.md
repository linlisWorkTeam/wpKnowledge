# 代码变更与文档变更的同步性

对应问题图：旧代码 →（Diff）→ 新代码，以及「每一次变更都要更新文档吗」这个问题。

## 为什么需要它

小飞轮的触发源是代码变更，但**不是每一次代码变更都值得更新卡片**。若把全部变更都当触发信号，检查成本会失控；若漏掉该记的，卡片就会静默变陈旧。判断标准是这套机制的第一道关口。

## 论文的核心主张

论文的立场很直接：**每一次代码变更都应当触发一次文档更新**，并把这种更新定义为 **documentation churn**（与 code churn 并列的概念）。

论文的立场根植于项目可持续性，而非形式化推导：代码变动量常被用来评估代码库的稳定性与可维护性，但**可理解性**同样重要。文档承担知识传递的功能，尤其在原维护者离开、新维护者接手时。作者据此认为**文档更新与代码变更的同步程度反映项目的健康度**，对第三方库而言还关系到可信度。

**这是论文的立场，不是实测结论。**

## 实测部分给出了更有用的东西

论文在**三个 GitHub 开源项目**上用**定性分析加仓库挖掘**，考察 code churn 与 documentation updates 在时间上的对齐与相关性。目标是**识别哪些代码变更倾向于与文档同步，以及文档能在多大程度上被自动生成**。

论文标注自己为 preliminary analysis（初步分析），所以结论强度有限。

## 对本项目的启发

### 方案要点

**把「变更是否需要记录」分成两类信号处理，不交给模型判断。**

论文提出的问题是「哪些变更多与文档同步」，但**从论文本身得不到可用的判据清单**（它只做了三个项目、且自述为初步分析）。可行的做法是把这个判断**下沉为确定性信号**，让模型只处理需要语义判断的部分：

| 信号类型 | 判断方式 | 是否耗模型调用 |
|---|---|---|
| 公开接口签名变化 | 确定性提取 | 否 |
| 契约类字段增删 | 确定性对比 | 否 |
| 调用关系变化 | 确定性提取 | 否 |
| 实现细节重构（外部行为不变） | **确定性重构检测** | 否 |
| 行为语义变化 | 模型判断 | 是 |

前四类可程序化，第五类才需要模型。这与项目既有的约束一致：**程序可以推导的内容不要求模型重复手填**。

**不要采用「每次变更都触发」的字面做法。** 论文的「每次变更都应触发」是一种主张，若直接照做会让小飞轮被大量无意义变更淹没。更稳的形态是**确定性信号做门控，模型只处理通过门控的变更**。

### 一个反向用法

既然代码通道和文档通道是平行的两条边，**它们的同步性本身可以当判据**：某次代码变更里出现了「接口签名变化」这类确定性信号，而卡片对应内容**完全没动**，这就是一个高置信度的漏检信号，且**不需要模型判断**。

## 局限

- **论文自述为初步分析**，样本为三个项目，不足以支撑普适的判据清单
- **论文没有给出「哪些变更该记」的可操作标准**，只提出研究框架与相关性分析的方向
- **三个项目的类型与规模未在摘要中说明**，对文档密集型项目的适用性未知
- **「每次变更都触发」的主张未做成本评估**，而成本正是本项目的主要约束
- **确定性重构检测的覆盖率有限**（见「文档一致性」专题：现有重构检测器只识别约三成的行为保持改动），所以第一类信号的门控本身也会有遗漏
