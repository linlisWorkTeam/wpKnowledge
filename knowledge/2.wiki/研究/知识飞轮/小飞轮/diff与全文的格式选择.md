# diff 与全文的格式选择

原始 diff 对模型不自然，以及块级重写的替代方案。

论文：To Diff or Not to Diff? Structure-Aware and Adaptive Output Formats for Efficient LLM-based Code Editing
标识：`2604.27296`
链接：[https://arxiv.org/abs/2604.27296](https://arxiv.org/abs/2604.27296)

## 要解决的问题

大模型越来越多用于代码编辑，但论文指出现行范式的问题：

> **普遍的全代码生成范式存在严重的效率瓶颈**，对需要低延迟和低成本的交互式编码助手构成挑战。

更关键的观察是关于研究重心的偏移：

> 尽管关注点主要在模型能力扩展上，**编辑格式本身在模型训练中很大程度上被忽视了**。

**这直接对应小飞轮的核心架构问题**：喂给模型的应当是原始 Git Diff，还是完整卡片，还是别的格式？

## 方法核心

### 第一步：系统研究传统 diff 格式的缺陷

论文先做了系统研究，结论很具体：

> **脆弱的偏移量（fragile offsets）与碎片化的 hunk** 让生成对 LLM **高度不自然**。

这条诊断解释了为什么很多系统的「让模型输出 diff」路线效果不稳定：

- **偏移量脆弱**：行号一错，整个补丁错位
- **hunk 碎片化**：一次逻辑改动被切成多个不连续片段，模型需要在碎片间保持一致性

### 第二步：结构感知的 diff 格式

论文提出两个替代格式：

| 格式 | 表示单位 |
|---|---|
| **BlockDiff** | **块级重写**，单位是语法上连贯的块 |
| **FuncDiff** | 以**控制结构、函数**等语法连贯单元为单位 |

关键点是**输出单位从「行」变成「语法单元」**。

### 第三步：自适应选择

论文提出 **AdaEdit**，一个通用自适应编辑策略：**训练模型在给定 diff 格式与全代码之间动态选择最省 token 的格式**。

这个设计说明「diff vs 全文」不是非此即彼：**可以让模型自己选**。

## 关键数据

| 指标 | 数值 |
|---|---|
| 准确率 | AdaEdit 配结构感知 diff **与全代码生成持平** |
| 长代码编辑的延迟 | **降低 30% 以上** |
| 长代码编辑的成本 | **降低 30% 以上** |

### 两条解读

**第一，结构感知格式不牺牲准确率。**

这是关键：**准确率持平**意味着换成块级表示不是「用质量换成本」。这打消了采用它的主要顾虑。

**第二，收益集中在长代码编辑。**

「30% 以上」的限定条件是**长代码编辑任务**。对本项目的含义：**卡片越长，格式选择的收益越大**。短卡片可能差异不明显。

## 对本项目的启发

### 方案要点

**一、不要喂原始 unified diff 给模型。**

这是本条最直接的结论。论文的实验证据：**脆弱的偏移量与碎片化 hunk 让生成对 LLM 高度不自然**。

对小飞轮的含义：即使输入是 Git Diff，也应当**先转换成结构化的表示**再喂给模型。这与「文档相似度」专题的 `2512.19883` 结论一致（把改动分解成替换/删除/新增的有序活动序列，F1 提升最高 13.54%），本条的增量在于**给出了「为什么不自然」的机制解释**（偏移量 + 碎片化）。

**二、输出格式用「章节级重写」而不是「行级补丁」。**

BlockDiff 与 FuncDiff 的对应物在文档场景是**章节级重写**：模型不输出「第 12 行改为 X」，而输出「『取消订单』这一节的完整新内容」。

**这个设计对项目特别合适**，因为：
- 项目第 63 行的定位规则本来就是**章节级**的（路径加章节标题、唯一章节标题）
- 项目第 43 行的最小性校验按**章节**判断（范围外正文逐字保留）
- 章节级重写与「范围外逐字保留」天然兼容

**三、「diff vs 全文」可以让模型选，但本项目建议固定。**

AdaEdit 的自适应选择需要**训练**。本项目不做训练，所以应当在两个选项里固定一个。

基于上述第二点，建议**固定为「旧卡片全文 + 结构化改动清单」**，理由是：
- 模型能看到完整上下文（避免 diff 的碎片化问题）
- 需要改动的范围由结构化清单明确（避免模型自己找）
- 与项目的章节级定位与校验机制一致

**这是本分析提出的建议，论文只证明「自适应选择可行」，未验证固定选择的等效性。**

**四、成本收益取决于内容长度。**

论文的 30% 收益来自**长代码**编辑。对本项目的实务判断：**卡片长度决定这个优化是否值得做**。可以先测量本项目的平均卡片长度，再决定是否引入。

**五、这个方向的证据强度需要注意。**

论文的结论是关于**代码编辑**的。文档编辑与代码编辑有一个重要差别：**代码有明确的语法单元（函数、控制结构），文档只有章节与段落**。

所以「块级」在文档场景的对应物是**章节**，粒度更粗。这个映射的合理性需要本项目自行验证。

### 与小飞轮 Q2 的对应

你 Q2 问「基于旧卡片和 Git Diff 只更新受影响内容是否可靠」。本文的贡献是**输入输出格式这一层**：

| 格式选择 | 本文的结论 |
|---|---|
| 输入：原始 diff | **不好**（偏移量脆弱、hunk 碎片化） |
| 输入：结构化改动清单 | 更好（与 `2512.19883` 一致） |
| 输出：行级补丁 | 不好（同上） |
| 输出：块级重写 | **好**（准确率持平，成本降 30%） |
| 格式选择 | 可自适应，但需训练 |

## 局限

**论文实测部分**（可信）：

- 传统 diff 格式的缺陷（偏移量脆弱、hunk 碎片化）
- AdaEdit 配结构感知格式：准确率与全代码生成持平
- 长代码编辑的延迟与成本降低 30% 以上

**论文提出但未量化效果的部分**：

- BlockDiff 与 FuncDiff 各自单独使用的效果（摘要只报告了组合结果）
- 自适应选择的决策准确率

**本分析提出的建议**（未经验证）：

- 文档场景用「章节级重写」对应块级重写
- 固定用「旧卡片全文 + 结构化改动清单」而不做自适应
- **章节级重写在文档场景的效果未知**，论文未涉及文档

**其他限制**：

- **场景是代码编辑，不是文档编辑**。语法单元 vs 章节的映射是推断
- 「30% 以上」是相对**全代码生成**的节省，不是相对所有方案的节省
- 论文未报告**绝对准确率数值**，只给「持平」
- 长代码的**长度阈值**未说明（多长才收益明显）
- AdaEdit 需要训练，**训练成本未报告**
- 未讨论**多轮编辑**下格式选择是否稳定
