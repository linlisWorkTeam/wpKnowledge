# 陈旧上下文的一致性协议

把观测链接到来源、检测变化、三态处置。

论文：When Agent Context Goes Stale: Incoherence in Volatile Agent Context
标识：`2610.05281`
链接：[https://arxiv.org/abs/2610.05281](https://arxiv.org/abs/2610.05281)

## 要解决的问题

论文描述的问题与知识卡片的陈旧问题**结构相同**：

> 现代 agent 越来越多地把推理建立在**工具返回的观测**上（例如从工作区读取的文件内容）。然而这些观测背后的数据源**后来可能被用户、其他 agent 或外部工具修改**，而模型**只在上下文窗口里保留着陈旧内容**。

论文指出现有运行时的缺口：

> 现有 agent 运行时**很少支持通知模型「先前观测到的事实已经陈旧」**，导致 agent **复用过期观测，并对当前工作区状态做出错误断言**。

**最后这句是问题的实质**：模型会**误以为陈旧内容仍然有效**，而非单纯「忘了更新」。

## 方法核心

### Concord：上下文一致性框架

论文提出 **Concord**，维护「agent 上下文中的工具观测」与「它们所来自的可变源」之间的一致性。

三个机制：

1. **把每个观测链接到它的来源**
2. **检测来源变化**
3. **用可配置的处理策略**，在复用前**更新、标注或抑制**陈旧上下文

### 三个处置动作

| 动作 | 含义 |
|---|---|
| **更新（update）** | 用新内容替换陈旧内容 |
| **标注（annotate）** | 保留内容但标记为已陈旧 |
| **抑制（suppress）** | 不提供给模型 |

**这个三态设计很关键**：它没有把「陈旧」当作单一状态处理，而是给了三种不同强度的处置。这与「文档一致性」专题的发现一致（简单的二元判定不够用）。

### 通用性设计

论文强调 Concord **适用于不同的 agent 运行时与外部资源，且可容易地扩展到新的运行时-资源组合**。

### 评测基准

论文构造 **ConcordBench**：其中**先前观测到的文件内容在后续编辑后变得陈旧**。

## 关键数据

| 指标 | 数值 |
|---|---|
| 一致性正确率 | **三个前沿模型在所有评测案例中，答案都与恢复后的工作区状态一致** |
| 与 oracle 对比 | **在 recover count 上与 oracle 持平** |
| 令牌效率 | **比最强的非 oracle 基线少 46.4% token** |

### 两条解读

**第一，「与恢复后的状态一致」是评测的核心。**

评测方式是：先让 agent 观测、再改动源、再问 agent 当前状态。**看它的回答是否与改动后的实际状态一致**。

这个评测设计可以直接借用到知识卡片场景：**改动代码后问卡片相关的问题，看答案是否与当前代码一致**。

**第二，46.4% 的 token 节省说明这个机制不昂贵。**

这是关键：一致性维护如果能**省** token（而不是增加），采用它的阻力就小。论文的机制通过**抑制陈旧上下文**避免了重复提供无效信息。

## 对本项目的启发

### 方案要点

**一、「链接到来源」是防陈旧的基础机制，且是确定性的。**

Concord 的第一步是**把每个观测链接到它的来源**。这是**程序化操作，不消耗模型调用**。

对小飞轮的直接映射：

| Concord | 知识卡片 |
|---|---|
| observation | 卡片中的一条声明 |
| source | 该声明依据的符号与代码位置 |
| 链接 | **卡片记录它依据的符号与位置** |
| 检测来源变化 | 提交时校验符号是否仍存在 |

**关键洞察：检测「来源是否变化」比「内容是否正确」便宜得多，而且是确定性的。** 所以小飞轮的第一道检查应当是**失效检测**而不是**内容正确性检查**。

**二、三态处置可以直接映射。**

| Concord 动作 | 卡片场景 |
|---|---|
| **更新** | 自动重新生成该声明 |
| **标注** | 保留但标记「本轮未验证」，进入待人工确认 |
| **抑制** | 暂时不向消费方提供该声明 |

**「标注」这一态对项目最有价值**：它既避免了信息损失（不删除），又避免了误信（标记未验证）。这与 `2605.17926`（见「文档一致性」专题）的「显式标注不可验证陈述」是同一思路。

**三、「可配置策略」说明不同内容可以不同处置。**

论文的处置策略是**可配置**的。对小飞轮的含义：不同类型的声明可以用不同策略：- 接口类声明（可程序化验证）→ 直接更新
- 行为描述类（需语义判断）→ 标注待确认
- 无法定位依据的 → 抑制或降级

**四、这个机制天然支持「一次 LLM 调用」的约束。**

因为**链接维护与变化检测都是确定性的**，模型调用只在「是否要更新内容」这一步发生。这符合你的约束。

**五、ConcordBench 的构造方法可以借用。**

「先前观测 → 源改动 → 检查回答是否与当前状态一致」这个三步模式，可以直接构造小飞轮的评测集。而且它是**自动可判定的**（有 oracle），不需要人工标注。

**六、论文未解决「如何判断该用哪种处置」。**

论文说策略是「可配置的」，但没有给出配置的判据。对小飞轮的含义：**处置策略的规则需要本项目自己定义**。

### 与小飞轮 Q7 的对应

你 Q7 问「如何避免历史错误被增量更新继承」。本文提供的答案分两层：

| 层次 | 机制 | 解决什么 |
|---|---|---|
| 来源变化检测 | 链接 + 变化检测 | **发现「依据已经不在了」** |
| 三态处置 | 更新 / 标注 / 抑制 | **不让失效内容被误信** |

**但本文不解决「依据还在，但内容本来就写错了」这种情况**：那是 `2608.21964` 的范围（陈旧但不失效）。两者互补。

### 与项目现有能力的对照

| 小飞轮需要 | 项目现状 | 差距 |
|---|---|---|
| 声明链接到来源 | 卡片生成时记录溯源（`Source.schema` 有 `observedRevision`） | **部分具备** |
| 检测来源变化 | `Source.schema` 有 `drift` 字段，但是**整文件哈希** | **粒度太粗**（只知文件变了，不知哪段变了） |
| 三态处置 | 无 | **缺** |

**第二行是本项目的一个已知限制**：「增量维护」专题已核实 `Source.schema` 的 `drift` 是整文件哈希。Concord 的做法（观测级链接）比整文件哈希细，可以参考「增量维护」专题里 openwiki 的**行区间哈希**方案。

## 局限

**论文实测部分**（可信）：

- 三个前沿模型在 ConcordBench 上的表现
- 与 oracle 在 recover count 上持平
- 比最强非 oracle 基线少 46.4% token

**论文提出但未量化效果的部分**：

- 「可扩展到新的运行时-资源组合」的通用性声明

**本分析提出的建议**（未经验证）：

- 把三态处置映射到卡片场景
- 「失效检测应当作为第一道检查」的优先顺序
- ConcordBench 三步模式用于构造小飞轮评测集
- **这些映射未经验证**

**其他限制**：

- **场景是 agent 的工具观测，不是长期知识卡片**。agent 上下文是**会话内**的（分钟级），卡片是**跨版本长期存在**的（月级）。时间尺度差异大，失效的积累模式不同
- **「观测」是单次读取的文件内容**，而卡片是**模型的生成物**，本身可能有错。Concord 的机制只能发现「来源变了」，**发现不了「生成时就错了」**
- **46.4% token 节省是相对最强非 oracle 基线**，不是相对所有方案
- **ConcordBench 的规模**未在摘要中说明
- **未讨论并发修改**（多个源同时变化时的处理）
- 论文未报告**误报率**（源未变但被判为变了）
