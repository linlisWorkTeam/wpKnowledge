# 技能静默陈旧与维护失败

把版本发布转换当作维护任务来测，以及「陈旧为什么不发出信号」。

论文：Repo2Skill-Evo: Repository Skills Go Stale in Silence
标识：`2608.21964`
链接：[https://arxiv.org/abs/2608.21964](https://arxiv.org/abs/2608.21964)

## 要解决的问题

论文的研究对象与本项目的形态**高度同构**：

大模型 agent 越来越多地在演化中的软件仓库上工作，而成功依赖**仓库特有的过程性知识**（该调哪些 API、跑哪些脚本、当前版本期望什么约定）。agent 技能把这类知识**外化成可复用单元**，已有工作证明它们能提升 agent 表现。

**论文问的是：这种提升是否持久？**

### 核心诊断：外化让衰减变得不可见

论文的洞见值得逐字引用：

> **让技能有用的版本特异性，同样让它脆弱**：在一次发布之后，它可能变陈旧**而不发出任何显式信号**，同时继续提供过时的指导。**把知识外化到技能里，可能反而让它的衰减变得不可见。**

**这段话直接命中小飞轮 Q7 的核心**：知识卡片本身就是「外化的知识」，所以它天然带着「陈旧而不自知」的性质。

## 方法核心

### 任务设计（与本项目几乎同构）

论文把**每一次版本发布转换当作一次技能维护任务**：

> 给定一个 **V1 技能集**和**官方的 V1 到 V2 补丁**，agent 必须**更新过时的技能内容，同时保留仍然有效的指导**。

换成小飞轮的语言：

| 论文 | 小飞轮 |
|---|---|
| V1 技能集 | **旧知识卡片** |
| V1→V2 官方补丁 | **Git Diff** |
| 更新过时内容 | 增量修改 |
| 保留仍有效的指导 | **修改最小性**（不能乱改） |

### 评测指标：同时平衡两个方向

论文用的指标是 **patch-grounded removal metric**，明确**平衡「陈旧内容的召回」与「过度编辑的精确」**。

这个指标设计本身就说明：**「该删的删掉」与「不该改的别改」是两个需要同时考虑的相反目标**。

### 评测规模

- **57 个真实世界仓库**
- **105 个选定的发布转换**

## 关键数据

| 指标 | 数值 |
|---|---|
| 失效普遍性 | **每一次转换都使 V1 技能集的一部分失效** |
| 六个前沿 agent 的表现 | **29.9%~69.7% avg@3 macro F1** |
| 指标口径 | patch-grounded removal metric（平衡陈旧召回与过度编辑精确） |

### 两种相反的错误（最重要的发现）

论文明确指出跨多次运行的主导错误是**成对出现**的：

**错误一：对受影响文件的覆盖不完整，导致陈旧内容原封不动留下。**

对应小飞轮 Q9「仅验证修改部分可能遗漏间接失效的旧描述」。

**错误二：编辑过宽，与更高的召回相关但精确度更低。**

对应小飞轮 Q4「修改最小性」。

**这两条错误互相拉扯**：想少漏就得改得多，想精确就容易漏。论文的结论是前沿 agent 在两端都没做好。

### 论文的收尾判断

> **仓库技能在静默中变陈旧，即便前沿 agent 也无法可靠维护它们。**

这句话的分量在于：**六个前沿 agent，最高也只有 69.7%**。

## 对本项目的启发

### 方案要点

**一、「每次改动都有内容失效」是这个量级的实测事实。**

**105 次转换，每一次都使部分 V1 失效。** 对小飞轮的含义：**不能假设「大部分改动不需要更新卡片」**。这个数据支持「每次 Git Diff 都触发检查」的设计，而不是靠抽样或定期检查。

注意这条与「过滤重构」不矛盾：重构属于**不该触发文档更新**的改动，而这条说的是**在真实发布转换中，失效是常态**。两者可以并存：重构被过滤掉之后，剩余改动里仍有相当比例需要更新。

**二、29.9%~69.7% 是「同类任务」的现实上界。**

这个区间是**前沿 agent** 的水平，用的是平衡两端的指标。对小飞轮的含义：

- 报出高准确率前先怀疑判据太宽
- 小飞轮应当定位为**发现问题供人工判断**，而不是**自动改对**
- 这个数字也说明「一次 LLM 调用」的约束是合理的：论文用的 agent 更复杂，效果也只有这个水平

**三、「陈旧不发信号」意味着检测必须主动。**

论文的诊断是**衰减变得不可见**。所以小飞轮不能等「出了问题」再检查，必须在**每次改动时主动检查**。这是 Git Diff 作为触发源的核心理由。

**四、两种相反错误必须同时度量，不能只优化一个。**

这是对小飞轮判定设计的直接约束：

| 只优化一端 | 后果 |
|---|---|
| 只追求「不漏陈旧」 | 大量过度编辑，精确度下降 |
| 只追求「最小改动」 | 间接失效的旧描述留下 |

所以小飞轮的输出应当**同时给出两个数**：漏检（应更新但未更新）与误改（不应更新却改了）。这与「文档一致性」专题的 CommitEval 发现一致（**特异度只有 63.8%**，即误报是主要问题）。

**五、指标设计要平衡，不能只看一端。**

论文的 patch-grounded removal metric **专门设计成平衡两端**。这提示一个具体做法：**不要用单一分数**，而是分别报告「陈旧内容的召回」与「过度编辑的精确」。

**六、「保留仍有效的指导」被单独列为任务要求。**

论文的任务描述里，「更新过时内容」和「保留仍有效的指导」是**并列的两个要求**。对本项目的含义：小飞轮的 prompt 应当**显式包含这两个要求**，而不是只说「更新卡片」。

项目 `DocGenAgent.md` 第 69 行的 prompt **已有「保留范围外正文」**，与这里的「保留仍有效的指导」方向一致。可以补充的是**「保留范围内仍然有效的表述」**：现在的约束只管范围外。

### 对本项目判定标准的直接影响

这篇论文给出了小飞轮**唯一有实测支撑的预期值**：

| 指标 | 参照值 | 来源 |
|---|---|---|
| 同类任务前沿水平 | **29.9%~69.7% macro F1** | 本文（六个 agent，105 次转换） |
| 每次改动的失效率 | **每次都有部分失效** | 本文 |
| 主导错误 | 覆盖不完整 + 编辑过宽 | 本文 |

**据此，小飞轮宣称超过 70% 的准确率时应当先验证评测口径。**

## 局限

**论文实测部分**（可信）：

- 57 个仓库、105 次发布转换
- 六个前沿 agent 的 29.9%~69.7% macro F1
- 每次转换都使部分 V1 失效
- 两种相反错误的观察

**论文提出但未量化效果的部分**：

- 「外化让衰减不可见」这个判断是**定性诊断**，论文未给出「不可见」的可操作度量方式

**本分析提出的建议**（未经验证）：

- 小飞轮应该同时报告漏检与误改两个数
- prompt 应补充「保留范围内仍有效的表述」
- 这些是从论文机制推导的设计建议，未在知识卡片场景验证

**其他限制**：

- **场景是 agent 技能，不是知识卡片**。技能是「怎么做事」的过程性知识（该跑什么脚本），卡片是「模块做什么」的描述性知识。**过程性知识的失效更快更明显**（脚本路径会直接失效），而描述性知识可能长期不失效。所以本项目的失效率**可能低于**论文的「每次都有失效」
- **指标是 patch-grounded removal metric**，其具体计算方式需查原文
- **「六个前沿 agent」的具体身份与配置**未在摘要中说明
- **avg@3** 说明做了三次采样取平均，单次运行的方差未报告
- 论文未给出**增量维护与全量重新生成的效果对比**，无法判断增量是否划算
