# 读取源码

DocGen 与 TestGen 都要读源码，而单仓三十万行、全部代码仓上亿行。本目录回答的问题是：**怎么在不丢代码信息的前提下，把读源码的成本控制在上下文预算内。**

项目自己把这一项列成了待调研：

> 业务分组、上下文预算及跨模块依赖处理尚未实现。按业务主题分批汇总、保存中间摘要、发现问题回查源码或请求补充分析**仍是待论文调研的方案**。2026-09-10 已确认留待下一版本确定，**当前文件均分和一次汇总不算这些目标完成**。

现状是 DocGen 把去重后的文件列表**均分**给 0 到 5 个 Worker，汇总一次成文；TestGen 拿「模块、源码和公开接口」直接生成测试。两者都缺同一件事：按什么切、切完怎么保证没丢、跨模块依赖怎么带过来。

## 问题的真实形状

先把「信息不损耗」和「上下文不爆炸」这两个目标的关系说清楚，因为它们是冲突的，冲突点决定了所有方案的取舍。

- **不损耗**要求：代码里的行为语义（边界条件、调用关系、数据结构、错误处理）在压缩后仍然可判断
- **不爆炸**要求：单次模型调用的输入远小于三十万行，甚至远小于模型宣称的上下文窗口

冲突在于：任何压缩都是有损的，而「有损」与「不损耗」直接对立。所以真正能做的不是无损压缩，而是**把损失变成可控、可检查、可回退的**：结构性压缩（只丢格式不丢语义）、按需展开（需要细节时能回去取）、以及把迭代逻辑移出模型上下文（模型不负责遍历）。

后面所有论文都落在这三条上。

## 三个立刻能用的数字

调研里最有价值的几条实测，先列出来：

- **有效上下文远小于宣称值**。`2509.21361` 定义并测量了最大有效上下文窗口，实测发现模型在远未达到宣称上限时准确率就开始下降。`2605.14362` 引用同类结论并直接在做「在最大有效上下文窗口约束下的过滤」。这意味着按模型的标称窗口做预算本身就是错的，安全区大概在 30% 到 60%。
- **渐进式披露只买到上下文，不买到智能**。`2607.17598` 的原话是「Progressive disclosure buys context, not intelligence」。语料小的时候强 agent 自己 grep 就够了，披露机制一点用没有；只有语料大到原生导航装不下时才起决定作用。而且**第二层路由从不复现收益，有时反而直接破坏准确率**，一层就够。
- **摘要的字数几乎不随输入增长**。`2607.01425` 实测 GPT-5 等大模型无论输入多少内容，生成的摘要都约 200 词。这解释了为什么层级越高语义相似度越低（各模型下降 10% 到 20%）。

## 六条技术路线

按「解决哪个环节的什么问题」归类，不是按论文领域归类。

### 路线一：结构化压缩，保住语法完整性

代表：`2506.15655` cAST。

按抽象语法树递归切分，先自顶向下把大的语法节点尽量整块放进一个切片，超过上限的节点才拆，拆完再做贪心合并把相邻的小兄弟节点合起来。四个设计目标里的第四点最关键：**把所有切片拼回去必须能逐字还原原文件**。

这一条直接回应「怎么保证不丢」：压缩过程可以是可逆的。项目里 DocGen 记录采信了哪些分析、TestGen 把证据限定为精确文件路径，都属于同一类做法可以让切分边界可审计。

### 路线二：按需展开，模型只拿摘要加引用

代表：`2605.04050` LCM、`2607.17598` 渐进式披露。

LCM 的核心设计值得逐条抄：

- 设一个 token 阈值，低于阈值的文件正常放进上下文，**高于阈值的存到外部，上下文里只放一个紧凑引用**（不透明 ID、文件路径、预计算的探索摘要）
- 探索摘要由**按文件类型分派的生成器**产出：结构化格式（JSON / CSV / SQL）做 schema 与形状提取；**代码文件做结构分析，例如函数签名与类层次**；非结构化文本才交给模型写摘要
- 文件内容**只存在于文件系统**，上下文里永远只有路径引用。理由是生产环境下被操作的文件可能到几十 GB，复制不可行
- 文件 ID 沿摘要 DAG 传播：即使经过多轮压缩，模型仍然知道有哪些文件、可以重新读取

`2607.17598` 补上了「几层合适」的实测答案：一层。它对比了原始导航、单层披露、层级披露三种做法，在单本书任务上三种没有差别，在图书馆规模上单层披露胜出，**层级披露从不复现收益**。

### 路线三：把迭代移出模型上下文

代表：`2605.04050` 的算子树、`2607.01425` 的关键词桥接。

这是最有启发的一条，也是最容易漏掉的一条。

LCM 区分了「符号递归」和「算子级递归」。符号递归是让模型自己写循环去遍历切片，灵活但要求模型每次执行都正确处理错误、并发与状态管理，在生产环境引入方差。算子级递归把循环交给确定性的引擎：模型只发起一次工具调用，指定逐项提示词与输出 schema，**引擎负责全部迭代、并发与重试**。原话说这是把控制流从随机层移到确定性层。

实测结论很硬：在 32K 以上，Volt（LCM 的集成）在每个长度上都超过 Claude Code，差距在 256K 时是 10.0 分、512K 时是 12.6 分。原因分析写得很清楚：**模型从不看见原始数据**，它只指定逐项提示词和输出 schema，引擎返回聚合结果。这就消除了「聚合类任务的上下文饱和」这个失败模式。

Agent4cs 用的是同一思路的变体：汇总文件夹时，直接把所有子文件夹摘要放进提示词是不可能的（上下文限制），所以引入关键词提取 Agent，用关键词作为层与层之间的桥接，得到更浓缩的表示且输入规模可控。

### 路线四：内容过滤，先扔掉不该读的

代表：`2605.14362`、`2406.18294`。

`2605.14362` 的结果有一个反直觉点：**按文件大小过滤（79.6% 平均削减、0.30 毫秒开销）比按扩展名过滤更稳定**，标准差 13.2% 对 29.3%。原因是大文件与小文件的 token 成本差异比扩展名差异更能代表真实开销。

更有价值的是它指出的失败：`NoFilter`、`GitignoreFilter`、`MinifiedFilter` 三个过滤器在其语料上**削减为零**。原因是主要的 token 成本来自**被有意提交的数据文件**（CSV / HDF5 / Pickle），它们不被 .gitignore 覆盖、不是压缩文本、也不在初始的魔数表里。

对项目的直接含义：三十万行的代码仓里，真正吃掉预算的可能不是代码，而是随仓库提交的数据与产物文件。先测量再设计过滤器，别照着直觉做。

### 路线五：依赖图与调用链

代表：`2608.01927` 部分依赖图、`2507.14791` 调用链感知、`2605.16352` 词法锚定图探索。

DocGen 的待办里明确写了「跨模块依赖处理尚未实现」。这一批解决的就是它：不是按目录结构切，而是按依赖关系取上下文。`2608.01927` 用**部分**依赖图而不是完整图来降低开销，这个「部分」的取舍是重点。

对 TestGen 尤其相关：写测试需要知道被测函数的调用者与被调用者，否则会生成编译不过或断言错位的用例。

### 路线六：层级汇总的正确做法

代表：`2607.01425` Agent4cs、`2501.07857`。

Agent4cs 用祖父-父-子三层滑动的层级框架，逐层向上构造摘要直到仓库顶层。每层都配一个质量保证 Agent 审查草稿并提改进建议，汇总 Agent 迭代修订。

但它的实测给了一个重要警告：**语义相似度从低层到高层逐渐下降，各模型降幅 10% 到 20%**。原因是高层汇总要在受限字数内捕捉更抽象的概念。

还有一条元发现值得注意：论文发现紧凑模型（Qwen3-8B 0.872）在关键词覆盖率上反超大模型，进一步分析发现**token 长度是混淆因素**，小模型写的摘要更长（800 词对 200 词）因而覆盖率天然更高。这提醒我们：层级汇总类评测要控制摘要长度，否则比的是啰嗦程度。

## 设计空间：三套可选组合

### Option A：结构化切分 + 确定性聚合

```text
# 输入：本次模块的文件列表、源码根目录、预算
# 输出：候选知识文档或测试集

1. 过滤        按文件大小排掉不该读的（数据与产物优先）
2. 切分        按 AST 递归切分，超限才拆，拆完贪心合并
               每个切片记录：文件路径、起止位置、语法节点类型
3. 分派        模型只发起一次工具调用，声明逐项提示词与输出 schema
               引擎负责遍历、并发、重试与聚合（控制流在确定性层）
4. 汇总        按需分层；一层为准，不建第二层路由
5. 回查        模型拿到的是摘要加文件引用，需要细节时按引用重读
```

- **需要什么数据**：AST 解析器（C/C++ 与 TS 都要覆盖）；文件分类规则；预算阈值
- **优点**：切分可逆、边界可审计；迭代不入模型上下文，聚合任务的上下文饱和被消除；与项目现有的「Worker 材料含完整片段与源码依据」设计直接衔接
- **缺点**：AST 切分对宏与条件编译密集的 C/C++ 有难度；算子级递归需要引擎侧实现并发与 schema 校验
- **实现复杂度**：中高

### Option B：只做过滤与预算，不引入摘要

```text
1. 测量        先看 token 成本实际分布在哪（别假设是代码）
2. 过滤        按大小加规则排除数据与产物文件
3. 预算        按有效窗口而非标称窗口定阈值（取 30% 到 60% 区间）
4. 直读        预算内直接读原文，超预算再触发摘要
```

- **需要什么数据**：一次真实的成本测量
- **优点**：改动最小，先摸清真实瓶颈；`2605.14362` 证明按大小过滤性价比最高
- **缺点**：不解决三十万行本身的规模问题；不做跨模块依赖
- **实现复杂度**：低

### Option C：依赖图取上下文

```text
1. 建部分依赖图   只覆盖当前模块及其直接调用者与被调用者
2. 按查询取子图   不是按目录切，是按依赖关系取
3. 接口层完整保留 签名、类型、契约全留，实现体按预算决定
4. 实现体按需    走 Option A 的摘要加引用
```

- **需要什么数据**：依赖抽取能力（调用关系、类型引用）
- **优点**：直接补上项目自认的「跨模块依赖处理尚未实现」；TestGen 尤其需要
- **缺点**：构建与维护依赖图的成本；「部分」的边界怎么定需要实验
- **实现复杂度**：高

### 三条建议的落地顺序

先做 **Option B 的测量**，因为 `2605.14362` 已经证明直觉会错（真正的开销可能是提交进仓库的数据文件）。拿到真实分布后再决定切分粒度。

然后做 **Option A 的切分与算子级递归**，这两块是 DocGen 与 TestGen 共用的底座。

**Option C 放最后**，它依赖前两步产出的切片与文件分类信息。

**贯穿始终的一条纪律**：任何摘要都要带回到原文的引用。项目已有溯源设计（每段知识标注对应源码位置），摘要层应当复用同一套引用，而不是另建一套。

## 研究缺口

**没有发现同时解决「三十万行规模 + 零信息损耗 + 上下文受控」的现成方案。**

逐条对照：

- **结构化切分**：cAST 做到了可逆，但它只解决「怎么切」，不管切完怎么读、怎么跨模块
- **按需展开**：LCM 最完整，但它的场景是 agent 会话中的工具返回，不是「一次读透一个模块生成文档」；它的预算是按会话累积算的
- **算子级递归**：机制上最贴近本项目，但论文的实验是聚合类任务（OOLONG），不是文档生成
- **有效窗口**：`2509.21361` 给了测量方法，但**没有给「哪种策略在有效窗口约束下最优」的答案**
- **层级汇总**：Agent4cs 直接对口，但它自己报告高层相似度下降 10% 到 20%，也就是**它没解决信息损耗，只是量化了损耗**
- **跨模块依赖**：`2608.01927` 与 `2507.14791` 都在代码生成场景，不是在知识文档场景

最关键的缺口是：**没有论文直接回答「压缩到什么程度会开始影响下游任务质量」**。现有工作都在测自己的下游任务（生成代码、回答问题），而本项目的下游任务是「Coder 基于这份知识能否重建出与源码相似度 80% 的实现」。这个下游反馈信号是独特的。

### 最合理的组合来源

| 缺什么 | 从哪来 | 具体拿什么 |
|---|---|---|
| 怎么切 | cAST `2506.15655` | AST 递归切分，拼回可还原 |
| 切完怎么读 | LCM `2605.04050` | 阈值外置 + 按类型分派摘要 + 文件引用传播 |
| 迭代怎么做 | LCM 算子级递归 | 控制流移到确定性层，模型只声明提示词与 schema |
| 几层披露 | `2607.17598` | 一层，别做第二层路由 |

### 需要项目先定的一件事

**用哪个信号度量「信息有没有丢」。** 这是本目录最重要的一条建议。

论文各自用自己的下游指标，项目有一个别人没有的现成信号：**知识门禁的重建相似度**。把「压缩策略」当成一个自变量，把「Coder 基于这份知识重建的实现与源码的相似度」当成因变量，就能测出每种压缩策略的信息损耗率。

这比任何论文的评测都更贴合项目，因为下游客观就是项目的下游。建议在实现任何压缩机制之前，先把这个测量搭起来，否则无法判断机制是否有效。
