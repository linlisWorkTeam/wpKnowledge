# 信息损耗率测量方案

本目录的结论是：**没有论文直接回答「压缩到什么程度会开始影响下游任务质量」**。缺的不是某个机制，而是一个**测量方法**。

这一篇把测量方案写出来。核心思路是：项目有一个论文都没有的信号（门禁的重建相似度），把它从「一个结果指标」改造成「衡量压缩策略的自变量实验」。

## 为什么需要单独的测量

前面几篇给出了六条压缩路线，但没有一条能回答「用了它之后丢了多少」。原因是所有论文都在测**自己的**下游任务：生成代码、回答问题、检索片段。而项目的下游是「Coder 基于这份知识能否重建出与源码相似度 80% 的实现」。

信息损耗在论文里是隐含的：如果下游指标没掉，就认为压缩没伤到信息。这个推理有两个漏洞，本文后面的两篇论文会分别证明。

## 三个概念的区分

测量之前要把三件事分开，混在一起就测不出东西。

- **体积压缩率**：压缩后的 token 数除以原文 token 数。这是最容易测的，也是最没有信息量的
- **答案保持**：下游任务还能不能过门禁。这是当前项目唯一在看的
- **依据保持**：支撑这个结果的证据链是否还在

第三项是缺口所在。项目当前的门禁只看第二项，而第二项可以在第三项已经损坏的情况下依然通过。

## 核心方法：固定轨迹重放

这个方法来自 KV 缓存压缩的评测（`2608.01631`），思路可以直接迁移。

它的关键设计是**把推理内容固定住**，只让压缩方法发挥作用。这样测出来的差异就可以归因到压缩本身，而不是归因到「模型这次生成的轨迹恰好比较简单」。

对照到项目：

```text
# 普通评测（当前项目做的）
源码 → [压缩策略] → DocGen → 知识文档 → Coder → 实现
                                    ↑
                        只测最终相似度

# 固定轨迹重放
源码 → 一次性生成完整轨迹（读全部源码，不压缩）→ 基准知识文档
     ↓
     把这份基准文档按不同的压缩策略降级
     ↓
     Coder 基于降级后的文档重建实现 → 测相似度
                                    ↑
                        差异归因到压缩策略
```

两种做法的区别很关键。第一种把所有变量一起变（压缩方式、模型当次的生成质量、轨迹长度），得到的差异无法归因。第二种固定了「原本能写出什么」，单独看「压缩后丢了多少」。

### 为什么这一步不能省

论文给的理由是：在端到端设置里，压缩不仅影响已有轨迹的保留，还影响**未来轨迹的生成**、生成长度、中间错误。所以端到端的数字「可以作为部署相关性的检查，但**不能作为定位保留失败的依据**」。

换句话说：端到端看结果是好的，但看不出问题出在哪。固定轨迹重放才能定位。

## 三个测量轴

论文用三个互补的轴测同一件事，这个三轴结构值得照搬。

### 轴一：下游结果

项目的版本是门禁通过与否加重建相似度。这一轴项目已经有了。

### 轴二：对错链一致性

这是本文最有价值的借鉴概念。论文定义了 **RWAC（Reasoning Wrong Answer Correct，推理错但答案对）**：最终答案正确，但推理过程不完全正确。论文把它计为分子，给出两个指标：

- **针对全部样本**：衡量「一个方法在整体上多常产生看起来正确但无支撑的答案」
- **只针对答对的样本**：衡量**条件可靠性**，即在那些能过结果判据的答案里，推理无支撑的比例

论文特别说明为什么要两个都给：第一个指标低可能只是因为准确率低；第二个才真正检验「通过了结果判据的输出是否有效」。

迁移到项目：

```text
门禁通过但依据不足 = RWAC 的项目版本

定义：Coder 基于知识文档重建出的实现与源码相似度 ≥ 80%，
      但知识文档本身存在下列问题之一：
        - 某段描述在源码里没有对应依据
        - 有依据但意图描述错了（比如把只返回 -1 的函数说成查数据库）
        - 缺少源码里明确存在的边界条件

两个指标：
  全体占比    = 有问题文档数 / 全部文档数
  条件占比    = 有问题文档数 / 门禁通过的文档数   ← 这才是关键
```

**第二个指标直接回答「怎么知道通过门禁的文档是不是侥幸通过的」。** 这是项目现在完全没有的信息。如果条件占比很高，说明门禁的通过在相当程度上是靠下游模型的补全能力，而不是靠知识文档的完整。

### 轴三：扰动保真度

论文的第三个轴是扰动：往推理轨迹里插入一个错误声明，看模型会不会改答案。

迁移到项目：

```text
做法：往知识文档里插入一处明确的错误陈述（例如把一个边界值写错），
      让 Coder 基于它重建，看重建结果是否沿用了这个错误。

保真 = 重建结果在扰动下保持稳定（没有沿用错误）
偏置率 = 重建结果采纳注入错误的比例
```

这一轴测的是「知识文档有多大的权威性」：如果注入一个错误，下游就跟着错，说明文档是有效的说明来源；如果注入错误后结果不变，可能是模型自己从别处补全了，等于文档没起作用。

论文对这一步的定位说得很清楚：由于扰动是一个明确的答案式声明，这个指标是「对无支撑推理内容鲁棒性的受控探针」，不是完整的对抗鲁棒性基准。

### 三轴的关系

```text
轴一 结果      能不能过          低成本，项目已有
轴二 依据      过了但有没有依据   中成本，需要判据
轴三 扰动      文档起没起作用     中成本，需要构造扰动
```

## 一个反直觉的结论：加预算不一定解决问题

这篇论文的第四个研究问题问的是「给更多缓存能不能消除答案与依据的差距」。

结论是**不能**，而且有一段话对本项目的参数设计直接相关：

> 更大的预算通常能改善压缩模型的准确率，但答案与链的一致性、扰动保真度仍然存在很大差距。**准确率是第一个恢复的指标。**
>
> 更大的预算可以在消除答案与依据差距之前先改善最终答案。它能恢复足够的信息去回答，有时也足够给出一个看起来合理的解释，**但仍然无法保留稳健推理所需的依赖与验证结构。**

这段是本目录里最该记住的一条实测结论：**加预算会让结果指标先恢复，依据指标后恢复。** 如果只看结果指标，会得出「预算够了」的错误结论。

对项目的含义：如果发现知识质量不够，第一反应通常是「给模型更多源码」。这一条说明这个反应会让门禁通过率上升，但**依据的完整性可能仍然很差**。两个指标必须分开看，否则会被第一个恢复的指标骗过去。

论文还指出瓶颈因任务而异：某些任务里持续瓶颈是链的有效性（证明证据分散在许多中间状态里），另一些任务里显式依据恢复得容易但扰动保真度始终低于基线。

## 判据怎么落地：实体追踪

轴二需要「依据是否还在」的判据。`2410.14748` 提供了具体做法，分两级。

### 第一级：实体验证

从代码和文档**两侧**分别抽实体，然后做映射：

- 代码侧用程序分析抽取（词法分析后解析成 AST，得到变量名、类名、函数名的细粒度分类）
- 文档侧用命名实体识别，采用代码摘要专用的标注集
- 映射后找出**只出现在文档里、不在代码里**的实体，这类叫 **ungrounded（无根据）**，包含这些实体的句子标为外在幻觉

论文给了一个很有说服力的例子：文档里出现了 `int16` 这个数据类型。它在 C、C++、C#、Go 里是合法的，但在被描述的 Java 代码里不存在。模型的错误来源正是**跨语言的记忆混淆**。这个错误对项目尤其相关：项目同时覆盖 TypeScript 与 C/C++，跨语言的类型与 API 混淆是高概率错误。

### 第二级：实体意图验证

实体存在不代表描述正确。论文的例子：`jobId` 是正确的实体，但「从数据库检索 jobID」这个上下文是错的。

做法是抽出包含该实体的句子构成「意图上下文」，然后验证意图与代码是否一致。

**这里有一个值得记的负面结果**：论文尝试过 few-shot 提示（把各种幻觉类型的例子放进提示），**性能反而下降，原因是提示变长**。所以判据用 zero-shot 加规则启发式，不要堆例子。

### 阈值的确定方式

论文的阈值不是拍脑袋定的：先做人工标注，当平均有 1.33 个实体的意图被错误描述时，人工把摘要评为「一般」或「差」，于是把阈值定为 1。

这个做法值得项目借鉴：**判据的阈值应当来自人工作为参照的标注，而不是从技术指标倒推。**

## 一个重要的负面参考：代理指标可能与有用性无关

轴二和轴三用的是代理指标，所以必须回答「这些代理指标能不能预测真实的有用性」。`2608.04195` 做了一件很有价值的事：它提出四个维度（正确性、抽象度、简洁性、流畅性），然后测每个维度与下游任务表现的相关性。

结论有两点，方向相反：

- **正确性相关性最强，抽象度次之**，比最好的基线高出多达 **14 倍**
- **简洁性和流畅性，虽然被人类开发者广泛看重，对下游消费者基本不显著**

论文的结论是「什么让摘要有用，取决于任务与消费者」。

对项目的直接含义：如果项目要给知识文档的质量打分，**不要平均加权四个维度**。简洁性与流畅性对人类读者重要，但对项目真正的消费者（Coder）可能无关。这一条与项目已有的门禁立场一致（相似度只用于归因，不用于门禁），但给出了一个新的可能性：**正确性类维度可以进入门禁，而形式类维度不该进。**

### 消费方是「重建代码」时的特殊含义

SONAR 的做法对项目有额外价值：它的正确性维度用的是**往返重建**，把文档重新生成代码，再与源码做功能相似度比较。论文明确说这是 Round-Trip-Correctness 这个既有思想的延伸。

**这正是项目飞轮的形状。** 区别在于项目已经把它做成了主循环（Coder 重建实现），而 SONAR 用它来评测摘要质量。这说明项目的方向在文献里是有依据的。

功能相似度的算法论文用的是差分模糊测试：现场生成测试输入集，两边都跑，相似度定义为输出相同的输入比例。论文解释为什么不用别的方法：

- **单元测试不可行**：可用的代码摘要数据集里几乎没有附带测试用例的
- **基于参考的指标（如 CodeBLEU）有表层偏差**，无法推理更深的代码语义

项目的场景里「单元测试不可行」这个理由不成立：TestGen 就是干这个的。所以项目可以比论文做得更强：用 TestGen 生成的测试集做功能相似度，比差分模糊测试更有针对性。

## 落地顺序

```text
零  测量体积压缩率
    最低成本，先知道每种策略压掉多少
    （提醒：`2605.14362` 显示真开销可能是提交进仓库的数据文件，
      不在业务代码上，所以这一步的分布要先看清楚）

一  搭固定轨迹重放
    生成一份「不压缩」的基准知识文档，作为后续对照
    这是整个方案的地基，必须先有

二  加轴二（对错链一致性）
    先用实体验证这一级，规则化、成本低
    得到「条件占比」这个项目现在没有的数字

三  加轴三（扰动保真度）
    需要构造扰动，成本高于轴二

四  用轴二的结果反推压缩策略的参数
    切片大小、汇总层数、外置阈值，都据此定
```

**关键纪律**：这个测量必须在实现压缩机制**之前**搭好。理由是本目录反复出现的同一个问题：没有基线就无法判断改动是否有效。`2605.14362` 的实测（三个看似合理的过滤器削减为零）和 `2608.08008` 的负面结论（QD 归档不比随机更好）都是同一个教训。

## 与项目现有设计的衔接

### 落点

测量不进入门禁，而是**平行于门禁**的一组观察指标。理由有两条：

- 项目已经明确「相似度、模型自评分和自然语言『通过』不能覆盖这些条件」，把新的代理指标塞进门禁会破坏这个边界
- 刚引的实测（代理指标可能与有用性无关）要求先验证相关性，再决定是否进门禁。轴二和轴三都得先证明自己能预测下游结果

### 记录位置

测量结果与知识版本绑定比较自然。项目已有 `qualityScore`（单值）与 `qualityOutcome`（二元），可以并列记录压缩率与依据保持率，而不改它们的语义。这样[父代选择](../../../版本管理/父代选择/README.md)可以按依据保持率而不是按总分排序。

另一个位置是评测报告。项目已有 `toolchainFingerprint` 这类指纹字段，把「本次压缩策略」也当作一个指纹记下来，就能事后分析「哪次门禁通过是侥幸的」。

### 与 IO-19 的关系

项目规定达标后立即清理中间候选。**如果基准文档与降级文档也要清理，就无法事后复现测量。** 建议在测量阶段保留这些中间产物，或者至少保留它们的摘要与指纹。这与父代选择专题发现的「IO-19 清理策略会削弱恢复能力」是同一类耦合。

## 研究缺口

**这个方法本身也没有现成实现可抄。** 三个来源各自只贡献一部分：

- 固定轨迹重放与三轴结构来自 KV 缓存压缩评测，**场景是推理轨迹不是代码文档**
- 实体追踪来自代码摘要幻觉检测，**只做检测不做损耗率测量，且只覆盖实体类错误**
- 下游相关性分析来自摘要评测，**它验证代理指标的相关性，但不测压缩**

组合起来才是完整的测量方案，而这个组合在文献里没有出现过。

**还需要项目自己定的两件事**：

1. **依据保持的完整判据集**。实体验证能抓「文档里说了源码没有的东西」，抓不到「源码里有但文档没说的东西」。后者是本项目最关心的（信息损耗的主要形式是**遗漏**而不是**编造**，因为知识文档刻意不写源码全文）。需要补一个覆盖度方向的判据
2. **扰动怎么构造才不破坏语法有效性**。往知识文档里注入一个错误陈述，要保证文档仍然可读、模型不会因为它明显异常而忽略它
