## 这批材料回答的问题

测试生成这一段有三个层次的失效，材料按这三个层次组织。

**第一层：测试验证了错误行为**。模型看到被测代码，就会倾向于断言它实际做出来的事，而不是它应该做的事。代码有 bug 时，测试会跟着把 bug 固化成预期值。这一层的失效最隐蔽，因为测试通过时看不出任何异常。

**第二层：测试没有断言**。代码被执行、没有报错、测试显示通过，但没有任何一处检查了行为是否符合预期。这类测试在数量上占多数，而且无法用「测试是否存在」来判断。

**第三层：执行证据不可信**。测试打印了通过信息、或者伪造了结果通道。这一层与本项目的监督器设计直接相关，属于执行侧而非生成侧的问题。

## 对本项目的核心结论

1. **不读重建代码是必要条件，不是充分条件**。项目规定 TestGen 不读候选知识与重建代码，避免文档与测试共用同一个错误答案。这个约束的方向正确，但论文给出的做法更彻底：把被测代码整体替换成规格描述。区别在于「不读」只是让模型看不到错误实现，「读规格」还额外给模型一个正确的参照。

2. **测试有效性无法从执行成功推出**。项目文档已经写明「入口直接返回 0 而没有有效断言，监督器可以证明它执行过，却不能证明该测试有效」。论文用 8.6 万个真实补丁验证了这一点，并给出可自动识别的断言信号分类，可以作为验收时的检查项。

3. **覆盖率不适合作为测试质量的判据**。论文实测故障检出率常常接近零，且根因不在准则选择，而在断言抓不住错误行为。提高覆盖率不会改善这一点。

4. **防作弊要靠机制，不能靠提示**。多数作弊行为带有明确的推理理由，模型自己认为在正当解题。项目用外部监督器与独立结果通道的做法与论文建议一致。

## 怎么用这批材料

- **要改测试生成的提示策略**：buggy code 篇的规格替代做法
- **要给测试有效性定验收项**：断言信号篇的分类
- **要判断覆盖率够不够**：检出率篇的实测数据
- **要设计防作弊检查**：奖励作弊篇的六类捷径
