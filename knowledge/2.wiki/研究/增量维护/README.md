# 增量维护 · 代码变更驱动的知识更新

代码库已有旧文档，代码持续更新。每次都跑完整知识生成流程成本太高，也不必要。本目录研究的问题是：**能不能只根据代码变更，增量更新受影响的文档，必要时再触发全量重建。**

这个问题横跨多个环节，不属于单一业务阶段，所以单独立目录。它涉及 `doc_gen` 的修订入口、`workflow_router` 的轮次决策、`Source` 的版本治理，以及知识版本之间的演进关系。与 [`../版本管理/`](../版本管理/) 的区别：版本管理关注**多个版本之间怎么组织和选择**，本目录关注**怎么从代码变更推导出「该更新什么」**。

## 结论先行

**找到了直接可用的开源实现，而且它与本项目同属 OKF 体系。**

`langchain-ai/openwiki`（⭐16,762，MIT，活跃）做的就是「维护一份随代码演进的 Markdown wiki」。它的核心机制叫 **Grounded Claims（有据断言）**：把文档里的每条事实绑定到**带版本的源码证据**上，更新前先逐一检查证据版本，只处理失配的断言。

这正好补上本项目当前最缺的一环。项目现在能**发现**源码变了（`Source.revision` 与 `observedRevision` 不一致就置 `STALE`），但没有**响应**机制：`drift` 只记录「这个文件变了」，既不说是文件的哪一部分变了，也不说哪条知识受影响。结果就是只能整模块重跑。OpenWiki 把这条路走通了。

**但有两件事必须说清楚，不要照抄**：

1. **它没有回答「知识漂移与误差累积」这个问题。** 另一篇论文（`2608.11095`）用 29.9 万次版本变迁的实证数据证明：**增量维护会让知识文件无限膨胀，而且全量重写治不好**。重写后 10 次提交内就涨回 91.5%，之后涨得更快。这是本目录最重要的警告。
2. **它没有公开的效果数据。** 唯一带数据的相关论文（`2606.09090`）只测了配置文件的失效引用，检出 23.0%，但**其中 36% 是误报**。

## 怎么用这批材料

**要设计增量更新机制** → 先读 [Grounded Claims](Grounded%20Claims有据断言.md)（机制本体）与 [行范围重定位](行范围重定位.md)（防误判），这两个合起来是可落地的骨架。再加 [契约式漂移监控](契约式漂移监控.md) 补语义层面的依赖判定。

**要先知道风险** → 读 [灾难性记忆与知识膨胀](灾难性记忆与知识膨胀.md)。**建议在动手实现之前读**，它会影响你对「增量」这个方向的预期。

**要低成本先拿收益** → 读 [陈旧引用检测](陈旧引用检测.md)。这条路不需要模型调用，纯规则，可以在 CI 里先跑起来。

## 与项目现状的接口

本项目已有、可以直接挂上去的东西：

| 已有 | 位置 | 增量维护需要补什么 |
|---|---|---|
| 源码版本与漂移检测 | `Source` 的 `revision` / `observedRevision` / `drift` | 现在只到**文件级**且只记录「变了」。需要细到**行区间级**，并映射到受影响的知识内容 |
| 溯源链接 | 知识片段的 `sources` 字段 | 现在记录位置，不记录**该位置当时的证据版本**。Grounded Claims 的全部价值就在这个版本号上 |
| 知识间差异 | `KnowledgeDiff` | 现在是**知识与知识**之间的差异，不是**代码与代码**之间的差异。增量更新需要的是后者 |
| 修订入口 | `doc_gen` 的修订流程与定位规则 | 现在由 Review 意见触发，输入是「上一版文档加纠正意见」。增量更新需要一个平行入口，输入是「代码变更」 |
| 单模块单轮 | `Orchestrator` 一次 Run 只处理一个模块 | 增量更新天然是**跨模块**的：一次提交可能影响多个模块的文档 |

最后一条是个结构性张力，值得单独决定：现有的「一轮一个模块」约束是为了让轮次可核对，而增量更新的收益恰恰来自「只碰受影响的部分」，两者粒度不同。这个取舍在 README 末尾的「还没回答的问题」里有展开。

## 还没回答的问题

1. **增量更新的触发粒度。** 按提交、按时间窗、还是按「累积到一定变更量」？OpenWiki 的选择是显式命令加定时 CI，把控制权交给人。
2. **什么时候必须全量重建。** 现有材料都只给「增量优先，必要时全量」这个原则，没人给出**升级判据**。可考虑的候选：失效断言比例超过阈值、结构变更（拆分、合并、跨模块依赖变化）、连续多轮增量后质量下降。
3. **增量与门禁的关系。** 增量更新的输出要不要重新过门禁？如果每次都过，成本优势会被吃掉一部分；如果不过，「未过门禁的改动」就进入了已发布知识，与项目现有的「未过门禁不合并」原则冲突。
4. **知识漂移的度量。** [`灾难性记忆与知识膨胀`](灾难性记忆与知识膨胀.md) 用「指令数量」当膨胀指标，本项目对应的指标是什么（正文长度、章节数、断言数）还没定。
