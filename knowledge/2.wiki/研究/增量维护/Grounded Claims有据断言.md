## 它解决了什么问题

代码库的文档一旦生成，就面临「代码改了文档不刷」的问题。做法通常有两种，都不理想。

一种是每次全量重新生成。成本高，而且会丢掉人工校订过的内容，产出也不稳定。

另一种是等人发现问题再手动改。文档慢慢过期，直到没人信它。

OpenWiki 走第三条路：**让文档里的每条事实自己带上一份「我当时是依据源码哪个位置的哪个版本得出的」记录**。代码变了以后，检查这些记录就知道哪些事实需要重新确认，其余部分不动。

这正好是本项目缺的那一环。项目现在能发现源码变了，但不知道变了以后**哪条知识受影响**，所以只能整模块重跑。

## 方法核心

### 断言（Claim）是维护的最小单位

关键设计是**把维护粒度从「文档」降到「事实」**。一份文档由若干条断言组成，每条断言独立记录自己的证据。

断言的覆盖范围在项目里对应知识文档的实质内容：行为、职责、架构、数据流、不变量、失败语义、配置、安全边界。每条断言都指向带版本的源码证据，形如指向某文件某一行的引用。

**最重要的一句话在它的文档里写得很直白**：每条断言记录的是**断言成立时所观察到的证据版本**，而不是只记录 Markdown 文件最后一次生成的时间。

这一句点破了本项目当前设计的缺口。项目 `sources` 字段记录的是位置，没有记录位置当时的版本。所以当源码变化时，项目只能拿「文件变了」这个信号去猜影响范围，而 OpenWiki 能直接判定「这条断言的证据变了，那条没变」。

### 更新流程：先确定性检查，再决定要不要用模型

流程分两段，前一段完全不需要模型。

**第一段，预检（preflight）。** 遍历所有持久化的断言，把每条断言的证据重新解析一次，然后分三类：

- 证据能解析且版本一致 → 有效，不动
- 证据能解析但版本不一致 → **失效**，需要处理
- 证据无法解析 → **未解决**，需要处理

这段是纯确定性代码。它的价值在于「干净更新跳过模型工作，wiki 内容一字不动」：如果没有失配，整个更新是零成本、零改动的。

**第二段，只把需要处理的断言交给模型。** 页面工作者（page worker）收到的是**只有需要处理的断言**，当前有效且无问题的断言被确定性地保留，不会重复塞进每一轮模型输入。模型可以确认复查过的断言、提交修订与新增、以及明确声明撤销。

这个设计对上下文预算是关键：文档可能有几十条断言，但一次更新可能只有两三条失效。把「其余都别动」做成机械保证，而不是靠提示词请求模型别动。

### 状态与正文分离

断言的完整状态不写在 Markdown 里，而是放在与正文并排的侧面文件（`openwiki/.claims/`）中。Markdown 保持干净，结构化状态独立存在。

好处是正文可以给人读，断言状态可以给程序读，两者互不干扰。项目现有设计也是这个路子（YAML 头与正文分离），可以直接对应。

### 持久化边界

页面完成的判定是**持久化边界**：只有当该页的 Markdown、断言状态、验证结果与清单条目全部落盘，该页任务才算完成。

再往上，整个运行有个全局证明：收尾时会重跑一遍全程检验，通过后才删除运行状态文件。中断后重跑会从持久队列继续，已完成的页面不会被重做。

这对本项目直接相关：项目的 IO-19「达标即清理中间候选」恰恰会清掉这些中间状态。如果照搬 OpenWiki 的做法，**清理策略需要重新划范围**，否则中断恢复的能力会被清理掉。

### 与 OKF 的接入

OpenWiki 输出 OKF v0.2 格式，把断言的证据投射到 OKF 的 `sources` 字段，并维护 `verified` 信任元数据（由哪个版本验证、何时验证）。只有在断言集非空、通过最终证据复查、并且断言状态已落盘之后，才会写入验证标记。**单纯通过预检不会产生或推进验证标记。**

这条区分值得注意：它把「我检查过了，没变化」和「我验证过了」分成了两件事。前者不足以建立信任。

### 人机分工

自动化只被用在「维护」上。它提供了定时 CI 的方案（GitHub Actions / GitLab / Bitbucket），产物是**只改文档的 PR**，合并与否由分支保护规则和人工评审决定，不自动合并文档以外的文件。

把「什么时候接受更新」留给人的流程设计，比让它自动提交要稳妥。

## 实验结果

**没有公开的量化评测。** 仓库里有 `evals/` 目录，但作者没有发布预检准确率、更新正确率或成本对比这类数字。

这一点必须如实标注。它的机制清晰、代码可读、工程完整度高，但**效果未经第三方验证**。对本项目的含义是：可以照着设计，但必须自己测。

可以确认的工程事实：

- 证据解析器对行区间的版本号形如 `repo-lines-v1:sha256:<内容哈希>:<重定位元数据>`，是可解析的、带算法前缀的不透明字符串，支持版本算法升级
- 预检的产出顺序是确定性的（按页面、问题类型、断言编号排序），便于测试与复现
- 断言侧车文件随 Markdown 一起走，可审阅

## 局限与注意

**一、没有效果数据。** 见上。机制设计值得借，具体阈值与收益必须自测。

**二、不解决知识膨胀。** 它解决的是「别重算没变的部分」，不解决「长期增量维护下知识会不会越积越臃肿」。[灾难性记忆与知识膨胀](灾难性记忆与知识膨胀.md) 给出了负面证据。**这两件事要分开预期**，别以为用了 Grounded Claims 就一并解决了膨胀。

**三、按行区间做证据单位有边界。** 代码大范围重构（函数搬家、文件拆分）时，行区间证据会大面积失配，退化成接近全量重算。它用重定位元数据缓解了一部分（见 [行范围重定位](行范围重定位.md)），但结构级变更仍需另想办法。

**四、语言与生态。** 它是 TypeScript 实现、面向 Node 生态，接口走 MCP。本项目是 TypeScript，语言层面接近；但它的证据解析器面向文件系统与 Git，接入公司本地部署的模型与内网源码需要适配。

**五、模型角色。** 它默认用宿主的编码 agent 会话来调模型，也支持十三种模型提供方与本地 OpenAI 兼容端点。这一点对本项目是好消息：本地部署模型可以接。

## 对我们项目的启发 ⭐

### 解决哪个环节的什么问题

解决 `doc_gen` 阶段的**重跑成本**问题，以及 `workflow_router` 的**轮次粒度**问题。项目现在一次 Run 只处理一个模块、每轮从头生成或按 Review 意见修订，没有任何机制判断「这次源码变更到底影响了哪几条知识」。Grounded Claims 提供的就是这个判断。

它同时补上了 `Source` 治理的一个空缺：项目已经有 `revision`、`observedRevision` 和 `drift` 字段，能识别源码版本不一致并置为 `STALE`，但 `drift` 的内容只到「检测到变化、新旧版本号、检测时间」。**它只知道文件变了，不知道文件里哪一段变了，更不知道哪条知识受影响。** 这个空档就是增量更新的入口。

### 方案要点

**第一，把溯源从「位置」升级为「位置加证据版本」。** 项目知识片段的 `sources` 现在记录源码位置。增量更新要求在同一处再记一个当时的内容指纹。这一步不改知识形态，只是给已有字段加信息，但它决定了后面所有能力能不能成立。

**第二，证据指纹的粒度按被引用的行区间算，不按整个文件算。** 按文件算会把「文件里改了一行」放大成「这个文件的所有知识都失效」，很快退化成全量重算。

**第三，更新分两段，检查在前、模型在后。** 前半段是确定性的版本比对，没有任何模型调用；只有失配的条目进入后半段的模型处理。这个分法的收益有两点：没变化时更新是零成本的；以及「其余部分不动」是机械保证，不靠提示词约束模型。

**第四，给现有 `doc_gen` 修订入口加一个平行入口。** 现有入口的输入是「上一版文档加 Review 纠正意见」，触发者是 Review。新入口的输入是「代码变更加受影响断言清单」，触发者是源码版本漂移。两者共用修订流程与定位规则，但触发条件与输入不同。

**第五，只把需要处理的条目交给模型，已有效的部分不要重复塞进上下文。** 这一点与 [读取源码](../知识飞轮/读取源码/README.md) 那批材料里「按需展开」的思路一致：能机械确定的部分就别花上下文。

**第六，增量与全量之间要有明确的分工。** 增量负责日常跟进，全量负责结构级变更与质量兜底。触发全量的判据本批材料没有答案，需要项目自己定。

### 提供了什么思路

**最重要的一条：`verified` 与「检查通过」分离。** OpenWiki 很明确：预检通过不产生验证标记。项目现在的知识状态机（`CANDIDATE` → `ACCEPTED` → `VERIFIED`）也把验证作为独立一步，这个设计取向是一致的。增量更新如果照搬，就要注意不要用「这轮没检查出错」冒充「验证通过」。

**第二条：持久化边界要按「产物完整」定义，而不是按「步骤执行完」。** OpenWiki 要求正文、断言状态、验证结果、清单条目四者齐全才算页面完成。项目可以对照检查自己的阶段完成条件。

**第三条：自动化止步于维护，接受者是人。** 定时产出只改文档的 PR，合并由人定。项目可以借用这个边界，避免自动化直接改已发布知识。

### 需要注意的

**错误一：把「没检查出错」当「验证通过」。** OpenWiki 明确禁止。项目的门禁机制更完整，不需要妥协这一点。

**错误二：清理策略会吃掉恢复能力。** 项目 IO-19 规定达标即清理中间候选。而增量维护依赖「断言状态加运行状态」长期留存，否则下次更新无法判断哪些变了。**这两个策略直接冲突**，需要在设计时一并决定。这与 [父代选择](../版本管理/父代选择/README.md) 那批发现的「IO-19 会削弱恢复能力」是同一类耦合。

**错误三：指望增量维护顺便解决知识膨胀。** 不解决。膨胀与效率是两个独立问题，见 [灾难性记忆与知识膨胀](灾难性记忆与知识膨胀.md) 的局限一节。

**错误四：把 `KnowledgeDiff` 当成现成的基础。** 项目已有 `KnowledgeDiff`，但它比的是**知识与知识**两个版本之间的差异，用于校订与比对。增量维护需要的是**代码与代码**之间的差异，再映射到知识。两者输入不同，不能直接复用。
