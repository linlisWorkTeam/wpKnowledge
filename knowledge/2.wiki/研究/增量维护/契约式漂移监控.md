# 契约式漂移监控（SkillGuard 与 DriftBench）

## 基本信息

| 项目 | 内容 |
|---|---|
| 链接 | [arXiv:2605.10990](https://arxiv.org/abs/2605.10990) |
| 标题 | Skill Drift Is Contract Violation: Proactive Maintenance for LLM Agent Skill Libraries |
| 发布时间 | 2026-05 |
| 代码 | 论文含基准（DriftBench）与方法（SkillGuard）描述，未见公开仓库 |
| 一句话总结 | 把「技能失效」重新定义为「契约被违反」，用抽取出的角色约束做监控，一轮修复成功率 78% |

## 它解决了什么问题

LLM agent 的技能库（skill library）会随环境变化而失效。已有的做法是**反应式修复**：等跑失败了再修。

论文提出改成**主动监控**，并且给了一个重新定义问题的视角：技能失效不是一个笼统的「它不管用了」，而是**某条具体的环境假设被违反**。

这个定义上的转变带来一个实际收益：**违反的假设本身就指明了该怎么修**。

## 方法核心

### 契约（Contract）是把「提到了什么」升级为「依赖什么」

抽取分两步，论文明确说这两步必须分开：

**第一步，候选提及抽取（candidate mention extraction）**，追求高召回，把技能里提到的环境元素都找出来。

**第二步，角色判定（role decision）**，判断哪些提及构成**运行义务**。

论文给的理由很关键：**只做高召回的提及抽取，正是「无契约探测」误报过多的原因。** 换句话说，光知道技能提到了某个东西不够，还要知道它是否**依赖**这个东西，依赖才构成需要监控的契约。

这一步的区分对本项目直接有用：知识文档里提到某个函数名，不等于该知识依赖它的存在。可能只是举例，可能是历史提及。**不做这层区分，失效检测的误报会淹没真问题。**

### 漂移的分类

论文构建了一个漂移基准（DriftBench），含漂移分类法、受控构造与验证、无模型参与的真实世界划分、负对照、以及人工审计。

分类法的价值在于：不同类型的漂移需要不同的检测方式，笼统的「变了」无法指导行动。

### 监控与局部化修复

契约监控的产出不只是「失效了」，还包括：**哪个值过期了、它出现在技能的哪里、什么环境条件使它失效**。

这三项合起来构成可执行的修复证据。论文用 Q3 专门验证这一点。

## 实验结果

**最有价值的一组数字**（Q3，一轮修复的严格验证通过率）：

| 修复提示方式 | 一轮成功率 | 说明 |
|---|---|---|
| 只告诉模型「这个技能过期了」 | **10%** | 无局部化的基线 |
| 给出漂移的纯文本描述 | **60%** | |
| **给出失败的契约记录** | **78%** | 一轮完成 |
| Self-refine（三轮） | 80% | 需要三轮 |
| 重写并给出完整漂移规格 | 78% | 使用了更强的 oracle 信息 |

成本对比：**契约引导的修复平均约 10K token 每个技能，三轮 Self-refine 约 18K token。**

论文的表述很克制，值得照抄它的口径：**SkillGuard 并没有在修复成功率上显著超过 Self-refine 或纯漂移文本。** 它证明的是**「被违反的契约是可执行的修复证据」**：它能用一轮就补上「模糊提示」与「多轮强方法」之间的大部分差距，同时保持检测到的失败与修改请求之间有直接对应关系。

论文还列了剩余错误类型：认证变更、schema 变更、以及被字面验证器拒绝的情况。

Q1 与 Q2 分别验证契约是否改变了监控的错误画像、以及能否迁移到在线发现。

## 局限与注意

**一、对象是技能库，不是代码知识文档。** 技能是「agent 怎么做事」的指令，知识文档是「代码是什么样」的解释。两者的漂移来源不同（技能依赖环境与工具，知识依赖代码），迁移需要论证。

**二、修复成功率没有超过三轮 Self-refine。** 优势在轮数与成本，不在上限。别把它当成效果上的突破。

**三、剩余错误集中在这几类。** 认证变更、schema 变更、字面验证器拒绝。本项目的对应类别需要自己总结。

**四、契约抽取本身依赖模型判断。** 「哪些提及构成运行义务」这一步是语义判断，会有误判，也决定了整个方法的精度上限。

**五、未见公开代码。** 基准与方法都无法直接复现。

## 对我们项目的启发 ⭐

### 解决哪个环节的什么问题

解决 `doc_gen` 增量入口的**失效判定精度**问题，以及 Review 的**修复指令质量**问题。

项目现在给 DocGen 的修订输入是 Review 的自然语言纠正意见。论文的 Q3 结果说明这类模糊输入的效果上限很低：只说「这块过期了」只有 10%，给出结构化的问题描述能到 78%。**修订输入的形态本身就是决定修复质量的关键变量。**

### 方案要点

**第一，把「提到」与「依赖」分开。** 知识文档里出现某个符号，要判断它是运行依赖还是顺带提及。只有依赖才进入失效监控。这一步直接决定误报率。

**第二，失效信号要带局部化信息，不能只说「过期了」。** 至少包含三项：哪个值过期、它在文档哪一处、什么变更导致它失效。论文的数字说明这三项能把一轮修复从 10% 抬到 78%。

**第三，给 Review 的输出定义结构化形态。** 项目已有 `Correction` 结构，可考虑在其中区分「现象」与「失效依据」。前者是「这里不对」，后者是「因为我依赖的那个东西变了」。后者才是可执行的。

**第四，监控与修复要能形成闭环并验证。** 论文用严格验证器判定修复是否成功。项目有门禁机制，可以承担同样角色。

### 提供了什么思路

**核心思路是把「知识失效」从模糊状态变成可判定的契约违反。**

「这份文档过时了」无法行动。而「这份文档假设某函数接受三个参数，该函数现在是两个」可以行动，而且能验证改对没有。

这给项目一个具体的改进方向：**在生成知识时就记录它依赖了哪些外部假设**，而不只是记录它引用了哪些位置。前者是语义依赖，后者是位置指针。

**第二条：主动监控优于被动响应。** 项目现在的修订由 Review 在评测失败后触发，属于反应式。契约监控可以在代码变更后直接判定哪些知识需要复查，不必等一轮完整的飞轮跑完。

### 需要注意的

**第一，契约抽取的精度是天花板。** 抽错契约会产生持续的误报或漏报。论文把提及抽取与角色判定分开，说明这个区分是必要的，也说明它有难度。

**第二，别指望修复成功率超过强基线。** 它的价值在轮数与成本，以及「失败与修改请求有直接对应」这个可审计性。

**第三，与 Grounded Claims 的关系要理清。** 两者可以互补：Grounded Claims 解决「证据版本变了没有」（位置层面），本方法解决「依赖的假设还成立吗」（语义层面）。前者是机械的、确定性的；后者需要模型判断。**建议前者先做**，因为成本低且确定。
