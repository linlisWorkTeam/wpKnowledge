# 陈旧引用检测（Context Rot in AI-Assisted Software Development）

## 基本信息

| 项目 | 内容 |
|---|---|
| 链接 | [arXiv:2606.09090](https://arxiv.org/abs/2606.09090) |
| 标题 | Context Rot in AI-Assisted Software Development: Repurposing Documentation Consistency for AI Configuration Artifacts |
| 发布时间 | 2026-06 |
| 代码 | 使用已有的 DOCER 工具与 `git grep`，无新增实现 |
| 一句话总结 | 两次快照的 `git grep` 就能在 CI 里扫出文档里指向已消失代码元素的引用，356 个仓库测得 23.0% 存在失效引用 |

## 它解决了什么问题

文档里的内容会失效：提到某个函数但它已被重命名，提到某个脚本但它已被删除，提到某个依赖但它已被移除。这类失效不会报错，只会在人照着文档做事的时候把人卡住。

已有的文档一致性工具（如 DOCER）本来是给传统文档设计的。这篇的贡献是把它们**迁移到 AI 配置制品**（agent 的配置文件、上下文文件）上，并测量迁移的效果。

**对本项目最直接的价值是方法极其轻量。** 它不需要模型调用，不需要向量库，只需要 Git 历史加一次文本搜索。可以直接放进 CI 当第一道门。

## 方法核心

### 两次快照差分

核心方法简单到可以直接描述完：取配置文件**第一次提交**时的内容，用正则提取出其中出现的所有代码元素（标识符、脚本名、依赖名），然后到**当前**的源码里逐个搜索，看还有没有。

搜索用的是 `git grep`。在仓库里搜不到的元素，判定为失效引用。

**这套流程不需要任何新工具**，论文明确说它「今天就能用」，可以在持续集成里跑，用来标记配置文件中那些已经从源码里消失的引用。

### 为什么这个思路值得借

它抓的是**引用完整性**，不是语义正确性。这是一个刻意收窄的范围：不去判断「文档说的对不对」，只判断「文档提到的这个东西还在不在」。

收窄换来的是确定性：这个问题有明确的机器可判定答案，不需要模型，不会有幻觉，结果可复现。

## 实验结果

数据集：**356 个仓库，612 个配置文件**。

- 正则共提取出 **29,454 个**候选代码元素
- 在 **82 个仓库**中检出 **230 处**失效引用
- 占比 **23.0%**（95% 置信区间 18.8% 至 27.2%）
- 受影响仓库中，失效引用数中位数是 1，最大是 20
- 各类配置文件的单条失效率在 **1.0% 至 1.4%** 之间，差异很小，论文未做显著性检验

准确率检验：随机抽 50 个被判为失效的元素做人工检查，**32 个（64%）是真失效**，其余是误报或模糊。误报的来源是正则过于宽泛，匹配到了普通英文词或恰好出现过的通用符号。

论文自己指出 23.0% 这个数字有**两个方向相反的偏差**：

- **低估**：两次快照的判据只能抓到「第一次提交时有效」的引用，抓不到后来新增又失效的
- **高估**：人工检查显示 36% 被判失效的元素其实是误报或模糊

所以它把这个数字定位成**可行性信号，不是精确的普遍率**。

论文也承认：检查由单一标注者完成，没有评估标注者间一致性。

## 局限与注意

**一、36% 的误报率偏高。** 这是它自己测出来的。直接拿来当门禁会拦下大量假问题。

**二、只测了配置文件。** 论文的对象是 AI 配置制品，不是代码知识文档。迁移到本项目需要重新评估准确率。

**三、样本只覆盖公开 GitHub 仓库**，且有配置文件的那些。公司内代码库的类型分布可能不同。

**四、两次快照的判据有结构性漏检。** 它只能发现「原来有、现在没了」，发现不了「原来没有、现在文档该加但没加」，也发现不了「内容变了但名字还在」。

**五、抓不到语义错误。** 函数名还在但行为已经变了，它完全看不出来。这类问题仍需要模型或人工。

## 对我们项目的启发 ⭐

### 解决哪个环节的什么问题

解决 `doc_gen` 修订入口的**低成本起点**问题，也补 `evaluation` 阶段的一个空白角。

项目当前的修订触发靠 Review 意见，是模型驱动的、有成本的。而「文档提到的函数已经不存在了」这类问题，用纯规则就能发现，没必要花模型调用。

### 方案要点

**第一，先做一层引用完整性检查，纯规则、无模型。** 从知识文档里抽出它提到的代码元素，到当前源码里搜，搜不到的标出来。这一步能独立于增量更新机制先跑起来。

**第二，用一个更早的基准快照而不是只有当前状态。** 论文的做法是拿第一次提交时的引用对当前源码。项目对应的是：拿知识生成时的源码版本作为基准。

**第三，把误报控制当成设计目标。** 36% 的误报率说明宽泛正则不可取。项目的知识文档术语比配置文件更聚焦，可以收紧匹配规则（比如只匹配已知的符号表成员，而不是任意英文词），把误报压下去再进门禁。

**第四，结果先给人看，不要直接当门禁判据。** 在误报率降到可接受之前，它的输出更适合当「待确认清单」，由 Review 或人复核。

**第五，在 CI 里跑。** 论文的落地建议就是这个。项目可以挂到提交检查上，成本极低。

### 提供了什么思路

**核心思路是「把可判定的一小部分从模型任务里摘出来」。**

陈旧引用是一个能被机器确定回答的问题。把它交给模型去判断，既浪费成本又引入不确定性。把它摘出来做成规则检查，模型就能专注在真正需要语义判断的部分（内容对不对、解释是否充分）。

这个分工对本项目的成本结构有实际意义。项目的飞轮要跑很多轮，每轮都调模型。任何能改成规则的部分，都是直接的节省。

**第二条思路：误报率也是要测的指标。** 论文没有只报检出率，同时报了人工抽检的准确率，并且把两个方向的偏差都讲清楚。这是可信报告的做法。

### 需要注意的

**第一，别把检出率当效果。** 23.0% 是「有多少仓库有这类问题」，不是「这个方法有多准」。准确性那个数字是 64%。

**第二，它和增量更新是两件事。** 它能发现文档提到的符号没了，但不能告诉你「该改成什么」。后者仍需模型。

**第三，误报的来源值得注意。** 论文的误报来自正则匹配普通英文词。项目的知识文档是中文撰写、术语集中，这个特定来源可能少一些，但会有自己的误报模式，需要实测。
