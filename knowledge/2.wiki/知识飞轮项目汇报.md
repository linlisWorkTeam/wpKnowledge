# 知识飞轮项目汇报

> 日期：2026-08-20
> 范围：项目方案与验证进展说明。详细设计见 [知识飞轮实现方案.md](设计/知识飞轮实现方案.md)、[codeagent执行手册.md](设计/codeagent执行手册.md)、[算子团队实现方案.md](设计/算子团队实现方案.md)。

## 0. 项目背景

目标场景：超大 C/C++ 业务代码仓库，每仓几十万行，文档滞后失真。我们要从源码回推解释型知识文档，形成"知识 → 代码 → 反馈"的闭环，让基于知识生成的代码持续趋近源码，同时反向验证并提升知识质量。

当前进展：设计基线已收敛（2.wiki），并已完成不依托外部编排工具的最小验证实现（mvp-flywheel），真实 LLM 端到端跑通。

## 1. 与算子团队的对比：异同

算子团队方案是知识飞轮理念在算子开发场景的完整落地（5 个角色 + 主调度，三阶段：准备 → Base 基线开发 → 飞轮循环）。我们与它高度同构，差异主要在场景与粒度。

### 1.1 相同点

| 维度 | 算子团队 | 我们 | 结论 |
|------|---------|------|------|
| 闭环理念 | 知识 → 代码 → 反馈，循环趋近 | 同左 | 一致 |
| 信息隔离 | 每角色独立新上下文，不共享历史会话 | 三角色分离，Coder 物理上看不到源码 | 我们吸收 |
| 写保护 | 受保护路径 SHA-256 快照，越权即失败 | 评测集独立 + 防作弊 + 版本控制 | 我们吸收 |
| 知识副本演进 | knowledge_worktree 副本继承，禁止重读原始 wiki | 未过门禁不合并，分数下降回滚 | 我们吸收 |
| 修订指令 | readlist 三字段（ID + 路径 + 判据） | 修订指令同构（ID + 知识段落路径 + 验证判据） | 我们吸收 |

### 1.2 差异点

| 维度 | 算子团队 | 我们 | 原因 |
|------|---------|------|------|
| 场景 | 算子开发，加速硬件评测，性能指标（avg_speedup） | 业务代码仓库，编译 + 测试 | 评测对象不同 |
| 角色粒度 | 5 角色按阶段细分（Base/Comparator/Evolver/Verifier/Landing Reviewer） | 3 执行 agent 按职责最小充分（知识生成/Coder/Review） | 粒度选择，见 §4 |
| 评测信号 | 正确率 100% + avg_speedup，单次 canonical 报告 | 测试主判 + 相似度辅助，重复评测均值 ± 方差 | 评测成本与可靠性策略 |
| 知识来源 | wiki 是输入，飞轮只演进副本 | 知识库输入，飞轮演进副本，首版生成由上游负责 | 一致 |
| 迭代上限 | max_loops = 20 | 默认 5 轮 | 先小规模验证收敛性 |
| 验证方式 | Verifier 逐条实现 + Landing Reviewer 语义审查 | 自动化评测闭环 + Review 归因 | 评测闭环自动化后不需要单独 LLM 验证角色 |

### 1.3 我们刻意不抄的部分

- 单次 canonical 评测报告：案例加速硬件评测昂贵，我们评测便宜，重复评测优先
- 性能指标退出条件：我们没有性能维度
- 轨迹驱动知识演进（读 JSONL）：我们靠 sources 溯源反查定位段落

## 2. 飞轮设计：每轮产物与预期效果

### 2.1 循环结构

```text
源码 ──▶ 知识生成 Agent ──▶ 知识文档 ──▶ Coder Agent ──▶ 临时代码
   ▲                                                          │
   │                                                          ▼
   知识生成 Agent ◀── 修订指令 ◀── 知识飞轮(编排层) ◀── 评测闭环 + Review
```

固定流水线 + 循环迭代 + 文件交接 + 编排层状态机。角色之间不直接对话，通信全部走文件产物，可审计、可断点续跑。

### 2.2 每轮产物

| 环节 | 产物 | 形态 |
|------|------|------|
| 知识生成 Agent | 知识文档（v1 首版 / 修订版） | Markdown，OKF 格式，每段带 sources 溯源 |
| Coder Agent | 临时代码 | C/C++ 源文件，编译门禁对象 |
| 评测闭环 | 评测报告 | JSON：compile_ok / passed / total / confidence / similarity / failures |
| Review Agent | 归因报告 | JSON：summary / weak_spots / corrections（readlist 三字段） |
| 编排层 | 决策 | 通过 / 迭代 / 回滚，写入状态 |
| 修订闭环 | 修订后知识 | 版本 +1，门禁通过才合并 |

### 2.3 预期效果

- **短期（P0）**：知识 → 代码 → 评测 → 归因 → 修订 → 重测全流程可跑通。MVP 已实测：真实 LLM 端到端一轮通过（8/8，相似度 0.14，非抄源码）；缺陷注入后 R1 置信度 0.00 → 修订 → R2 1.00，修订闭环有效。
- **中期（P1）**：评测集按模块构建，holdout 分层（0.2），收敛曲线用 holdout 画，量化知识质量提升。
- **长期（P2）**：知识库随代码演进，文档滞后问题闭环解决；薄弱点地图积累，反复触发差异的知识段优先重写。

### 2.4 决策规则

- confidence ≥ 门限 → 通过，合并
- confidence < 门限 → 迭代，下发修订指令
- confidence 较上一轮下降 → 回滚（防污染）

## 4. 多 agent 编排为什么这样选

### 4.1 与算子团队的归并逻辑

算子团队 5 个角色按项目阶段拆得细（基线生成与迭代实现分属两阶段，所以 Base Developer 与 Verifier 分开）。我们按职责划分最小充分集，归并如下：

| 算子 5 角色 | 归并去向 | 理由 |
|------------|---------|------|
| Base Developer | 知识生成 Agent（首版生成） | 从知识产出初始产物，不读官方实现 |
| Comparator (A) | Review Agent（差异对比环节） | 同属只读对比 + 出报告 |
| Landing Reviewer (R) | Review Agent（落地审查环节） | 与 Comparator 同属只读审查 |
| Evolver (B) | 编排层（决策）+ 知识生成 Agent（修订执行） | 案例 Evolver 既决策又执行，我们拆开 |
| Verifier (C) | Coder Agent（迭代执行） | 按清单逐条实现，评测驱动 |
| 主调度 | 编排层（状态机） | 循环决策 + 校验关卡 |

### 4.2 三条原则

1. **生成与验证分离**。案例的 Verifier 既要实现又要自我证明，我们拆成 Coder（只写不验）+ Review（只审不写）+ 评测闭环（只测不改）。依据 CRITIC：自我纠错必须调用外部验证，自评有确认偏误。
2. **评测闭环自动化**。案例由 Verifier 承担的部分评测验证工作，我们交给纯自动化单元（编译 + 测试 + 相似度），不需要单独一个 LLM 角色。评测便宜、可重复、客观。
3. **3 + 1 + 1 最小充分集**。知识生成（写知识）、Coder（写代码）、Review（审）、编排层（决策）、评测闭环（测）。任何职责都能落入这五格之一，无重叠、无遗漏。

### 4.3 为什么固定流水线 + 文件交接

- 角色之间不直接对话，通信 = 文件产物（知识 md / 临时代码 / 评测报告 json / 归因报告 json），物理交接，可审计、可断点续跑。
- 信息隔离：每角色独立上下文，历史会话只属于编排层。Coder 物理上看不到源码。
- 决策权与执笔权分离：编排层只决策不执笔，知识生成 Agent 是唯一执笔者。防止自改进放大系统性错误（Fragility / ConSelf 警示）。

## 5. 评测部分的设计

### 5.1 评测方法（三层信号）

| 层 | 信号 | 作用 | 是否参与门禁 |
|----|------|------|-------------|
| 前置 | 编译 / 静态检查（gcc/g++ -Wall -Werror） | 必过门槛，编译失败直接判失败 | 是 |
| 主判 | 测试执行通过率（confidence = passed / total） | 功能等价强证据 | 是 |
| 辅助 | 文本/AST 相似度 | 归因诊断，功能等价但写法不同不得误杀 | 否 |

可靠性约束：重复评测 ≥ 5 次报告均值 ± 方差；holdout 分层（0.2）防刷分；评测集独立 + 防背源码；变异测试验证评测集强度；规格定义到可执行级。

### 5.2 参考依据

- 测试主判：Spec-Driven Test Gen（Google）+9.8pp、TDD-Agent、Scaling TDD、Test Gen from Program Docs
- 防作弊：Code-QA-Bench（区分真读代码与背训练数据）
- 可靠性：Fragility（重复评测、顺序控制、规格精确）
- 一致性检测：CASCADE
- 评测集构建：从源码 + 专家文档构建，期望输出必须来自源码实际行为，边界用例 ≥ 30%

### 5.3 与算子团队的对比

| 维度 | 算子团队 | 我们 | 说明 |
|------|---------|------|------|
| 主信号 | 正确率（passed == total）+ avg_speedup | 测试通过率 + 相似度辅助 | 我们没有性能维度 |
| 评测次数 | 单次 canonical 报告 | 重复 ≥ 5 次，均值 ± 方差 | 我们评测便宜，优先可靠性 |
| 门禁判断 | 正确率 100% + 性能达标 | confidence ≥ 门限（可配置，默认 0.8） | 阈值策略不同 |
| 防刷分 | 评测框架独立 + 私有算子场景 | holdout 分层 + 评测集独立 + 防背源码 | 我们补了 holdout |
| 评测集 | 评测框架按算子语义自动生成 cases | 从源码 + 文档构建，探针跑源码拿期望输出 | 场景不同 |

### 5.4 门禁为什么这么设计

1. **测试通过率做主判**：功能等价的强证据，比文本相似度可靠。Google TDD 研究证明规格契约驱动的测试能提升 bug 检出率 9.8 个百分点，测试驱动路线有实证支撑。
2. **相似度只做辅助**：单一相似度门禁会误杀功能等价但写法不同的代码（同义表达、命名差异）。相似度保留为归因诊断，帮助 Review 定位"哪里不一致"，不参与通过/失败判定。
3. **编译必过是前置门槛**：成本最低、最客观的信号，编译失败直接拦截，不进测试阶段，节省迭代轮次。
4. **多信号组合**：单一指标必误判（调研结论 9），结构 + 编译 + 测试三信号互补。
5. **holdout 防刷分**：评测集参与反馈迭代会过拟合，holdout 冻结不参与，收敛曲线用 holdout 画，测的是真实泛化能力。
6. **重复评测防方差**：Fragility 证明自改进 agent 单次结果方差大，均值 ± 方差判定更可靠。
7. **防背源码**：Code-QA-Bench 证明高分可能来自背训练数据而非读知识，评测集独立 + 私有/变换代码是门禁生命线。
8. **变异测试验证评测集强度**：注入 bug 抓不出 = 评测集太弱，先验证评测集本身合格。
