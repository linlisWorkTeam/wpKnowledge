# 设计：soul 加载层级、常驻与一键卸载（问 2、问 3）

> 快照 2026-08-23。前提是 omp 现状（本知识库结论）：群聊 = 治理平面，外部 Agent CLI = 执行平面，有扩展宿主、Version/Wave/审批/灰度，Connecter P0-P3 已本地验证（[实施状态](../../规划/Connecter%20P0-P3实施状态.md)）。

---

## 1 · 加载到哪个层级：群文化 + 成员个性，两层绑定

soul 不是"加载到群里"或"加载到 agent 上"二选一，而是**两个正交维度**：

| 层级 | 是什么 | 例子 | 类似物 |
|---|---|---|---|
| **Group 级 soul（团队气质）** | 这个群"什么氛围、什么纪律、怎么协作" | 开发群 = 严格评审文化；调研群 = 怀疑论者文化 | clowder 的"团队强项/SOP"、AGENTS.md（仓库级）、OpenClaw 工作区 |
| **Agent 级 soul（成员个性）** | 群里的每个 agent"是谁、什么性格、负责什么" | 评审鹰、架构军师、文档工匠 | clowder 的猫个体（cat-template）、SillyTavern 角色卡、OpenPersona persona |

**答案"是不是 agent 接入的时候加载"：** 接入时绑定只是一种时机，完整设计是三个时机都支持——

1. **接入/建群时绑定（默认）**：给 agent 配 soul、给群配气质（soulspec CLI 的 `install --use <platform>` 就是这个模式：装 soul 并激活）；
2. **会话启动时注入（常驻）**：每次会话把 soul 内容注入上下文前缀（AgentOS 的"启动加载顺序"：SOUL.md → STYLE.md → IDENTITY.md → AGENTS.md → MEMORY.md → examples）；
3. **运行中热切换（丰富）**：`switch` 即换即生效，带上下文移交（OpenPersona 的 handoff：对话摘要/待办/情绪状态交给新 soul）。

**注入点（抄 clowder 调研结论 + OpenPersona 实践）**：`上下文前缀 + 群公告 + 成员卡片`，**不动任务状态机**——soul 是壳，不是电梯。OpenPersona 的实现细节可抄：切换人格时只替换 `SOUL.md` 里 `<!-- OPENPERSONA_SOUL_START -->` 与 `<!-- OPENPERSONA_SOUL_END -->` 之间的块，用户自己的笔记不动，且**只换"是谁"，不换"能干什么"**（技能/工具保留）。

**注入优先级与冲突仲裁（多 soul 叠加时必答）**：平台安全策略 > 群气质 > 成员个性 > 默认人格；群气质与成员个性冲突时以群气质为准，并由关键字面检测给出冲突告警（"先看 SPEC" vs "快速出活"这类矛盾在绑定时就提示，不在运行中悄悄吞掉）。

**⚠ CLI 注入可行性（P0 开工前必做）**：omp 执行面是外部 CLI agent（Claude Code/codex/opencode 等），各家"注入人格"的方式不同（`-p` 参数 / 文件约定 CLAUDE.md/AGENTS.md / 不支持）。P0 前先出**「CLI × 注入方式矩阵」**；不支持注入的 CLI 至少降级为"群公告 + 任务描述里体现 soul"，并在该 agent 上禁用"热切换"只保留"接入时绑定"。

**注入预算（P0 成本项）**：群气质 + 成员个性全量注入 = 每次会话的固定 token 开销（执行面按 token 计费）。建议：SOUL.md 注入版 ≤ 2KB/agent；群气质与成员个性合并渲染（不重复段落）；高风险长上下文任务可配置"轻量注入"。

## 2 · 加载之后怎么常驻：四层常驻机制

soul 的"常驻"不是靠一个开关，而是靠四层各自负责（参照 soulspec 的 Soul Memory 四层架构，[原文](https://github.com/clawsouls/soulspec/blob/main/docs/platform/soul-memory.md)）：

| 层 | 存什么 | 常驻机制 | 关键设计 |
|---|---|---|---|
| **配置常驻** | 群/agent ↔ soul 的绑定关系 | SQLite（omp 已有持久化）+ 面板配置 | 重启不丢绑定；换机可迁移 |
| **注入常驻** | 每次会话的人格上下文 | 会话启动时从 soul 包渲染注入前缀 | 人格与"今天的任务"分离：每 session 都重新加载完整人格，防人格被对话带偏 |
| **记忆常驻** | soul 的阅历 | 身份/经验分离：**T0 身份（SOUL.md 等，不可变、人授权才改）** → T1 常青记忆（决策/架构，不衰减）→ T2 工作记忆（带日期的经验，指数衰减）→ T3 会话记忆（随会话消失） | 解决"记忆-身份悖论"：记忆太好会侵蚀身份，全忘则断连续性 |
| **活性常驻** | soul 的主动性 | HEARTBEAT.md / 定时任务：soul 在空闲时主动汇报、提醒 | OpenPersona `heartbeat`（workspace-digest 只报真实数据）；可接 omp 的心跳/定时任务机制 |

**与 omp 知识飞轮的关系**：T1/T2 记忆的"提炼/晋升"与现有 flywheel 的"harvest → 提炼 → ingest 门禁"同构，可以直接复用——soul 的经验沉淀就是给记忆文件跑的 mini-flywheel。

## 3 · 一键卸载：能做，且答案必须是"能"

**结论：一键卸载不是可选项，是 soul 功能上线的前提。** 理由：soul 是"关系资产"，用户会投入感情；如果装上容易、拆下麻烦，反向伤害最大（clowder 调研的原话："关系资产不可回收"是最大风险）。

**卸载语义 = 解绑 + 停注入 + 资产保留**，业界现成机制：

| 环节 | 业界机制 | 可抄的点 |
|---|---|---|
| 解绑 | OpenPersona `uninstall` / `switch`；soulspec `use`/`restore`（一键回退到上一个 soul，且 `USER.md`/`MEMORY.md`/`TOOLS.md` 受保护永不被覆盖） | 解绑只动人格块，用户记忆与工具配置永不被删 |
| 停注入 | AgentOS：删掉 soul 文件 → agent 退回"无性格的普通 LLM" | 卸载后 agent 依旧能干活（soul 是壳） |
| 上下文移交 | OpenPersona switch 自动生成 `handoff.json`（对话摘要/待办/情绪），新 soul 读取后无缝续聊 | 换 soul 不丢上下文 |
| 资产带走 | OpenPersona `export` → zip，`import` 到别处；soulspec 支持导出为 CLAUDE.md/.cursorrules/system-prompt | soul + 它的记忆都应该能导出 |
| 进程内停用 | 本知识库 DSH 的动态插件先例：`cordis_stop`（停）+ `cordis_undefine`（删） | omp 扩展宿主已有同类生命周期可对齐 |

**omp 的 UX 建议**：卸载按钮 = "卸载并保留记忆资产（可导出 zip）" / "彻底删除"两级；卸载后群里 agent 变"无名但可干活的默认人格"，群任务语义不受影响——这正是"soul 是壳不是电梯"的验收标准。

## 4 · 落地清单（伪代码级）

```
soul 表（SQLite）: id, package(路径), specVersion, group_id?, agent_id?, heartbeat?, state
群绑定表: group_id ↔ soul_id(群气质) ；agent_id ↔ soul_id(成员个性)
启动注入: session_boot(group, agent) -> render(soul.SOUL.md) + render(群公告) -> 前缀
热切换: switch(group, from, to) -> 生成 handoff -> 替换注入块 -> 记录审计
卸载: unload(group, soul, keepAssets=true) -> 停注入 + 保护 USER/MEMORY + 可选 export zip
心跳: cron(群, soul.heartbeat) -> 主动消息（只报真实数据）
```
