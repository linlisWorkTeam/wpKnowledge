# 制造：流水线生产 soul 与预制群组（问 6）

> 快照 2026-08-23。问题：soul 除了预制模版，是否还能流水线制造——workpanel 自己生产 soul？代价如何？是不是需要支持预制群组？预制群组如何打通一条 soul 生产线？整个 workflow 如何定制？

---

## 1 · 结论先行

**能，而且"预制群组 = soul 生产线"就是最顺的落地形态。** 流水线制造 soul 的业界先例已经开源（OpenPersona 的 persona-seed：人群语料 → SeedProfile → persona.json → 成品包），而 omp 的知识飞轮（[endlessWpKnowledgeRunner 飞轮](../../调研/endlessWpKnowledgeRunner飞轮实现分析.md)）已经验证过 "harvest → agent 提炼 → 打分门禁 → 入库" 的同构管道——soul 生产线就是给这套管道换个"产物"。

## 2 · 业界先例：流水线已经有人跑通

| 先例 | 流水线内容 | 可抄的点 |
|---|---|---|
| **OpenPersona persona-seed 技能** | 用户意图 → 语料库搜索（MatrAIx Persona 1M 等）→ 3-5 候选重排 → SeedProfile → 补全缺口 → persona.json → `openpersona create` → 成品包 + 溯源文件 | 整条"意图→候选→补全→生成→溯源"流程；**有溯源（seed-provenance）是精髓** |
| **OpenPersona presets 工厂** | 6 个预设 = 由声明文件经 7 阶段生成管线（clone→validate→load→derive→prepare→render→emit）自动产出完整包 | "小而精的声明文件 → 自动补全大包"的生成模式 |
| **soulspec 发布体系** | `validate`（schema）→ `soulscan`（安全/质量扫描）→ `test`（schema+行为测试）→ `publish` 注册表 → `diff` 版本对比 | **上架前必须有质量门禁**；soul 也讲版本与 diff |
| **clowder** | 猫的名字/性格"从真实对话里自然长出来" | soul 的"出生"可以是半自动的（人参与命名与定调） |
| **ClawHub / openpersona.co** | soul/skill 目录与市场，人人可发布、安装计数 | 商店模式 = 生产线的"出口" |

## 3 · 预制群组为什么是必经之路

**预制群组（群模板）是 soul 生产线的"车间"，理由有三：**

1. **生产线本来就是一群角色分工**——采集员、提炼师、评审、发布员，各有各的 soul 与工具；这恰恰是 omp 的群聊形态最擅长的（多 agent 分工 + 群内可见协作过程）。
2. **预制群组同时是"建群推荐"的下发通道**：建群推荐（03 章）要给人"一键就用"的组合，预制群组（含成员 soul、工具、工作流模板）就是那个组合的载体。做一次基建，两处受益。
3. **产物闭环可观测**：生产线是"作品即宣传"——生产过程中群里能看到一步步怎么造出一个 soul，这本身就是 omp 孵化的叙事（对应战略里的"AI 协作文档/调研连载"）。

## 4 · 整条 workflow 如何定制（建议设计）

```
输入：资料包（仓库 README/文档/对话导出/团队风格描述）或 只读意图（"造一个前端团队 soul"）
  │
  ▼ 采集（SoulFactory 群 · 采集员）：归拢资料、去重、标注来源（L1 原文/L2 转述）
  ▼ 提炼（提炼师）：4 维提取——思维模式 / 说话方式 / 记忆锚点 / 边界与底线
  ▼ 评审（评审员 · 人在环）：草案 + 证据分级 L1-L4，冲突以高证据级为准；人可改、可毙
  ▼ 门禁（复用飞轮打分）：结构完整性 / 溯源率 / 可验证性 / 去重 / 与现有货架不冲突
  ▼ 发布（发布员）：写入 soul 商店（soul.json + 版本 + tags + 封面）→ 建群推荐可用
  ▼ 回灌（可选）：开放"contribute"通道，用户改进可回灌官方（OpenPersona 的 Persona Harvest 模式）
```

**定制点**：① 输入适配器可插拔（对话导出/文档/语料库/人工描述）；② 提炼维度模板可换（工程 soul 用 4 维，文化 soul 用 MBTI 映射）；③ 门禁阈值可调（**正式门禁以 12 章总纲为准**；本节为流程示意，早期用 checklist 跑通再自动化）；④ 产出可以直接导出为 soulspec/OpenPersona 兼容包（承接 01 章的"格式兼容"决策）。

## 5 · 代价评估（诚实版）

| 项目 | 量级 | 说明 |
|---|---|---|
| soul 包格式 + CRUD + 绑定/注入 | 小 | 借 soulspec 子集，主要工作量在渲染注入 |
| 群模板（预制群组）基建 | 中 | 群模板 = 成员配置 + 工具 + 工作流脚本；omp 已有群/agent/扩展宿主，主要是"模板化"改造 |
| SoulFactory 生产线（采集/提炼/评审/门禁/发布） | 中 | 大部分是 prompt 工程与流程编排；门禁在飞轮管道**旁**挂同构新脚本（接口对齐、实现独立，P0 先手工 checklist——飞轮打分器为知识卡设计，"直接复用"未验证） |
| 内容质量 | **最大的隐藏成本** | 生产线跑通容易，"产出的 soul 真的好用"难——需要评审标准、样例库（good/bad outputs）、跨模型保真验证（[Cross-Model Persona Fidelity](https://zenodo.org/records/18849974) 的做法） |

**一句话代价（估，待基线）**：代码是中型功能（约 1-2 个 sprint），内容工程是长期投入——这与知识飞轮的教训一致：**工具便宜，标准贵**。

## 6 · 与"预制群组支持"的关系

- **必须支持预制群组**，但不需要等全部做完：第一版只需要"群模板 = 预设成员组合 + 预设 soul 列表"，即可支撑建群推荐；SoulFactory 生产线作为第一个吃螃蟹的预制群组（内部先跑），边用边打磨模板系统。
- 预制群组的开放顺序建议：**先官方 1-2 个（开发四人众 / SoulFactory），再开放用户自建**，避免一上来就掉进模板生态治理的深坑。
