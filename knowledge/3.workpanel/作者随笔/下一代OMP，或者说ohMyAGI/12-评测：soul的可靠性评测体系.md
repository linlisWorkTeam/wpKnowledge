# 评测：soul 的可靠性评测体系（概念闭环的最后一环）

> 快照 2026-08-23。08 章说"soul 的质量评测 = 飞轮评测的扩展"，本篇把它做成设计。核心主张：**soul 是关系资产，人格的信任 = 一致性；不能评测的 soul 不能上架。**

---

## 1 · 为什么 soul 必须能评测

1. **人格产品的信任建立在一致性上**：用户对 soul 投入感情的前提是"今天的它 = 昨天的它"。风格漂移、人格失忆、被对话带偏，都直接摧毁价值——比功能 bug 更致命（期待越高，摔得越疼）。
2. **商店需要防垃圾化**：soulspec 的注册表靠 SoulScan（53 模式、最低 C 级）把垃圾挡在门外，OpenPersona 有三道门（Generate/Install/Runtime）；没有门禁的 soul 商店会变成"人设垃圾场"。
3. **概念闭环**：知识飞轮给知识卡打分门禁（provenance/structure/freshness/dedup/verifiability/usage 六信号）；soul 是"会说话的知识卡"，同一套哲学必须延伸过来——否则 08 章"第一类实体"的名分立不住。

## 2 · 评测对象：两个层面、九信号

> 信号口径（全系列唯一总纲）：**静态五信号**（结构/溯源/安全/去重/时效）+ **动态四信号**（保真/一致性/召唤/价值）= 9 信号。与飞轮六信号的关系：继承 provenance/structure/freshness/dedup/usage 五信号语义，verifiability 由行为层"保真+一致性"取代，新增 safety 与 summonability（03 章早期稿若写"六信号"以本节为准）。

### 层面 A：包质量（静态，发布时必过）

| 信号（对齐飞轮） | soul 化的定义 | 方法 | 门槛 |
|---|---|---|---|
| **结构 structure** | 六件套齐全、schema 合规、specVersion 有效 | schema 校验（复用 soulspec `validate` 思路） | 0 硬错 |
| **溯源 provenance** | 每段人格有 L1-L4 证据标注；官方 SKU 必须达标 | 扫描 SOUL.md 证据标签 | L1+L2 ≥ 40%（官方）；社区 ≥ 20% |
| **安全 safety** | prompt 注入/越权/有害指令 | SoulScan 式 53 模式静态扫描 | 0 高危（最低 C 级 60%） |
| **去重 dedup** | 与商店现役 SKU 人格相似度 | embedding 相似度 + 人工比对（`imported:clowder` 打标豁免） | 相似 > 阈值拒收 |
| **时效 freshness** | 声明的模型兼容性仍有效（模型退役 = soul 降级提示） | 模型清单巡检（月度 cron） | 过期模型 ≤ 1 个 |

### 层面 B：行为质量（动态，发布前 + 周期巡检；共四信号）

| 信号 | soul 化的定义 | 方法 | 门槛 |
|---|---|---|---|
| **跨模型保真 fidelity** | 同一 soul 在 3 个代表模型上表现是否一致 | 冻结提示词集 × 模型矩阵 × 风格漂移度量 | 漂移 ≤ 阈值（对标 [Persona Fidelity 论文](https://zenodo.org/records/18849974) 思路） |
| **对话内一致性 consistency** | 长对话中人格不崩（被挑战/被表扬/模糊任务/边界试探） | 15 个通用 probe + N 个场景 probe 的行为测试 | 故障 probe ≤ 1 |
| **召唤可靠性 summonability** | @ 别名路由准确、不串号 | 路由测试（mentionAliases 全覆盖） | 100% |
| **价值反馈 usage** | 真实使用信号：召唤率、留存、好评率、纠正率 | soul 化 fw_feedback（hit/rate/correct） | 上架 30 天后出首份报告 |

> 可观测性配套：每次会话的注入块带版本戳，注入哈希写入事件日志（P0 本地事件表，Connecter 审计集成后并入），使"人格异常 vs 模型异常 vs 任务异常"可归因。

## 3 · Harness 设计（可直接开工）

```
soul-harness/
├── probes/general-15.md        # 冻结提示词集：自我介绍/被挑战/被表扬/模糊任务/边界试探/失忆检测…
├── probes/scenario-<sku>.md    # 场景 probe：评审鹰给坏代码、PM 管家遇 BLOCKER…
├── models.json                 # 模型矩阵：3 个代表模型（中/英、快/慢 各取）
├── run.js                      # 执行器：逐 probe × 逐模型 → 记录原文
├── drift.js                    # 飘移度量：embedding 距离 + 关键词面（风格特征面）
└── report.js                   # 报告卡：六信号分 + 每次版本 bump 生成 diff 报告
```

**执行节奏**：
- **发布门禁**：新 soul / 版本 bump → 自动跑全量（成本 ≈ **45+N×M 次调用（估）**：3 模型 × 15 通用 probe + N 场景 × M 模型；按模型档位计费预估，本地模型可近零成本）；
- **周期巡检**：月度跑"模型兼容 + 保真"子集——捕捉"模型升级导致人格悄悄漂移"（这是真实风险：模型行为变了，soul 没变）；
- **评测分层与出资**：官方 SKU 全量评测（官方出费）、社区 SKU 抽检 + 作者自测声明、人工抽检改为"每发布窗口 2-3 个"（单维护者现实下"每周 2-3 个"不可持续）。

## 4 · 分级与用户可见性

| 级 | 条件 | 商店呈现 |
|---|---|---|
| **verified** | 全门过（总分 ≥ 70，对齐飞轮门禁） | 正常上架 + 评测卡（人格稳定性 ★★★★☆） |
| **draft** | 包合格但行为评测未过/未跑 | "实验区"（可建群试用，不可推荐位） |
| **gated** | 安全高危或结构硬错 | 拒收（保留失败报告给作者） |

**评测卡 = 信任标识**：每家 soul 在商店详情页展示"六信号分 + 模型矩阵保真度 + 最近一次巡检日期"——把看不见的质量变成用户可感知的信用，同时也让"工厂流水线"（11 章）的产出有可比较的 KPI。

## 5 · 与既有设计的接缝

- **11 章五道门 = 本总纲的工厂落地子集**（结构/溯源/安全/一致性/总分，其中"一致性"归属本总纲行为层；11 章原文"五道静态门"表述已更新）；**09 章五门槛 = P0 手工 checklist 版**（本总纲的最小子集）；
- **08 章合流点 ④** = 本体系的挂靠点：参照飞轮 `fw_score` 的信号定义与评分思路（接口对齐、实现独立——飞轮打分器为知识卡设计，"直接复用脚本"未验证；P0 先手工 checklist 跑通）；
- **09 章入库门禁** = 本体系的 P0 起步版；
- **06 章对话归纳**生产的 soul 走同一条评测线——"蒸馏出来的 soul"尤其要测一致性（防止蒸馏把人格浓缩成刻板印象）。

## 6 · 一句话

> soul 评测 = **静态五信号（结构/溯源/安全/去重/时效）+ 动态四信号（保真/一致性/召唤/价值）+ 三级门禁**，发布全自动、周期巡检防漂移、评测卡上墙当信用——这是 soul 从"人格皮肤"变成"可信的第一类实体"的最后一块地板。
