## 它解决了什么问题

多 agent 系统做代码生成很有效，但**工作流是人工设计的**：几个 agent、怎么连接、各干什么，都是人拍脑袋定的。机器学习任务优化出来的工作流，换到别的任务可能完全不适配。

SEW 的目标：让系统**自动生成并优化**多 agent 工作流——包括工作流拓扑（谁连接谁）和每个 agent 的提示词，不需要人手工设计。

## 方法核心

```mermaid
flowchart LR
    A[任务描述] --> B[工作流生成<br/>LLM 生成初始工作流]
    B --> C[工作流进化<br/>变异拓扑结构]
    C --> D[Agent 进化<br/>变异提示词]
    D --> E[评估性能<br/>跑代码生成任务]
    E --> F{达标?}
    F -- 否 --> C
    F -- 是 --> G[最优工作流]
```

三个模块：

| 模块 | 作用 |
|------|------|
| **工作流生成** | 用 LLM 根据任务描述生成初始工作流（对比了 BPMN/Python/YAML/pseudo-code 多种表示法，找出 LLM 最容易理解的格式） |
| **工作流进化** | 用演化算子在拓扑层面变异：加/删/重排 agent 节点和连接 |
| **Agent 进化** | 直接进化（改 agent 提示词）和超进化（先改进化用的变异提示词本身，再改 agent） |

两个进化算子：
- **直接进化（DE）**：用变异提示词直接改工作流/提示词
- **超进化（HE）**：先优化"变异提示词"再应用——进化机制本身也可进化

工作流有效性用两个指标衡量：逻辑成功率（结构合法）+ 执行成功率（跑任务效果）。

## 实验结果

- 在三个代码生成基准上评测，包括**LiveCodeBench**
- SEW 自动设计的工作流比只用 backbone LLM 单干**提升高达 12%**
- 工作流表示法对比发现：某些表示法（如 Python/伪代码）比自然语言更适合 LLM 理解和变异
- 进化出的工作流因任务而异——验证了"人工设计不通用"的前提

---

## 局限与注意

- 演化搜索有成本：每轮变异都要跑评估
- 进化出的工作流可能过拟合特定基准
- 工作流表示法的选择影响进化效果，需要探索

## 对我们项目的启发 ⭐

### 可以直接借鉴的

**① 工作流也是可进化的对象**：我们的飞轮管线（知识生成 → 代码生成 → 对比 → 反馈）目前是固定流程。SEW 提示：**流程本身也可以优化**——比如差异分析的粒度、反馈的注入方式，都可以当超参搜。初期先固定流程跑通，后期可以引入进化。

**② "进化机制可进化"（超进化）**：HE 的思路有意思——不只是优化知识，还可以优化"优化知识的方法"（我们的差异分析 prompt 也可以迭代改进）。这是飞轮的二阶版本。

**③ 结构化表示 > 自然语言**：它发现工作流用 Python/伪代码表示比自然语言好。我们的反馈格式、知识结构也应该尽量结构化（frontmatter + 固定字段），比让 LLM 自由写文本可靠。

### 需要改造的

**① 进化对象从"工作流"到"知识"**：SEW 进化工作流和提示词，我们进化的核心对象是知识文档。可以把它的演化框架套在我们的知识上：知识 = 个体，门禁分数 = 适应度，差异分析 = 变异指导。

**② 评估信号**：SEW 用代码生成基准分数做适应度。我们用"生成代码 vs 源码相似度"做适应度——更贴合我们"知识要能还原代码"的目标。

### 需要注意的

- 演化搜索的评估成本在超大代码库上不可忽视。对海量知识做全量演化不现实，建议：先按模块小范围演化，验证有效再推广。
