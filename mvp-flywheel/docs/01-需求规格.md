# 需求规格

> 状态：Normative  
> 适用范围：`mvp-flywheel/` 代码、测试、示例和运行产物。

## 1. 系统目标与范围

| ID | 规范 |
|---|---|
| SYS-001 | 系统 MUST 验证“知识能否支持 Coder 生成行为正确的代码”，不得把脱离代码行为的文档质量分数作为主门禁。 |
| SYS-002 | P0 闭环 MUST 为：知识 → 代码 → 编译 → 测试 → 归因 → 修订 → 重测，并支持通过、迭代、回滚和有界停止。 |
| SYS-003 | 系统 MUST 演进输入知识的副本；首版知识生成属于上游能力，不应成为 runner 启动 P0 闭环的强制前置步骤。 |
| SYS-004 | 系统 MUST 面向 C/C++ 业务代码，并允许复用项目既有编译和测试体系。 |
| SYS-005 | P0 MUST 使用轻量确定性编排；不得把编排决策委托给 LLM。 |
| SYS-006 | AST/数据流相似度、多候选、变异测试自动化、性能门禁和规模化切分 MAY 在 P1/P2 实现，但不得阻塞 P0 基础合规。 |

## 2. 模型与角色

| ID | 规范 |
|---|---|
| MOD-001 | 生产角色调用 MUST 使用公司本地部署的 GLM 5.1，并优先通过公司 codeagent CLI；只有 CLI 无脚本化能力时才可使用批准的 SDK 或 HTTP API。 |
| MOD-002 | DeepSeek、公开外部 API 或其他模型 MAY 用于隔离实验，但 MUST NOT 被描述为生产基线，也不得成为默认生产配置。 |
| ROLE-001 | 知识生成 Agent 是知识的唯一执笔者；编排层只能生成决策与修订指令。 |
| ROLE-002 | Coder Agent MUST 只根据知识、需求和公开接口生成代码，不得读取源码实现、评测期望或 holdout 详情。 |
| ROLE-003 | 自动评测 MUST 只读知识并执行编译、测试和诊断，不得修改知识或生成代码。 |
| ROLE-004 | Review Agent MUST 基于客观评测结果做差异解释和知识归因；不得替代门禁状态机判定通过。 |
| ROLE-005 | 角色间 MUST 通过文件产物交接，且每个角色使用独立上下文；不得共享隐藏会话历史。 |
| ROLE-006 | 桩实现 MAY 用于单元测试和管道自检，但桩结果 MUST NOT 作为真实模型能力或知识质量证据。 |

## 3. 知识约束

| ID | 规范 |
|---|---|
| KNOW-001 | 知识 MUST 使用 Markdown，并具备可机器读取的版本、状态、来源 commit 和 symbol 级 sources；行号只作展示。 |
| KNOW-002 | 知识 MUST 说明职责、输入输出语义、算法步骤、边界条件、失败模式和设计原因。 |
| KNOW-003 | 提供给 Coder 的知识 MUST NOT 包含完整源码实现、连续函数体摘录或可直接复原实现的源码搬运；公开签名和重新组织的伪代码允许。 |
| KNOW-004 | 每次修订 MUST 只针对归因命中的知识单元，产生新版本，并保留旧版本可恢复。 |
| KNOW-005 | 未通过门禁的候选知识 MUST NOT 标记为 verified 或覆盖已接受版本。 |
| KNOW-006 | sources MUST 支持失败用例 / 源码 symbol → 知识段落的反向定位。 |
| KNOW-007 | 文档被截断或上下文不完整时，Coder MUST NOT 臆造未知语义；系统 SHOULD 产生显式“不完整上下文”状态，而不是静默继续。 |

## 4. 评测与门禁

| ID | 规范 |
|---|---|
| EVAL-001 | 编译和静态检查 MUST 是前置门槛；编译失败时本轮不得进入测试，并判为迭代或终止，而不是通过。 |
| EVAL-002 | 测试执行通过率 MUST 是门禁主信号：`confidence = passed_cases / total_cases`。 |
| EVAL-003 | `total_cases = 0` MUST 视为无效评测，不能计算为通过。 |
| EVAL-004 | 门禁阈值 MUST 可配置且来自评测集校准；任何数据模型或属性不得写死 `0.8`。 |
| EVAL-005 | 文本、AST 或数据流相似度 MUST 只进入诊断与归因，不得参与通过/失败判定。 |
| EVAL-006 | 同配置生成与评测 SHOULD 至少重复 5 次，并 MUST 报告每次结果、均值、方差和最差值；不得用“取最大通过数”掩盖不稳定性。 |
| EVAL-007 | 重复结果方差超过配置阈值时 MUST 标记为 `unstable`，不得直接通过。 |
| EVAL-008 | 期望输出 MUST 来自探针运行真实源码；无法运行时必须记录人工推导依据和待确认状态，禁止 LLM 编造。 |
| EVAL-009 | train 失败 MAY 产生具体修订反馈；holdout 详情 MUST NOT 进入 Review、知识生成 Agent 或 Coder 上下文。 |
| EVAL-010 | 候选知识必须先通过 train，再做 holdout 验证；最终发布结论 MUST 同时报告 train 与 holdout。 |
| EVAL-011 | native 与 JSON 两种评测集 MUST 具有一致的门禁语义；若某种格式不支持 holdout，系统必须 fail closed 或明确标记“不可发布”，不能静默跳过。 |
| EVAL-012 | LLM Review 的判断 MUST 与自动评测报告交叉验证；LLM 不能修改 `compile_ok`、`confidence` 或最终 decision。 |

## 5. 安全、隔离与防污染

| ID | 规范 |
|---|---|
| SEC-001 | 业务源码 MUST 位于 Coder 工作区之外；`src_dir` 对 Coder 永久拒绝，即使配置白名单试图放行。 |
| SEC-002 | 生产配置 MUST 显式提供 `interfaces_dir`；不得回退到 `src_dir` 让 Coder 或评测间接接触源码目录。 |
| SEC-003 | Coder 可读范围 MUST 限于当前知识、公开接口和本轮输出目录；默认不应把整个 `work_dir` 的历史报告和 traces 暴露给 Coder。 |
| SEC-004 | evalset MUST NOT 向 Coder 暴露 expected output、golden 实现或 holdout 详情。 |
| SEC-005 | 所有路径检查 MUST 在规范化后执行，并防止 `..`、符号链接或前缀碰撞绕过。 |
| SEC-006 | 受保护路径 MUST 在角色执行前后做完整 SHA-256 校验；仅记录截断哈希而不验证，不满足写保护。 |
| SEC-007 | 知识来源或反馈来源不可信时 MUST 停止自动合并并进入人工检查。 |
| SEC-008 | 公开源码用于评测时 SHOULD 做语义保持变换，降低训练数据记忆造成的假高分。 |

## 6. 修订、状态机与审计

| ID | 规范 |
|---|---|
| FLOW-001 | 编排状态至少 MUST 包含 `pass / iterate / rollback / unstable / stopped`。 |
| FLOW-002 | 主指标低于上一已接受基线时 MUST 回滚；不得仅回退版本号而保留同一内容。 |
| FLOW-003 | 达到轮次、时间或成本上限时 MUST 以 `stopped` 结束并报告未收敛原因。 |
| FLOW-004 | 修订指令 MUST 包含稳定 ID、知识段落路径和可执行验证判据；纯自然语言建议不能直接触发合并。 |
| FLOW-005 | 修订队列 MUST 保留 pending、done、failed 状态和处理证据；成功或失败后不得无审计地清空历史。 |
| OBS-001 | 每轮 MUST 持久化知识版本、生成代码、自动评测报告、归因报告、修订指令和最终决策。 |
| OBS-002 | 评测报告 MUST 记录 run ID、知识版本、评测集版本、源码 commit、编译环境、每次重复结果、均值、方差、最差值和 decision。 |
| OBS-003 | holdout 报告只向编排层暴露聚合结果；详细失败不得落入生成角色可读目录。 |
| OBS-004 | 所有运行产物 MUST 可关联到同一 run ID，并能复现使用的配置与输入版本。 |

## 7. P0 验收边界

P0 合规需要满足：

- 角色权限和源码隔离可验证；
- 编译、测试、重复评测、门禁与回滚由确定性代码执行；
- train / holdout 信息隔离成立；
- 知识版本和所有关键报告可审计；
- 生产模型约束与配置一致；
- 规格对应的验收场景自动化通过。

仅有 demo 一轮全通过、相似度较低或 LLM 自述“未抄源码”，都不能单独证明 P0 合规。
