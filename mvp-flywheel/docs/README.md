# mvp-flywheel SDD 文档入口

本目录把 `knowledge/2.wiki/设计/` 中已经收敛的项目设计转化为 `mvp-flywheel` 的可执行约束。这里采用 SDD（Spec-Driven Development）：**规格先于实现，验收场景先于代码变更，代码与测试必须能追溯到规格 ID。**

## 1. 权威关系

1. 项目级设计源以 [`knowledge/2.wiki/设计/`](../../knowledge/2.wiki/设计/) 的 6 份正式文档为准。
2. 本目录是这些项目级设计在 `mvp-flywheel` 代码范围内的约束投影。
3. 当本目录与代码或 `mvp-flywheel/README.md` 冲突时：
   - 目标行为以本目录的规范性规格为准；
   - 当前实际行为以代码和测试为准；
   - 两者不一致必须记录在[当前差距与实施顺序](05-当前差距与实施顺序.md)，不得把未实现能力写成“已满足”。
4. 当本目录与项目级设计冲突时，先更新项目级设计并完成决策，再同步本目录。

## 3. 规范词

- **MUST / MUST NOT**：违反即不符合该规格，不得合并或发布。
- **SHOULD / SHOULD NOT**：原则上必须满足；偏离需要记录原因和风险。
- **MAY**：可选能力，不影响基础合规。
- **CURRENT**：当前代码已具备，仍需测试证明。
- **PARTIAL**：部分具备，但存在明确缺口。
- **GAP**：当前未实现或实现方向与规格冲突。
- **DEFERRED**：明确不在 P0 范围。

## 4. SDD 变更流程

任何改变角色权限、门禁判断、评测集、状态机、报告结构、模型接入或知识版本行为的代码变更，必须按以下顺序进行：

1. 在 `01-需求规格.md` 中新增或修改规格 ID。
2. 在 `04-验收场景.md` 中增加对应 Given / When / Then 场景。
3. 更新 `06-追踪矩阵.md` 中的代码和测试落点。
4. 实现代码，并添加自动化测试。
5. 运行验收命令，记录结果；未满足项继续保留在 `05-当前差距与实施顺序.md`。
6. 只有规格、实现、测试和说明一致后，才能把差距状态改为 `CURRENT`。

禁止仅修改 README 宣称能力已经完成；README 只能概述由规格和测试证明的能力。

## 5. 基线验收命令

```bash
python -m pytest tests -v
python verify_sandbox.py
python verify_isolation_layout.py
```

真实模型端到端验证必须使用公司允许的 GLM 5.1 接入，并在具备相应凭据和内网环境时运行。当前环境若缺少 `pytest`、编译器、模型凭据或网络，必须报告“未执行及原因”，不能把未执行写成通过。
