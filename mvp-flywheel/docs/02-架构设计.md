# 架构设计

> 状态：Normative architecture  
> 约束来源：[需求规格](01-需求规格.md)

## 1. 系统上下文

```text
受保护源码区                         飞轮工作区
┌──────────────────┐                ┌───────────────────────────────┐
│ src-biz/          │                │ knowledge/  interfaces/       │
│ 源码实现，只读     │                │ eval-public/  artifacts/      │
└───────┬──────────┘                └───────────────┬───────────────┘
        │ 仅知识生成/受控评测                         │
        ▼                                             ▼
  KnowledgeGen ──知识候选──▶ Coder ──临时代码──▶ Evaluator
        ▲                         源码不可见             │
        │                                              │客观报告
        └────修订指令──── Orchestrator ◀── Attribution ◀┘
                              │
                              └── pass / iterate / rollback /
                                  unstable / stopped
```

## 2. 组件职责

| 组件 | 当前代码落点 | 目标职责 |
|---|---|---|
| 配置 | `fw/config.py::Config` | 路径、模型、门禁、重复评测、资源上限和安全策略的唯一配置入口 |
| 编排层 | `fw/runner.py::KnowledgeFlywheel` | 确定性状态机和文件交接，不执行 LLM 主观决策 |
| 沙箱 | `fw/sandbox.py` | Coder 路径最小权限、源码永拒绝、输出路径约束 |
| 角色接口 | `roles/__init__.py` | 稳定的 KnowledgeGen / Coder / Review 协议和数据模型 |
| 模型适配 | `roles/llm_roles.py` | GLM 5.1 / codeagent 适配、独立上下文、结构化输入输出 |
| 自动评测 | `eval/` | 编译、测试、重复统计、辅助相似度和 train/holdout 执行 |
| 修订 | `revise/` | 修订队列、版本演进、回滚和审计 |
| 存储 | `storage/` | 知识、运行产物、基线版本和不可变历史 |

## 3. 信任边界

### 3.1 源码区

- `src-biz/` 或 `Config.src_dir` 保存业务实现。
- 只有知识生成 Agent 和受控的探针/评测进程可访问。
- Coder 进程、Coder prompt、Coder 环境变量和 Coder 可读日志中不得出现源码正文或路径。

### 3.2 Coder 区

Coder 最小输入：

1. 当前知识版本；
2. 任务需求；
3. `interfaces/` 中的公开声明；
4. 本轮专属输出目录。

Coder 不应读取整个 `knowledge_dir`、历史 `work_dir`、评测报告、失败期望或其他轮次 traces。路径白名单应按**文件或本轮目录**授予，而不是按宽泛根目录授予。

### 3.3 评测私有区

- `eval-public/`：仅含可公开给运行器的测试入口和接口，不向 Coder 暴露期望。
- `eval-private/`：expected outputs、holdout、可选 protected golden 和探针证据，仅评测进程可读。
- 当前仓库可保留简化夹具，但生产布局必须区分这两类数据。

## 4. 文件产物协议

推荐运行目录：

```text
artifacts/<run_id>/
├── config.snapshot.json
├── knowledge/
│   ├── candidate_v1.md
│   └── candidate_v2.md
├── code/
│   ├── round_001.cpp
│   └── round_002.cpp
├── eval/
│   ├── train_round_001.json
│   ├── train_round_002.json
│   └── holdout_final.json
├── attribution/
│   └── round_001.json
├── corrections/
│   └── ledger.jsonl
├── protection/
│   ├── before.json
│   └── after.json
└── result.json
```

要求：

- 每个文件包含或可由路径确定 `run_id`、round 和版本。
- 报告采用 UTF-8、稳定字段和原子写入。
- holdout 明细存入生成角色不可读位置；对生成侧只输出聚合 decision。
- 旧轮次不可覆盖，新运行不可复用未清理的可变队列。

## 5. 状态机

```text
INIT
  │
  ▼
GENERATE_CODE
  │
  ▼
COMPILE ──失败──────────────▶ ITERATE 或 STOPPED
  │通过
  ▼
TEST_REPEATED
  ├── 方差过大──────────────▶ UNSTABLE
  ├── 指标倒退──────────────▶ ROLLBACK
  ├── 未达阈值──────────────▶ ATTRIBUTION → REVISE → GENERATE_CODE
  └── train 达标────────────▶ HOLDOUT
                                  ├── 达标 → PASS
                                  └── 未达标 → STOPPED/ITERATE
```

门禁状态只能由确定性代码根据规范字段计算。Review 输出的文字不得直接设置状态。

## 6. 知识版本模型

一个知识版本至少包含：

```yaml
title: <module>
status: draft | verified | rejected
version: <monotonic integer>
source_commit: <full commit>
sources:
  - file: <relative path>
    symbol: <stable symbol>
    lines: <display only>
parent_version: <version or null>
run_id: <run id>
```

版本规则：

- 修订产生新对象，不原地修改已接受对象。
- `verified` 只能在 train 和发布所需 holdout 均通过后设置。
- rollback 必须恢复已持久化的父版本内容、元数据和索引，不是只做 `version - 1`。

## 7. 防护设计

- 路径校验使用 `Path.resolve()` 后的父子关系判断，避免字符串前缀误判。
- 符号链接目标必须仍位于允许根内。
- 执行角色前记录受保护文件的完整 SHA-256，执行后重新计算并比较。
- 检测到越权读取、越权写入、哈希变化或 holdout 泄露时，本轮立即失败并记录安全事件。

## 8. P0 与后续边界

P0 实现编译、测试、统计、隔离、修订、回滚和审计。P1/P2 才引入 AST/数据流相似度、多候选、覆盖率/变异测试自动化、鲁棒性变换、性能门禁和全库调度。后续能力不得改变 P0 的角色权限和测试主判原则。
