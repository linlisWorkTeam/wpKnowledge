## 它解决了什么问题

人类开发者理解一个仓库，靠的不只是读代码，还有**视觉结构**：文件夹层级、依赖关系图、文件组织方式，一眼就能建立"这个项目长什么样"的心理模型。

但 coding agent 几乎完全以文本方式消费仓库——把文件内容拼进上下文。这有两个问题：

1. 丢失了结构信息（哪个目录是核心、依赖怎么流转）
2. 上下文爆炸（全塞进去装不下，选择性塞又漏信息）

论文想验证：如果 agent 能"看到"仓库的视觉结构，仓库级软件工程任务会不会做得更好？

---

## 方法核心

```mermaid
flowchart LR
    A[仓库] --> B[生成视觉结构表示<br/>目录树/依赖图/关系图]
    B --> C[视觉输入<br/>给 Agent 的视觉通道]
    C --> D[Agent 结合文本+视觉<br/>理解仓库]
    D --> E[仓库级任务<br/>定位/修复/生成]
```

核心想法：把仓库的目录层级、依赖关系渲染成图像（类似人看到的项目结构图），作为额外的视觉输入给 agent。agent 结合文本内容和视觉结构做决策。

论文做了系统性实验，对比：
- 纯文本 agent（现状）
- 文本 + 视觉结构 agent（本方法）

在多个仓库级软件工程任务上评测（导航、定位、理解类任务）。

---

## 实验结果

- 加入视觉结构后，agent 在仓库级任务上表现显著提升
- 特别是在需要全局理解的场景（跨文件定位、理解模块职责）收益最大
- 视觉结构帮助 agent 建立"仓库地图"，减少盲目检索

（详细指标见论文 Evaluation 章节）

---

## 局限与注意

- 需要额外生成结构图像，有成本
- 视觉输入依赖多模态模型能力（我们只有 GLM 5.1，要看它是否支持图像输入）
- 图的质量（渲染方式）影响效果

## 对我们项目的启发 ⭐

### 可以直接借鉴的

**① 结构信息的价值**：即使不做视觉输入，"让 agent 感知仓库结构"这个方向是明确的。我们的知识生成 Skill 和代码生成 Agent 都应该显式注入仓库结构（目录树、依赖图），而不是只有代码文本。可以用文本形式的结构描述（tree + 依赖列表）达到类似效果，不一定要图像。

**② 知识文档里带结构上下文**：我们的知识文档可以包含"这段代码在仓库结构中的位置"（哪个模块、依赖谁、被谁依赖）——这等于把视觉结构沉淀进知识，让消费知识的 Agent 天然拥有结构感知。

### 需要改造的

**① 视觉 → 结构化文本**：如果 GLM 5.1 不支持图像，就退化为文本结构表示（目录树 ASCII、依赖关系文本）。效果打折但思路保留。

**② 结构感知 → 门禁环节**：对比"生成代码 vs 源码"时，结构层面的对比（模块划分、依赖关系是否一致）也是相似度的一部分，可以纳入门禁维度——不只比代码文本，也比结构。

### 需要注意的

- 检查 GLM 5.1 是否多模态。如果支持，可以试点"结构图 + 代码"双通道；不支持就用文本结构表示，成本更低。
